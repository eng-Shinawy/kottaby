## 1. Summary

- **`useOnboardStudentMutation(directoryVariables: AdminStudentsQueryVariables): OnboardStudentMutation`** — `useMutation(adminOnboardStudentWithOfflinePaymentMutationDocument, { refetchQueries: [{ query: adminStudentsQueryDocument, variables: directoryVariables }], awaitRefetchQueries: true })` per the `useAdminUsersDirectory.ts:77-97` idiom. Returns:
  - `onboardStudent(input: AdminOnboardStudentOfflineInput): Promise<AdminOnboardStudentWithOfflinePaymentMutation_adminOnboardStudentWithOfflinePayment | null>` — thin wrapper over the mutator that resolves with the mutation payload (`result.data?.… ?? null`) AFTER the awaited directory refetch completes; rejections propagate untouched (the feedback hook is the single catch point).
  - `submitting: boolean` — mutation `loading`.
  - The refetch variables are the CALLER's live directory page/filter state (mirrors `useDirectoryMutations(variables: AdminUsersQueryVariables)`), so the refreshed row lands on the page the admin is looking at — never a hardcoded page 1.
- **`useOnboardStudentFormFeedback(): OnboardStudentFormFeedback`** — `runWithFeedback`-style error mapping mirroring `useAdminUserFormFeedback.ts:4-16`: the caller's submit action must let rejections propagate; `runWithFeedback(action)` clears both stores, awaits the action once, and projects any rejection — `extractFieldErrors` non-empty → `serverFieldErrors` (VALIDATION `extensions.fields[]`, field-keyed, inline `helperText`); otherwise `globalError = extractErrorMessage(err)` (field-less failures → the shell's top-level alert band). Server messages render VERBATIM — no client re-translation. Returns `serverFieldErrors` (typed `OnboardStudentFieldErrors` — the dialog prop's exact type), `globalError` (`string | null`), `runWithFeedback`, and `resetFeedback()` (clears both stores without a submit — the close affordance uses it so a reopened dialog never greets with a stale rejection; the dialog host resets only its own draft/client errors, server state is the hooks seam's to clear).
- **`useOnboardingPlanOptions(): OnboardingPlanOptions`** — two STATEFUL `useQuery` reads (both from `@apollo/client/react`; NO `useLazyQuery`):
  - `planCatalogQueryDocument` (no variables) → `planOptions: readonly PlanCatalogQuery_planCatalog[]` — active-only BY CONSTRUCTION (`PlanCatalogService.listActiveCatalog` resolves the root field to active plans; no client-side filter, so none added), plus `plansLoading`.
  - `adminUsersQueryDocument` with `variables: { filters: { role: UserRole.Parent } }` → `parentOptions: readonly AdminUsersQuery_adminUsers_items[]` for the optional parent-association picker, plus `parentsLoading`. The root field defaults absent `page`/`pageSize` server-side (`resolveAdminDirectoryPageBounds`), so role-only filters are the sanctioned minimal shape.
  - Rows pass through VERBATIM — the dialog's option props ARE the codegen-extracted row types (zero mapping, per the no-type-mapping rule).

## 6. Carry-forward for task 4.4 (exact wiring)

The container composes the three hooks into the dialog's props:

```tsx
const { planOptions, parentOptions } = useOnboardingPlanOptions();
const { onboardStudent, submitting } = useOnboardStudentMutation(directoryVariables);
const { serverFieldErrors, globalError, runWithFeedback, resetFeedback } = useOnboardStudentFormFeedback();
const [success, setSuccess] = useState<AdminOnboardStudentWithOfflinePaymentMutation_adminOnboardStudentWithOfflinePayment | null>(null);

const handleSubmit = (input: AdminOnboardStudentOfflineInput) =>
  runWithFeedback(async () => {
    const result = await onboardStudent(input);
    if (result) setSuccess(result); // non-null swaps the dialog to the success content
  });
// on dialog close: setSuccess(null); resetFeedback(); — stale rejections/payload never greet a reopened dialog
```

- **Directory variables seam:** `useOnboardStudentMutation` requires the directory's CURRENT `AdminStudentsQueryVariables` (refetch-where-the-admin-is contract). `useAdminStudentsDirectory` builds `variables` internally but does NOT return it today — 4.4 must expose it additively (one return-surface line) so the container can thread it through; that file is 4.4's declared edit surface, untouched here (fix-or-report rule).
- `submitting` also gates the toolbar affordance per 4.4's spec (disabled while the dialog is open; the shell already disables save while `submitting`).
