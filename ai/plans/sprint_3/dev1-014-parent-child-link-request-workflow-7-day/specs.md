## 1. Executive Summary & Problem Statement

- **Feature:** The sanctioned, transactional parent↔child linking flow that converts an out-of-band handshake code into a monitored relationship: a parent re-submits the child's code (`requestParentChildLink`), the student is notified and must explicitly confirm within 7 days (B.14), and ONLY that confirmation writes `students.parent_id` (INV-P1). The flow introduces the platform's first persistent link-request record (`parent_link_requests` — statuses from the pre-existing `link_status` enum: `pending → confirmed | rejected | expired`), with lazy expiry materialization, one-parent-per-student enforcement under concurrency (B.12), and per-recipient localized notifications (request → student; accepted/rejected → parent) through the single-writer `NotificationEngine` (publish-after-commit).
- **Problem from user perspective:**
  - **Parent (Fatima):** found her child by code on the handshake page (`docs/parents/handshake-code-discovery.md`); today the "you can send a link request" affordance is a dead end — no request state, no record, no notification, no way to track or withdraw it.
  - **Student (Yusuf):** must SEE who wants to link and explicitly accept or reject from his account (Workflow 04 §4.4) — before this ticket there is no surface and no event delivering that decision.
  - **Super Admin / Platform integrity:** a parent gaining monitoring WITHOUT student confirmation is the worst-case supervision breach (INV-P1); a second parent attaching to an already-linked student (B.12) is a data-integrity breach; both must be structurally impossible, not code-reviewed.
  - **Downstream consumers:** DEV1-016 (parent monitoring portal) reads `students.parent_id` — it needs THIS ticket's guarded write as its only provenance; DEV1-017 (parent session-completion notifications, INV-P3) resolves parents through the same column; the session-completion notification contract (`notifications.relatedEntityType`) gains its first `parent_link_request` emitter.
- **Business value:** Parent supervision is the M3 release gate's first deliverable (ROADMAP §M3; SPRINT_PLAN Sprint-3 DoD line "Link requests expire after 7 days"; FR-7.2). The link request is the trust gate that makes every later parent feature (portal, notifications) legitimate.
- **Actors involved:** **Parent** (requester/canceller), **Student** (confirmer/rejecter), **System** (expiry materialization, sibling expiry), **NotificationEngine** (single-writer emit substrate), downstream observers (DEV1-016/017). No admin actor — link requests are NOT admin actions (zero `audit_logs` rows by design).
- **Non-goals (explicitly OUT of scope):**
  - NO parent monitoring reads (sessions/reports/homework/progress) — DEV1-016 owns them; this ticket ships the link, not the portal.
  - NO parent session-completion notifications — DEV1-017 (INV-P3 substrate emits once the link exists).
  - NO link revocation/unlink surface (the `Unlinked` state of Workflow 04 §2 belongs to a future revoke ticket; the FK's `ON DELETE SET NULL` semantics stay untouched).
  - NO admin-side parent-link override — Workflow 04's resolved "Admin can override … set `students.parent_id` directly during direct student onboarding" is DEV3-019 territory (direct onboarding), NOT this ticket.
  - NO scheduler/cron expiry sweep — expiry is materialized lazily at interaction points and rendered computed-on-read (a periodic sweep is a recorded forward-reference, not open debt).
  - NO expiry or sibling-expiry NOTIFICATIONS (silent expiry by decision; documented — see REQ-024).
  - NO changes to discovery (`findStudentByHandshakeCode`/`myHandshakeCode`), registration, handshake generation, the `students` table shape, the `link_status` pgEnum inventory, or the notifications engine.
  - NO `audit_logs` writes anywhere in this flow (A.5's audit trail covers ADMIN actions; this is a user-to-user handshake — denial-no-audit and success-no-audit alike).
  - NO hard-delete of any request row in production code paths (rows are append-and-transition only).

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (New Table — `parent_link_requests`, the only sanctioned schema addition):** WHEN the schema ships THEN `backend/db/schema/parents/parent-link-requests.ts` SHALL define `parentLinkRequests = pgTable("parent_link_requests", …)` with EXACTLY: `id` (identity PK), `parentId integer NOT NULL REFERENCES users(id) ON DELETE RESTRICT`, `studentId integer NOT NULL REFERENCES students(id) ON DELETE RESTRICT`, `status link_status NOT NULL DEFAULT 'pending'` (REUSING the existing `linkStatus` pgEnum from `backend/db/schema/enums.ts:54` — zero enum edits), `createdAt timestamp NOT NULL DEFAULT now()`, `expiresAt timestamp NOT NULL` (application-written `createdAt + 7 days`, NEVER default-computed), `respondedAt timestamp NULL`; indexes: `(parent_id)`, `(student_id)`, and a PARTIAL UNIQUE index `(parent_id, student_id) WHERE status = 'pending'` enforcing one live pending link per pair. Delivery SHALL be `bun run db push` per `docs/DATABASE_MIGRATIONS.md` (Drizzle-expressible; IF the partial-unique `.where(...)` proves unexpressible in the bundled Drizzle version, the fallback is ONE additive custom SQL file under `backend/db/migration/` + new drizzle folder — recorded in the ledger, never a silent workaround). NO other file under `backend/db/schema/**` may change except the one-line barrel addition in `backend/db/schema/parents/index.ts`.
- **REQ-011 (Request Creation — the R5 handshake re-submission):** WHEN an authenticated parent submits `requestParentChildLink(code)` THEN the service SHALL, in ONE `withTransaction`: (1) normalize (`normalizeHandshakeCode`) and validate (`isHandshakeCode`) the code PRE-DB (malformed → `ValidationError(handshakeCodeInvalid)`, key exists verified); (2) re-verify the ACTOR from a fresh read (`UserRepository.findById(parentActorId, tx)`) — missing row / non-parent role / governed actor (`isDeleted || isBlocked || suspended`) → denial BEFORE any write (service-layer re-check, closing the documented context-boundary governance window for THIS surface ONLY — `backend/graphql/gqlContextFactory.ts:206-216` applies no such filter; anchor re-verified at the 0.3 gate); (3) re-resolve the target via `StudentRepository.findDiscoveryByHandshakeCode(normalized, tx)` (capability-by-code — the student id is NEVER accepted from the client, per R5.1/R5.2 of `docs/parents/handshake-code-discovery.md`); (4) apply `isGovernanceExcludedFromDiscovery(row, now)` to the target (R5.4); (5) reject target-linked (`parentId !== null` → conflict) and same-pair-duplicate-pending (pre-check AND the partial-unique race → `translateDbError`-class 23505 traversal → SAME conflict); (6) insert the row with `expiresAt = now + LINK_REQUEST_TTL_MS`; (7) emit ONE in-tx notification to the STUDENT (`NotificationType.ParentLinkRequest`, `relatedEntityType: "parent_link_request"`, `relatedEntityId: request.id`, copy composed in the RECIPIENT's persisted locale via `findLocalesByIds` with `defaultLocale` fallback, verbatim-stored per the engine's §3.3 emitter-localization rule). WHEN the tx commits THEN `publishReceipts` SHALL run strictly post-commit; a push failure SHALL degrade (`NOTIFICATION_DELIVERY_DEGRADED`) and NEVER fail the request.
- **REQ-012 (Miss/Governed Collapse — Nullable Return):** WHEN the code is well-formed but resolves to no row OR a governance-excluded row THEN `requestParentChildLink` SHALL return `null` — byte-equivalent to the discovery miss channel (`docs/parents/handshake-code-discovery.md` R2/R3), NEVER an error, with ZERO rows written and ZERO notifications emitted. The field SHALL be nullable by design; observer-perspective indistinguishability is test-locked.
- **REQ-013 (Already-Linked Target):** WHEN the resolved target's `parentId IS NOT NULL` THEN the service SHALL reject with `ConflictError("PARENT_LINK_TARGET_ALREADY_LINKED", <localized>)` — an honest, code-bearing denial (the discovery surface already discloses `linkable: false`, so no new oracle exists), with ZERO writes.
- **REQ-014 (Duplicate Pending Per Pair):** WHEN a pending request already exists for (parent, student) THEN creation SHALL reject with `ConflictError("PARENT_LINK_ALREADY_PENDING", <localized>)`; the SAME conflict SHALL result from a concurrent-creation race surfacing as the partial-unique 23505 (cause-chain traversal, never top-level error reading).
- **REQ-015 (7-Day Expiry Semantics — B.14, Lazy Materialization):** `expiresAt` SHALL be stamped `createdAt + 7 * 86_400_000` ms at creation (shared constant — REQ-003). A request is actionable IFF `status = 'pending' AND expiresAt > <one captured now per invocation>` (strict-`>` parity with the applicant-cooldown predicate, `backend/services/teachers/applicant-lifecycle.service.ts` precedent). List/read paths SHALL render an expired-pending row as expired WITHOUT writing (read purity); WRITE paths (respond/cancel) SHALL materialize expiry via a guarded `UPDATE … SET status='expired' WHERE id=? AND status='pending'` inside the same tx BEFORE answering the denial (`PARENT_LINK_REQUEST_EXPIRED` on respond; cancel-of-expired answers per REQ-018). A periodic sweep is NOT shipped (ledger forward-reference to the cron stream, resolved-pointer).
- **REQ-016 (Student Confirmation — the INV-P1 write):** WHEN the owning student confirms (`respondToParentLinkRequest(requestId, true)`) THEN inside ONE tx the service SHALL: (1) re-verify the ACTOR (fresh read; student role; ungoverned — same fail-closed service re-check); (2) atomically claim the REQUEST via ONE guarded update `… SET status='confirmed', responded_at=now WHERE id=? AND student_id=<ctx.user.id> AND status='pending' AND expires_at > now RETURNING` — the ownership, liveness, and expiry predicates ride the UPDATE itself (NO read-then-write); (3) on zero rows, run the classifier: expired-pending → materialize `expired` + `ConflictError("PARENT_LINK_REQUEST_EXPIRED", …)`; resolved → `ConflictError("PARENT_LINK_REQUEST_ALREADY_RESOLVED", …)`; nonexistent OR foreign-owned → `NotFoundError("PARENT_LINK_REQUEST", …)` (constant shape — foreign ≡ nonexistent, mirroring the `NOTIFICATION_NOT_FOUND` oracle rule at `notification-engine.service.ts:161`); (4) only after a successful claim, write the LINK via ONE guarded `UPDATE students SET parent_id=<parentId from the claimed row> WHERE id=<studentId> AND parent_id IS NULL RETURNING` (NEW `StudentRepository.linkParentIfUnlinked`) — zero rows → `ConflictError("PARENT_LINK_TARGET_ALREADY_LINKED", …)` and the WHOLE tx rolls back (the request claim is NOT left committed — ghost confirmations are impossible); (5) expire ALL sibling pending requests for that student (`SET status='expired' … WHERE student_id=? AND status='pending' AND id <> <winner>`) in the same tx; (6) emit ONE in-tx `parent_link_request` notification to the PARENT (accepted copy, student's name, recipient locale); publish post-commit.
- **REQ-017 (Student Rejection):** WHEN the owning student rejects (`accept: false`) THEN the SAME guarded-claim pattern SHALL flip the request to `rejected` (+ `responded_at`), write NOTHING to `students.parent_id`, emit ONE in-tx rejection notification to the parent (rejected copy), and NEVER expire siblings (a rejection of one parent leaves other pending requests live until their own expiry — children choose parents, not first-come).
- **REQ-018 (Parent Cancellation):** WHEN a parent cancels (`cancelParentLinkRequest(requestId)`) THEN ONE guarded update `… WHERE id=? AND parent_id=<ctx.user.id> AND status='pending'` SHALL apply; zero rows → classifier produce `..._ALREADY_RESOLVED` (already answered), `..._EXPIRED` (stale — materialized), or `NotFoundError` for foreign/nonexistent — with NO write to `students`, NO notification (a withdrawn pending request is silent), and the cancelled row remaining permanently as request history. CANCELLATION MAPS TO `status='rejected'`? NO — `link_status` has no `cancelled` member and the enum is frozen; a cancelled request SHALL be recorded as **`rejected`** with a documented semantic note (act of withdrawal), and the audit-free history row persists. IF product later wants a distinct vocabulary, that is a schema-enum change owned by a future ticket, never patched here.
- **REQ-019 (Sibling Expiry on Confirmation):** WHEN a confirmation commits THEN every OTHER pending request targeting the same student SHALL transition to `expired` inside the same transaction (their opportunity window closed); NO notification SHALL be emitted to those sibling parents (silent — REQ-024).
- **REQ-020 (Self-Scoped Reads):** WHEN a parent calls `myOutgoingParentLinkRequests` (role-gated Parent) THEN the system SHALL return their requests newest-first (capped at 50, no pagination surface) with per-row computed display-status (expired-pending renders expired); WHEN a student calls `myIncomingParentLinkRequests` (role-gated Student) THEN the incoming rows SHALL carry the parent's FULL name (sanctioned disclosure — the confirmation decision requires knowing who asks, Workflow 04 §4.4) while the outgoing rows SHALL carry only the student's MASKED name via the existing `maskFullName` helper (`shared/lib/mask-full-name.ts:53-62` — imported at `student-handshake.service.ts:49`, used at `:151`; re-verified by Task 0.2) — never raw student PII expansion on the parent surface.

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (Transaction Boundaries — Exact Membership):** request-create tx = { fresh actor read, code resolution, insert, notification insert } + post-commit publish; confirm tx = { actor re-check, guarded request claim, guarded students link write, sibling expiry, notification insert } + post-commit publish; reject/cancel tx = { actor re-check, guarded flip, notification insert (reject only) } + post-commit publish (reject only). EVERY repository/service call inside a tx SHALL receive THAT tx (no `tx`/`db` mixing).
- **REQ-041 (Guarded-Update-Only Rule — No TOCTOU):** EVERY state transition (`pending → confirmed | rejected`, claim-with-ownership-and-expiry, `students.parent_id` link write, sibling expiry, expiry materialization) SHALL be a SINGLE guarded `UPDATE … WHERE <predicates> RETURNING` statement; SELECT-then-UPDATE is PROHIBITED; the zero-row class is resolved by the documented classifier probes (existence vs status vs ownership).
- **REQ-042 (Concurrent Confirmation Race — Exactly One Winner):** WHEN two parents' pending requests for the SAME student are confirmed concurrently (two distinct student-actor confirmations are impossible — the student confirms twice OR two raced claims interleave), THEN at most ONE confirmation SHALL commit a `students.parent_id` write; the loser SHALL surface `PARENT_LINK_TARGET_ALREADY_LINKED` (from the zero-row guarded link write) with its ENTIRE tx rolled back (no claim, no notification row, no sibling expiry); final state: exactly ONE confirmed request, exactly ONE linked parent, all other pendings expired, exactly ONE notification per direction.
