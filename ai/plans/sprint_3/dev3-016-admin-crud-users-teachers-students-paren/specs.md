Per the DEV2-004 precedent, existing infrastructure (registration pipeline, applicants lifecycle, governance context) is **consumed, never rebuilt**.

## 1. Executive Summary & Problem Statement

- **Feature**: The Super Admin's canonical user-management surface for Draft Academy. One directory listing every user across roles (`admin`, `teacher`, `student`, `parent`) with filtering (role, governance status, country, sanitized text search), pagination, and role-child status projection (applicant status and verification state for teachers; linkage/subscription presence headline for students; linked children count for parents). A detail view resolves the full user profile plus its role-child record. The surface supports generic user creation (identity only), whitelisted profile update, and soft-delete/reactivate with self-protection. Every mutation emits an append-only `audit_logs` row via the DEV2-003 `AuditLogWriteContract`.
- **Problem from user perspective**:
  - **Super Admin**: needs ONE directory to answer "who is this person, what role are they in, are they suspended/deleted, is this teacher an applicant or certified?" without SQL. Needs to create identities (e.g., a parent account for a phone-only onboarding), fix a mistyped name/phone, and soft-delete abusive accounts — with every action permanently logged (FR-10.1, FR-10.5, A.5).
  - **Student (Yusuf) / Teacher Applicant (Ibrahim) / Parent (Fatima)**: are NEVER affected beyond their own validity — their balances, subscriptions, applicant attempts, cooldowns, and parent links MUST survive any admin edit/soft-delete/reactivate untouched (INV-U1, INV-U5, INV-TV6).
  - **Downstream admin tickets**: DEV3-017 (deeper governance states), DEV3-018 (cold-start), DEV3-019 (direct onboarding), DEV3-020 (audit browsing), DEV3-021 (session governance), DEV3-022/022b (disputes/financials) all need this directory core and its audit-emission pattern to exist first.
- **Business value**: This is the M3 release-gate's central deliverable ("Admin can perform all governance operations with audit logging") and the foundation under five subsequent tickets. It converts "full CRUD visibility" from prose into a permission-gated options contract and locks the governance fields (A.7) behind a tested boundary so no future admin surface re-litigates identity, soft-delete, or audit plumbing.
- **Actors involved**:
  - **Caller**: Super Admin (`role = 'admin'`) — the ONLY actor permitted on every operation.
  - **Observed actors (cross-actor effects)**: created/updated/soft-deleted users, whose login/session-creation ability flips through the existing DEV2-001/DEV2-002 fail-closed governance boundary (this ticket never re-tests that whole boundary's internals, only asserts the junction: soft-deleted ⇒ context denial).
  - **Explicitly NOT actors**: students, parents, teachers (applicant or certified), anonymous callers — every surface returns `FORBIDDEN` (authenticated non-admin) or `UNAUTHORIZED` (anonymous) before any resolver body executes.
- **Non-goals** (explicitly OUT of scope for DEV3-016):
  1. **Plan catalog CRUD** — shipped by DEV1-005; this ticket only links out from detail views (no plan mutations).
  2. **Subscription management** (extend/renew/cancel/proration) — DEV1-009; **direct student onboarding with subscription + offline payment + parent association** — DEV3-019.
  3. **Cold-start teacher certification** (`is_approved=true` / `is_evaluator=true` writes) — DEV3-018. Admin user creation with `role=teacher` produces an **applicants row** (per the registration mapping), NEVER a `teacher` row (B.7).
  4. **Suspend/block window management** (`suspended`, `suspended_period_days`, `is_blocked`) — DEV3-017. This ticket ships `is_deleted` soft-delete/reactivate only; the detail view READS the other governance flags.
  5. **Parent-link override** (writing `students.parent_id` directly) — admin link override is exercised inside DEV3-019's onboarding flow, not here; this ticket's update whitelist structurally omits `parentId`.
  6. **Session governance** (reschedule/cancel/reassign) — DEV3-021; **financial surfaces** (payments list, wallet inspection, withdrawal approval, adjustments) — DEV3-022b; **dispute arbitration** — DEV3-022.
  7. **Audit-trail browsing UI** — DEV3-020. This ticket WRITES audit rows; it does not read them back.
  8. **Email change and password reset flows**, role mutation (`users.role` is immutable post-creation except through owning lifecycle flows), and **hard delete** of any user (structurally impossible — no delete surface exists; INV-U4).
  9. **Any schema change** — all columns/enums exist from DEV1-001; discovered gaps escalate via `deferred-items.md`, never patched inline.

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (Admin User Directory)**: WHEN an admin queries the directory THEN the system SHALL return a paginated list of users with fields: `id`, `fullName`, `email`, `phone`, `role`, `country`, governance summary (`isDeleted`, `suspended`, `isBlocked`), `lastActiveAt`, `createdAt`, plus a role-child status headline per row: for `teacher` users → applicant status (`ApplicantStatus` via `isApplicantStatus`, fail-closed) when an `applicants` row exists, plus `teacher.isApproved`/`isEvaluator` when a `teacher` row exists; for `student` users → presence flags (`hasParentLink`, `hasActiveSubscriptionHeadline` computed by a single read, NEVER by decrementing or touching balances); for `parent` users → linked-children count; for `admin` → no extras. `passwordHash` SHALL be structurally absent from every projection (`Omit<UserSelectType, "passwordHash">` composition per DEV2-003 forbidden-field registry).
- **REQ-011 (Directory Filtering)**: WHEN filters are supplied THEN the service SHALL support independent ANDed filters: `role` (`UserRole` enum member), governance state (`active | suspended | blocked | deleted`), `country` (exact), and free-text `search` applied case-insensitively over `fullName` and `email` with ALL LIKE wildcards escaped via `escapeLikeWildcards` before query construction (the ONE injection-sensitive surface of this ticket). Unknown/empty filter input SHALL fall back to the unfiltered directory rather than erroring, except malformed pagination/enum values which fail validation (REQ-050).
- **REQ-012 (Pagination Contract)**: WHEN the directory lists THEN pagination SHALL be bounded page-based (`page >= 1`, `pageSize` in `1..100`, default `pageSize=25`), ordered deterministically by `created_at ASC, id ASC` (stable secondary key), returning `{ items, totalCount, page, pageSize }`; an out-of-range page SHALL return an empty `items` array with an honest `totalCount` (never an error, never clamped results).
- **REQ-013 (Admin User Detail)**: WHEN an admin requests `adminUserDetail(id)` for an existing user THEN the system SHALL return the full profile (all non-sensitive `users` columns incl. `dateOfBirth`, `gender`, all governance timestamps, `lastActiveAt`) plus the resolved role-child record: `teacher` row fields if present AND `applicants` row (status/attempts/cooldown) if present, `students` core fields + headline flags if present, `parents` row presence if present. IF the id does not exist (or refers to a soft-deleted-then-unknown id shape) THEN the system SHALL throw `USER_NOT_FOUND` (NotFoundError with entity `"USER"`, never the double-suffixed code) — admin surfaces use NOT_FOUND, not FORBIDDEN, because plan IDs/user PKs in a role-gated admin surface are non-sensitive enumeration data (DEV1-005 ruling).
- **REQ-014 (Generic Admin User Creation)**: WHEN an admin submits creation with `role ∈ {student, teacher, parent}` THEN the system SHALL create the `users` row plus the corresponding child row INSIDE one transaction through the same atomicity discipline as DEV1-002 (`withTransaction(outerTx)` SAVEPOINT-aware): student → `students` row with zeroed balances + unique handshake code (bounded retry per `docs/auth/user-registration.md`) and `trial` handling exactly as DEV1-004's provisioning entry point semantics allow (reuse the same single entry point if already landed, otherwise record the trial grant as a ❌ deferred dependency on DEV1-004's contract rather than re-implementing it); teacher → `applicants` row only (status `pending`, `verification_attempts=0`, `cooldown_until=NULL`), NEVER a `teacher` row (B.7/INV-TV1); parent → `parents` row. The admin sets the initial password server-side; `email` uniqueness failures SHALL translate 23505→`ConflictError` via the existing cause-chain traversal. NO subscription, payment, teacher assignment, or parent-link is created by this operation (DEV3-019).
- **REQ-015 (Role Immutability at This Surface)**: WHEN an admin attempts to create an `admin` user through this surface THEN the operation SHALL be rejected with `ValidationError` code `ADMIN_ROLE_CREATION_FORBIDDEN` (the service-only `createAdminUser` path remains untouched and is NOT wired to any GraphQL mutation by this ticket); WHEN any update input carries a role change THEN it SHALL be rejected by structural absence (the patch type omits `role`) AND a runtime guard SHALL re-verify that the stored `role` is never overwritten (BFLA defense-in-depth).
- **REQ-016 (Whitelisted Profile Update)**: WHEN an admin submits a profile patch THEN the editable whitelist SHALL be EXACTLY `{ fullName, phone, country, gender, dateOfBirth }`; the service SHALL build the update object field-by-field (never `{ ...input }`), SHALL ignore/never accept `email`, `role`, `passwordHash`, any governance field, `parentId`, handshake code, balances, or timestamps, and SHALL validate supplied fields (non-empty trimmed `fullName ≤ 255`, `phone ≤ 20`, `country ≤ 100`, `dateOfBirth` valid past date). An empty patch SHALL be rejected with `VALIDATION`; a nonexistent id SHALL produce `USER_NOT_FOUND`. On success, `updated_at` is set server-side and the returned row is the post-write `RETURNING` row.
- **REQ-017 (Soft-Delete via Guarded Update)**: WHEN an admin soft-deletes a user THEN the system SHALL execute a single guarded `UPDATE users SET is_deleted = true, deleted_at = now(), updated_at = now() WHERE id = <id> AND is_deleted = false RETURNING *` (NO SELECT-then-UPDATE); a nonexistent id SHALL yield `USER_NOT_FOUND`; an already-deleted user SHALL yield `ConflictError` code `USER_ALREADY_DELETED`. The operation SHALL NOT touch any child table, financial record, session, evaluation, or balance (INV-U1/INV-U5).
- **REQ-018 (Reactivation — Symmetric Guard)**: WHEN an admin reactivates a soft-deleted user THEN the system SHALL execute the symmetric guarded update (`SET is_deleted=false, deleted_at=NULL … WHERE id AND is_deleted = true RETURNING *`), yielding `USER_NOT_FOUND` for unknown ids and `USER_NOT_DELETED` (CONFLICT) for active users.
- **REQ-019 (Self-Protection)**: WHEN the target id equals the calling admin's own id (`ctx.user.id`) on a soft-delete call THEN the system SHALL reject with `ConflictError` code `USER_SELF_DEACTIVATION_FORBIDDEN` BEFORE any write (Workflow 05: the orchestrator cannot remove his own account; other admins MAY be soft-deleted by an admin, and the action is audited).
- **REQ-020 (Audit Emission on Every Mutation)**: WHEN create/update/soft-delete/reactivate commits successfully THEN the SAME transaction SHALL append exactly one `audit_logs` row constructed via `AuditLogWriteContract` composition (`actorId = ctx.user.id`, `actionType = AuditActionType.Create|Update|Delete|Reactivate`, `entityType = "user"`, `entityId = target id`, `details` = a capped, PII-minimal JSON summary: changed field names for updates — NEVER values for `phone`-class PII beyond what the workflow already logs, NEVER `passwordHash`, NEVER email pre/post pairs), written through the existing `AuditService` create path with the transaction's `tx`. Append-only semantics SHALL never update prior rows (A.5, INV-W6-analog for audit).
- **REQ-021 (Governance Visibility Is Read-Only Here)**: WHEN detail or directory rows include `suspended`/`isBlocked` flags THEN they SHALL be pure reads; this ticket ships NO mutation for them (DEV3-017) — the Pothos mutations surface SHALL contain no suspend/block operation (grep-verifiable).
- **REQ-022 (No Behavioral Change to Existing Surfaces)**: WHEN this ticket ships THEN `registerUser`, `login`, `refreshToken`, `me`, `myApplicantProfile`, DEV1-005 plan operations, and the DEV3-004 session lifecycle SHALL remain behaviorally byte-identical; `git diff` on `backend/db/schema/**` SHALL be empty (schema zero-drift — all columns exist from DEV1-001).

### 2.3 Security, Authorization & Tenancy

- **REQ-030 (BFLA — Admin-Only Gate on Every Operation)**: WHEN ANY new query or mutation executes THEN it SHALL carry `authScopes: { authenticated: true, role: [UserRole.Admin] }` (explicit conjunction semantics per the DEV2-004-verified pattern); anonymous callers SHALL receive `UNAUTHORIZED` (401 semantics, via the `authenticated` scope) and authenticated non-admin callers SHALL receive `FORBIDDEN` (403) BEFORE any resolver body executes. No `grantRole*`/`assignRole*`/`elevate*` surface exists by construction.
- **REQ-031 (BOPLA — Structural Whitelists)**: WHEN inputs are mapped THEN create input SHALL be `{ fullName, email, phone, password, gender?, country, role }` (closed whitelist mirroring the public registration shape minus nothing server-controlled) and update input SHALL be the REQ-016 patch whitelist; any transport-tampered extra field SHALL be ignored by explicit field-by-field mapping (grep-verified zero `{ ...input }` spreads in new files). Server-controlled fields (`id`, governance flags, `lastActiveAt`, timestamps, child-table fields, balances) are structurally unreachable.
- **REQ-032 (BOLA / IDOR — Oracle-Aware Admin Scope)**: WHEN an admin reads or mutates by id THEN the identity of the ACTOR is always `ctx.user.id` (never input), while the TARGET id is a legitimate admin-controlled parameter; the documented ruling (same as DEV1-005 REQ-032) is that on an admin-gated surface `USER_NOT_FOUND` instead of `FORBIDDEN` is acceptable because user existence is not sensitive to a full-governance admin. The canonical doc SHALL warn that this ruling MUST NOT be copy-pasted to non-admin surfaces.
- **REQ-033 (Sensitive-Field Discipline)**: WHEN any payload (GraphQL response, log line, audit detail) is produced THEN `passwordHash` SHALL never appear (structurally omitted), tokens SHALL never be logged, and audit `details` SHALL contain field names and ids only — never credentials, never full contact payloads beyond what the existing audit precedent records.
- **REQ-034 (Injection & Search Sanitization)**: WHEN the directory search/filter executes THEN: (a) `search` SHALL pass through `escapeLikeWildcards` before any `ilike`/LIKE composition; (b) all queries SHALL be parameterized Drizzle operations with NO string concatenated SQL and NO inline `--` comments inside any `sql` template; (c) malicious wildcard payloads (`%`, `_`, `\`, unicode/RTL) SHALL match literal text only (security-tier test proof).
- **REQ-035 (Cross-Role Containment)**: WHEN any creation/update/delete executes THEN applicant/verification state (`applicants.status`, `verification_attempts`, `cooldown_until`), teacher certification flags, student balances, subscription rows, and parent links SHALL remain bit-identical unless the operation is the explicit creation of a NEW user (which produces only its own fresh child row) or the explicit soft-delete marker on `users` (INV-U1/INV-U5; proven by fixture-immutability tests).
- **REQ-036 (Rate Limit Posture — Unchanged)**: WHEN these operations execute THEN they SHALL inherit the platform's existing authenticated/global limiter posture; no new public surface exists and no new limiter is added.

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (Creation Atomicity)**: WHEN admin user creation runs THEN user row + child row + audit row SHALL commit or roll back atomically inside one Drizzle transaction (SAVEPOINT-aware under test `outerTx`); a forced child-insert failure SHALL leave ZERO residual rows in `users`, the child table, and `audit_logs` (rollback proof test).
- **REQ-041 (Guarded Mutation Discipline)**: WHEN update/soft-delete/reactivate executes THEN each SHALL be a single guarded statement with `RETURNING`; zero-row outcomes SHALL be disambiguated by a follow-up existence probe ONLY on the cold path (DEV1-005 D3 pattern) into `USER_NOT_FOUND` vs the typed CONFLICT; no read-then-write mutation sequence SHALL exist.
- **REQ-042 (tx Propagation)**: WHEN any repository/audit call participates in a flow THEN every call SHALL receive the same `tx` as the optional-last parameter; mixing tx-scoped and `db`-global operations inside one flow is PROHIBITED.
- **REQ-043 (Concurrency Matrix — Mandatory Proofs)**: WHEN chaos tests run THEN they SHALL prove via `Promise.allSettled`: (a) two concurrent soft-deletes of the same user → exactly one success + one `USER_ALREADY_DELETED`, final state transitioned once; (b) soft-delete ⚡ reactivate → exactly one winner with final state consistent with the winner; (c) concurrent profile patches → last-write-wins per documented ruling (low-frequency admin surface, no version column — documented in canonical doc); (d) double-create of the same email → exactly one success + one CONFLICT (23505 traversal); (e) creation rollback leaves the directory count unchanged.
- **REQ-044 (Schema Zero-Drift)**: WHEN implementation completes THEN `git diff` on `backend/db/schema/**` and `backend/db/migration/**` SHALL be empty; no `bun run db` schema action is run by this ticket (`db reset`/`cleanGenerate` remain permanently disabled by repo policy).
- **REQ-045 (No Module-Level Mutable State)**: WHEN new modules load THEN they SHALL contain zero module-level mutable Maps/Sets/arrays; pagination and filters are computed per-request only (serverless-safe).
- **REQ-046 (Deterministic Ordering)**: WHEN directory pages are scanned across pages THEN the `(created_at ASC, id ASC)` ordering SHALL guarantee no row appears twice or vanishes between consecutive pages created between mutations (static-anchor rule documented; keyset pagination is a documented future refinement, not shipped here).

### 2.5 Validation & Error Contracts

- **REQ-050 (DomainError Discipline & Code Map)**: WHEN any failure surfaces THEN it SHALL be a `DomainError` subclass with `extensions.code` per `docs/graphql/domain-error-extensions-code.md` and the DEV3-002 taxonomy: anonymous → `UNAUTHORIZED`; non-admin → `FORBIDDEN`; missing user → `NotFoundError("USER", …)` → `USER_NOT_FOUND`; malformed/patch-empty/invalid-field input → `VALIDATION` (with `extensions.fields[]` for field-mappable failures); `USER_ALREADY_DELETED`, `USER_NOT_DELETED`, `USER_SELF_DEACTIVATION_FORBIDDEN`, `ADMIN_ROLE_CREATION_FORBIDDEN`, duplicate email (23505) → CONFLICT-family codes; unexpected failures → masked `INTERNAL_SERVER_ERROR` at the boundary. Plain `new Error(...)` is PROHIBITED.
- **REQ-051 (Localized Errors — Key Registry)**: WHEN new errors are produced THEN the keys SHALL be added under an `adminUsers` grouping inside the EXISTING `errors` namespace across `shared/locale/types/errors/index.ts`, `shared/locale/en/errors/index.ts`, `shared/locale/ar/errors/index.ts` (compile-time `MessageSchema` parity is the gate): `userNotFound`, `userAlreadyDeleted`, `userNotDeleted`, `userSelfDeactivationForbidden`, `adminRoleCreationForbidden`, `userPatchEmpty`, plus field-level validation messages; existing keys (`emailAlreadyExists`, etc.) SHALL be REUSED — no near-duplicates.
- **REQ-052 (Audit + Log Content Hygiene)**: WHEN logging occurs THEN expected rejections SHALL use `logger.logDomainError` with structured context (`code`, `entity: "user"`, `entityId`), unexpected failures SHALL use `logger.error`; NO `console.*`, NO password/token/plaintext-PII payloads; the audit `details` JSON is length-capped (≤ 2000 chars per the `audit_logs.details varchar(2000)` column) with overflow truncation — a truncated write MUST NOT fail the mutation.
- **REQ-053 (No Silent Paths)**: WHEN the happy path executes (create/update/delete/reactivate) THEN no swallowed `try/catch`, no `catch {}`, no catch-and-return-false SHALL exist; every rejection throws its typed error through the clean path (DEV3-002 REQ-026 discipline).
- **REQ-054 (Boundary Validation Before DB)**: WHEN any input is malformed (bad enum member, negative/zero/overflow id, out-of-range pageSize, invalid date) THEN it SHALL fail with `VALIDATION` codes BEFORE any DB read — the ID-channel guard (positive safe integer guard, no `as number` narrowing) mirrors the DEV3-004 pattern.

**Actor Table:**

| Actor | Role / Permission Group | CAN do (this ticket) | CANNOT do (this ticket) |
|---|---|---|---|
| Super Admin | `users.role = 'admin'` | List/filter/paginate all users; view any user detail; create student/parent/teacher-applicant identities; update whitelisted profile fields; soft-delete/reactivate OTHER users | Create admin users via this surface; touch own soft-delete; edit role/email/governance windows; hard-delete anyone; trigger certification |

| Anonymous | none | Nothing | All five operations (`UNAUTHORIZED`) |

**Journey A — Create → Observe → Govern → Reactivate (happy path + governance junction):**

1. `admin` → `adminCreateUser(role=student)` → `users` + `students` (zeroed balances, unique handshake, trial per DEV1-004 entry point if landed) + `audit_logs(create)` commit atomically; side effect: none external.
2. `admin` → directory list filtered `role=student` → new user row OBSERVABLE with correct projection.
3. `new student` → `login` → succeeds (governance clean); observes his own state via `me`.
4. `admin` → `adminSetUserDeleted(id, true)` → guarded single UPDATE + `audit_logs(delete)`; state `is_deleted=true`.
5. `new student` → `login` → system SHALL deny at the governance gate (fail-closed context — localized forbidden); `admin` → directory → row shows deleted badge.
6. `admin` → `adminSetUserDeleted(id, false)` → reactivation + `audit_logs(reactivate)`; `new student` → `login` → restored.
7. **Denial step:** `admin` → `adminSetUserDeleted(ownId, true)` → system SHALL reject `USER_SELF_DEACTIVATION_FORBIDDEN` with zero writes and NO audit row (rejection precedes persistence).

**Journey B — Teacher-Applicant Identity via Admin Creation:**

1. `admin` → `adminCreateUser(role=teacher)` → `users` + `applicants(status=pending, attempts=0, cooldown=NULL)` + audit create; ZERO `teacher` rows (B.7 lock).
2. `admin` → `adminUserDetail(id)` → applicant projection (pending/0/null) observable; `isApproved` shows no certified state.
3. `new applicant` → `myApplicantProfile` (existing DEV2-004 surface) → observes `pending` truthfully (cross-ticket contract verified, not reimplemented).
4. `admin` → `adminUpdateUser(id, { fullName })` → whitelist update + audit update; applicant row untouched (fixture-immutability assertion).
5. **Denial step:** `new applicant` → `adminUsers` → system SHALL deny `FORBIDDEN` before resolver body.

**Journey C — Legitimate Denials (RBAC matrix):**

1. `anonymous` → any of the five operations → `UNAUTHORIZED` (401 semantics), zero writes.
2. `student` / `parent` / `teacher` (applicant AND certified fixtures) → any of the five operations → `FORBIDDEN`, zero writes, zero `audit_logs` rows created by denied calls.
3. `admin` → `adminCreateUser(role='admin')` → `ADMIN_ROLE_CREATION_FORBIDDEN`, zero writes (BFLA self-elevation block).

**Cross-Actor EARS criteria:**

- **JR-A-1**: WHEN admin completes a create/update/governance mutation THEN the TARGET user observing their own next login SHALL experience exactly the state flip the admin committed (blocked when deleted, restored when reactivated), and an `audit_logs` row SHALL exist bearing `actorId = admin` for the ADMIN to later audit (DEV3-020 surface).
- **JR-A-2**: WHEN any participant observes denial (non-admin on admin operations, admin self-deletion, admin-role creation) THEN the denied caller SHALL receive a typed localized code AND the shared state (users/children/audit tables) SHALL be byte-identical to pre-call.
- **JR-B-1**: WHEN admin creates a teacher-role identity THEN the teacher-applicant observing `myApplicantProfile` SHALL see a truthful pending applicant state, and NO observer (admin included) SHALL see a certified-teacher artifact until the verification chain (out of this ticket) creates one.
- **JR-C-1**: WHEN any denial path executes during journeys B–C THEN NO `audit_logs` row SHALL be emitted for the denied attempt (write-path-only auditing — denial noise never pollutes the trail), a rule the journey test asserts by count-delta.

Each journey maps 1:1 onto `test/workflows/admin/admin-user-lifecycle.journey.test.ts` (A) and `test/workflows/admin/admin-user-denials.journey.test.ts` (B–C) in tasks.md, following REQ-078's discipline (committed fixtures, hard-delete in `afterAll`, actor-attributed sequential steps, real permission resolution, spied externalities).
