## Findings

[MEDIUM] shared/locale/ar/adminBroadcasts/index.ts:29-35 — `successToast(count)` is a NAIVE LINEAR SWITCH (0 / 1 / 2 / 3–10 / else), not the CLDR Arabic cardinal classes (zero: n=0 · one: n=1 · two: n=2 · few: n%100∈3..10 · many: n%100∈11..99 · other: else). It is correct only for count 0–99 (and coincidentally for many-class values ≥111 whose mod-100 lands in 11..99), and WRONG for every reachable count ≥100 whose mod-100 falls in `other` (100, 101, 102, 200–202, 300–302, …, 1000, 2000, **5000**) or `few` (103–110, 203–210, …, 4903–4910): the fallback renders the 11–99 accusative counted-singular "مستلماً" where the grammar/CLDR form is the singular genitive "مستلم" (other, e.g. "خمسة آلاف مستلم" at 5000) or the few plural "مستلمين" (e.g. 103, 110). All these counts are REACHABLE: `BROADCAST_MAX_RECIPIENTS = 5000` (backend/services/notifications/admin-broadcast.service.ts:70) bounds the server-returned delivered count, and real cohort sizes (a 305-student country cohort, a 1000-recipient plan cohort) hit the wrong branches. Cross-check vs R4: the claim "Arabic pluralization is NOT a naive count switch — it implements the proper CLDR zero/one/two/few/many branches" (outcome/6.1-review-R4-frontend.md:16) is FACTUALLY INCORRECT — the code is exactly a linear switch whose branch bounds hold only below 100; the parity suite then cements the non-CLDR form at :189 (`5000 → "…إلى 5000 مستلماً"`). Note this mirrors the sibling precedent the task mandated (`notificationsAr.markAllResult`/`unreadCount`, shared/locale/ar/notifications/index.ts:23-37 — same linear scheme, same latent defect for per-user unread counts >99), so it is a SYSTEMIC pattern, not a broadcast-only regression. Suggested fix: branch on `count % 100` for count ≥ 100 (few: 3..10, many: 11..99, other: 0..2 → "مستلم") or use `Intl.PluralRules("ar").select(count)`, and re-pin both suites' boundary tables in the same change.
