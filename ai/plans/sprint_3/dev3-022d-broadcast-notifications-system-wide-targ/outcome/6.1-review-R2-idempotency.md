## Q1 — Two SEQUENTIAL same-key submits, identical input → exactly one row-set + one audit + one publish?

**YES, under a healthy cache for both submits** (proof below; two documented caveats after).

- Cohort determinism: both submits resolve the identical id list — `DISTINCT` + `ORDER BY id ASC` on every selector arm (`broadcast-audience.repository.ts:110,121,132,152,175,184,194,204-213`) — so the digest input `<sorted ids>:<type>:<key>` (`emit-idempotency.ts:67-71`) is byte-identical → same claim key.
- Submit A: `claim` = `SET key "1" EX 86400 NX` resolves `"OK"` → true (`redis-claim-cache.ts:65-68`) → batch insert + audit commit atomically in ONE `withTransaction` scope (`admin-broadcast.service.ts:370-403`; engine tx-branch `notification-engine.service.ts:102-104` returns the receipt WITHOUT publishing) → post-commit `publishReceipts` (`:408`) stores the full receipt over the sentinel (plain SET, `notification-engine.publish.ts:54-59`) then publishes once (`:61-64`).
- Submit B: `claim` resolves `null` → false (`:66-67`); `get` returns the receipt JSON; `parseStoredEmitReceipt` revives it (`emit-idempotency.ts:144-185`) → `duplicate` (`:97`) → `claimOrPriorReceipt` returns `{ priorReceipt, claimKey: undefined }` (`notification-engine.helpers.ts:50-52`) → `emitForUsers` returns the prior receipt at `notification-engine.service.ts:95-97` **before any insert construction**; service detector fires (`:386-387`) → audit skipped (`:389`), publish skipped (`:407`), return value = prior receipt's recipient count (`:412`). Total across A+B: one row-set, one audit row, one fan-out.
- Caveat (a), documented D5: if A ran while the cache was unavailable (no `REDIS_URL`, outage, timeout), no claim was ever taken → B claims fresh and emits a full duplicate. Dedupe is best-effort by design (`emit-idempotency.ts:1-21`, §3.6).
- Caveat (b): cohort drift between A and B → different digest → separate emission (R1b MEDIUM-1 — not re-reported).

## Q2 — Same-key submit with DIFFERENT input (hostile): digest mismatch path; oracle leak?

**No payload/digest-mismatch detection exists anywhere** — the claim key binds ONLY `<sorted recipient ids>:<type>:<idempotencyKey>` (`emit-idempotency.ts:67-71`); title/body/relatedEntity are absent from the digest, and the stored value is the prior RECEIPT, never the request. Two hostile shapes:

1. **Different cohort, same key** → different digest → separate claim → both emissions proceed as independent fresh accepts (full duplicate broadcast + second audit — R1b MEDIUM-1's finding; engine-documented at `emit-idempotency.ts:19-21`).
2. **Same cohort, different copy (title/body)** → SAME digest → B's claim loses, prior receipt revived, B returns `priorReceipt.recipientUserIds.length` (`:412`).

Oracle analysis of shape 2: a fresh accept returns the cohort size; the replay returns the prior receipt's count — the same number for the same resolved cohort. The mutation's type is `Int!` (`admin-broadcast.mutation.ts:5,58`), and BOTH paths log nothing (`admin-broadcast.service.ts:37-40` — "happy paths, including replays, log NOTHING"). **The response is byte-identical between replay and fresh accept → no oracle leak** (the property the question probes holds). The flip side — the mutated copy is silently dropped and undetectable from the wire — is recorded as INFO-2 below (REQ-016's unconditional prior-receipt return).

## Q3 — Claim won, crash before receipt store: what does the NEXT same-key submit see?

Both crash windows verified, each with **exactly one warn**:

- **Crash before commit** (rows/audit rolled back): the sentinel `"1"` remains held (`redis-claim-cache.ts:30,66`; TTL 86 400 — `emit-idempotency.ts:30`). Next submit: `claim` → false → `get` → `"1"` → `JSON.parse("1")` yields a number → envelope object check fails → `parseStoredEmitReceipt` returns `null` (`:151-158`) → `"claim held, but no replayable receipt was readable"` → `warnIdempotencyDegraded` fires ONCE (`:94`) → `unavailable` → `claimOrPriorReceipt` still attaches the claimKey (`notification-engine.helpers.ts:53`) → **fail-open insert proceeds** → its own post-commit store (plain SET, `notification-engine.publish.ts:58`) overwrites the ghost sentinel → key healed. No other warn site fires on this path (the loser's store succeeds silently), so exactly one warn.
- **Crash after commit, before store** (rows+audit persisted, publish never ran): next submit sees the same held-sentinel → same ONE-warn fail-open → inserts a FULL duplicate cohort row-set + second audit row + publish. This is the documented recoverable-duplicate residual (D5, §3.6 — "a crashed emitter that claimed but never stored", `emit-idempotency.ts:79-81`); net effect bounded by the 24h TTL.
- Sentinel-vs-receipt discrimination is airtight: `parseStoredEmitReceipt` rejects non-envelope shapes (`"1"`, `null`, arrays, wrong field types, empty arrays — `:151-168`), so a live sentinel can never masquerade as a replayable receipt.

## Q4 — Concurrent same-key submits over the real HTTP wire: any path where BOTH proceed to insert?

**YES — the in-flight sentinel window (documented §3.6 residual; no NEW defect).** Wire trace: both requests carry the same `X-Idempotency-Key` (`ctx.idempotencyKey`, `admin-broadcast.mutation.ts:101`); both resolve the same deterministic cohort; the atomic `SET NX EX` admits exactly one winner (`redis-claim-cache.ts:65-68`). The loser immediately `GET`s the key — but the winner does not store its receipt until AFTER its transaction commits (`notification-engine.publish.ts:54-59`), and the claim is taken INSIDE the open `withTransaction` (`admin-broadcast.service.ts:370-384` → helpers `:48-49`). So for the winner's entire tx duration — up to a 5000-row batch insert + audit + commit — the loser reads the sentinel → `unavailable` → one warn → **proceeds to a full duplicate insert + audit + publish** (`emit-idempotency.ts:93-96`). Both responses are honest `Int`s. A transient cache error on the loser's claim (timeout/rejection) lands in the same arm (`:100-103`). Sharpened observation recorded as INFO-3: the duplicate window width scales with cohort size precisely because claim-then-store brackets the write unit — the residual is widest exactly for max-cap broadcasts. Known/documented (§3.6 "first emission still in flight"; REQ-041; R1b §5 row) — not a new finding.

## Q5 — The 5000-recipient cap: fail-closed pre-DB? Race between count-check and insert?

**Fail-closed pre-DB at `admin-broadcast.service.ts:293-299`**: `recipientIds.length > BROADCAST_MAX_RECIPIENTS` (5000, `:70`) → `rejectBroadcast` → throw — executed at step 4, BEFORE the `withTransaction` unit (`:370`), before the claim, before any write. **Cannot be raced past**: the insert consumes the FIXED captured array — `input.userIds.map(...)` (`notification-engine.service.ts:100`) feeding `createManyReturning` (`:103/:107`) — there is no re-query between `assertCohortSize` and the insert, so concurrent signups/role changes alter only FUTURE resolutions, never the array being inserted; row count ≡ array length ≡ checked length. No bypass exists: the service is the surface's only engine caller, and the batch duplicate-id guard (`emit-validation.ts:140-146`) plus the repo's `DISTINCT` dedupe prevent id multiplicity from inflating the insert. Inclusive edge (exactly 5000 allowed) matches the docstring ("above it", `:64-69`) and keeps ~5000×9 ≈ 45k bind params under PostgreSQL's 65 535 per-statement ceiling.

## Findings (NEW issues only — R1b's MEDIUM-1/LOW-1/INFO×2 not re-reported)

### [LOW] emit-validation.ts:73-75 (+ admin-broadcast.pothos.ts:66-67, emit-idempotency.ts:118,133-135) — `body` is unbounded end-to-end and the idempotency receipt multiplies it recipients-fold: no aggregate bound on the serialized receipt

`title` is bounded at 255 on BOTH the service (`admin-broadcast.service.ts:344`) and engine (`emit-validation.ts:70-72`) gates, but `body` is bounded NOWHERE on the broadcast chain: the GraphQL input declares a plain unbounded `t.string` (`admin-broadcast.pothos.ts:67`), the service forwards verbatim (`:376`), and the engine's gate explicitly accepts any string (`emit-validation.ts:73-75`; header line 16: "any string is accepted (no bound)") against an unbounded `text` column (`notifications.ts:36`). The idempotency machinery then serializes EVERY row of the receipt — one row per recipient, each carrying the full body — into a SINGLE Redis value (`serializeEmitReceipt` = `JSON.stringify(receipt)` over up-to-5000 rows, `emit-idempotency.ts:133-135`, stored via `:118`). Aggregate receipt size ≈ recipients × (body + row overhead) with no cap on either factor. Consequences for a large-but-insertable body (e.g. ~100 KB × 5000 recipients): (a) the store-time `JSON.stringify` and EVERY replay's `parseStoredEmitReceipt` revival (`:144-185`) build multi-hundred-MB transient strings — process-memory/GC pressure on the API process; (b) a receipt over the Redis server's `proto-max-bulk-len` (512 MB default) makes `store` reject → caught → ONE warn (`:119-121`) → the receipt is silently never replayable and every same-key retry for 24 h fail-opens into a full duplicate broadcast (dedupe quietly lost with no operator-visible signal beyond one log line). The insert amplification (5000 body copies in one statement) precedes and would usually fail first, which bounds practical reachability — hence LOW, additionally mitigated by the admin-gated surface (double gate: scope + `assertActorAdmin`).

EVIDENCE: `emit-validation.ts:16,73-75` (no body bound, by design); `admin-broadcast.pothos.ts:66-67` (wire input unbounded); `notifications.ts:36` (`text("body")`); `notification-engine.service.ts:100` (one row per recipient, each embedding `input.body` via `toNotificationInsert`); `emit-idempotency.ts:118,133-135` (whole-receipt single-value store); `:119-121` (store failure → warn → dedupe silently lost).

### [INFO] emit-idempotency.ts:161-184 — stored-receipt envelope validator has no cross-field consistency check between `notifications` and `recipientUserIds`

`parseStoredEmitReceipt` validates each array's members independently (non-empty, per-row field shapes, positive-safe-int ids) but never asserts the two arrays AGREE — a parseable value with, say, 3 rows and 5000 `recipientUserIds` (or recipient ids disjoint from the rows' `userId`s) revives cleanly, and the replay path then returns `recipientUserIds.length` as the persisted count (`admin-broadcast.service.ts:412`) while carrying 3 rows. Not reachable through the application surface (the only writer is the engine's own `serializeEmitReceipt` output for a real emission, where the arrays are built from the same insert result — `notification-engine.service.ts:104,110`), so this is defense-in-depth only; noting it because the parser's own header promises structural deviation → `null` ("bad field types" — `:139-142`) and an inconsistent envelope is a structural deviation that currently passes. Cheap hardening: `rows.length === recipientUserIds.length` (+ id-set agreement) alongside the existing non-empty checks.

EVIDENCE: `emit-idempotency.ts:161-168` (independent array checks, no cross-check); `:169-184` (member loops, no join); contract claim at `:139-142`.

### [INFO] admin-broadcast.service.ts:370-409 — concurrent same-key duplicate window spans the winner's whole write unit (window width scales with cohort size) — documented residual, recorded with sharpened evidence

Q4's verified trace: claim-then-store brackets the entire tx (claim inside `withTransaction` at `:370-384` via `notification-engine.helpers.ts:48-49`; store only post-commit at `notification-engine.publish.ts:54-59`), so the in-flight loser's fail-open duplicate window (`emit-idempotency.ts:93-96`) is exactly the winner's insert+audit+commit duration — widest for a 5000-recipient broadcast, and the loser's post-commit plain-SET store then overwrites the winner's receipt on the same key (`:58`). Documented §3.6/REQ-041 residual (not previously noted that the residual is cohort-size-scaled); disposition belongs with R1b MEDIUM-1's option (a) (service-level key derivation) or 7.1 documentation. No code change requested this wave.

EVIDENCE: `admin-broadcast.service.ts:370-384,407-409`; `notification-engine.helpers.ts:48-53`; `notification-engine.publish.ts:54-59`; `emit-idempotency.ts:79-82,93-96`; §3.6 (`docs/notifications/realtime-engine.md:149-151`).

### [INFO] admin-broadcast.service.ts:386-412 — same-cohort copy edits under a live key are silently absorbed; response provably indistinguishable from a fresh accept (verified no-oracle property; flip side recorded)

REQ-016's unconditional "duplicate → return the PRIOR receipt" (`emit-idempotency.ts:44-45,97`) means a resubmit with an edited title/body under the same compose-session key + same cohort replays the ORIGINAL emission with zero signal: no error, no audit, no log (`admin-broadcast.service.ts:37-40`), and the returned count equals a fresh accept's (`:412` — Q2's byte-identical analysis). Correct from the oracle-leak standpoint and consistent with the documented semantics; the caller-visibility gap (an admin cannot learn their edit never landed) should be stated in the 7.1 canonical doc alongside REQ-016 so the silence is specified behavior, not an oversight.

EVIDENCE: `emit-idempotency.ts:44-45,67-71,97` (digest excludes copy; unconditional prior receipt); `admin-broadcast.service.ts:37-40,386-387,407,412`; `admin-broadcast.mutation.ts:5,58` (Int! surface).

The connection-error `error` listener (`:122-128`) still bounds `error`-event fallout to a name-only log.
- R1b LOW-1 closed: worst-case in-tx Redis hold is now bounded (≈ connectTimeout for the first dial + commandTimeout per command, one retry per `maxRetriesPerRequest: 1`) instead of ioredis' unbounded default wait — the pool-pressure/lock-window amplifier during a silently-dropping Redis outage no longer exists.
- No behavior pin broke: `redis-claim-cache.test.ts` never asserts constructor options anywhere (full read — the factory matrix asserts instance type/port shape/sharing/env-gating only, `:388-475`); the double-injected suites construct `RedisClaimCache` directly and never touch the factory, so the added options are unpinned and unbroken.
