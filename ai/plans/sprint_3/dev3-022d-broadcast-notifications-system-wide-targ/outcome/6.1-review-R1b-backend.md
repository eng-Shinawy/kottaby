## Checklist verification (evidence-first)

### 1. SINGLE-WRITER rule — PASS

The service writes `notifications` rows ONLY through `NotificationEngine.emitForUsers` (`admin-broadcast.service.ts:371-384`); the only other write in the flow is the audit row via `AuditService.createAuditLog` (`:390-399`), which inserts into `audit_logs`, not `notifications`. Static sweep of the scoped files shows **zero** `.insert(`/`.update(`/`.delete(` calls in `admin-broadcast.service.ts`, `admin-broadcast.mutation.ts`, and the audience repository; the mutation invokes no engine primitive directly (`admin-broadcast.mutation.ts:88-102` — single delegation to `AdminBroadcastService.broadcast`). Engine contract honored: `emitForUsers` with `type: NotificationType.SystemBroadcast`, `relatedEntityType: null, relatedEntityId: null` (`admin-broadcast.service.ts:372-380` — REQ-019).

### 2. Service/resolver/repo delegation purity — PASS

- **Resolver thin:** guard (TS-narrowing only) → field-by-field input mapping (never a spread — `admin-broadcast.mutation.ts:89-98`) → single service call. Imports: pothos input, enums, errors, service — no repo, no engine, no logger (`admin-broadcast.mutation.ts:49-53`). Identity exclusively `ctx.user.id` (`:99`), locale `ctx.locale`, key `ctx.idempotencyKey ?? undefined` (null-absent → optional slot, `gqlContextFactory.ts:72,181,229` verified). Side-effect barrel wiring verified (`mutation/notifications/index.ts`).
- **Service holds logic:** coherence matrix, cohort guards, replay gating, audit composition — all service-owned; repo gets only validated selectors (`admin-broadcast.service.ts:122-301`).
- **Repo holds queries:** four parameterized query shapes, no business logic, no translations, no error mapping (`broadcast-audience.repository.ts:103-222`); every selector value is a bound parameter (`$n` / `eq(...)` bind) — no concatenation, no LIKE/ILIKE anywhere (so the LIKE-sanitizer is correctly inapplicable), no `sql.placeholder`, no inline `--` comments in SQL text.
- **No cross-layer imports:** service→repo/service/shared-locale only; repo imports drizzle/db/schema/enums/types only; no `@/backend/graphql` import below the graphql layer.

### 3. Transaction propagation — PASS (REQ-042 + REQ-021 + REQ-022)

- Cohort read rides `outerTx` when supplied (`resolveBroadcastRecipients(..., outerTx)` → `PlanRepository.existsById(planId, outerTx)` + `BroadcastAudienceRepository.resolveAudienceIds(selector, outerTx)`; `assertActorAdmin(actorId, locale, outerTx)` likewise — `admin-broadcast.service.ts:338,357,261,272`). When `outerTx` is absent the reads run on the pool via `queryDb` — REQ-042 explicitly sanctions this ("the audience read … MAY run outside the write tx").
- Emit insert + audit row share ONE `withTransaction(outerTx, tx)` scope (`:370-403`); `withTransaction` opens a SAVEPOINT on a supplied outer tx or a top-level transaction otherwise (`backend/lib/db/with-transaction.ts:27-35`). No global-`db` write inside the unit.
- Publish is strictly POST-commit: `NotificationEngine.publishReceipts([receipt], …)` runs only after `withTransaction` resolves, and only when `!isReplay` (`:407-409`). Verified the engine does NOT double-publish on this path: with a caller tx, `emitForUsers` takes the tx branch (`notification-engine.service.ts:102-105`) which returns the receipt WITHOUT publishing — the service is the sole publisher. Receipt STORE also cannot precede commit: it happens inside `publishReceiptsFromIndex` (`notification-engine.publish.ts:54-59`), which the service reaches only post-commit.

### 5. Race discipline — PASS (with documented residuals, none new)

- Claim cache is genuine atomic `SET key "1" EX ttl NX` → `"OK"` mapping (`redis-claim-cache.ts:65-68`); `store` is plain `SET … EX` so the post-commit receipt always lands over the sentinel (`:74-76`); `get` is plain `GET` (`:79-81`). The adapter swallows nothing — rejections propagate unchanged (verified against `attemptEmitClaim`'s catch → `unavailable`, `emit-idempotency.ts:100-103`), which is what makes the engine's fail-open handlers correct.
- Engine §3.6 (`docs/notifications/realtime-engine.md:147-151`) sequential guarantee holds in code: won → insert → commit → store → publish; held+replayable → prior receipt, no insert/publish; held+unreadable or cache error → fail-open + ONE structured warn; receipt stored ONLY post-commit (store site is `publishReceiptsFromIndex`, reached post-commit by both the own-commit and caller-tx paths).
- Inside the write unit there is no read-then-write on shared DB state: emit insert + audit insert only. The claim-then-get in `attemptEmitClaim` is claim-atomic; the `get` races only with the in-flight winner's store, and the "no receipt readable yet" outcome degrades fail-open exactly as documented (REQ-041's stated residual).
- Cohort read sits OUTSIDE the production write tx (read-then-insert across the boundary). This is REQ-042-sanctioned and idempotent-safe; its one observable consequence (cohort-drift vs the claim digest) is finding MEDIUM-1 below.
- Rolled-back unit leaves a claim held with no receipt → next same-key attempt reads the sentinel, parse fails → `unavailable` → warn + insert — exactly the documented "claimed but never stored" fail-open arm (`emit-idempotency.ts:79-81`); no ghost-receipt risk because stores are post-commit only.

## Findings (NEW issues only)

### [MEDIUM] admin-broadcast.service.ts:357 (+ context: emit-idempotency.ts:67-71, notification-engine.helpers.ts:48) — Same-key replay absorption is cohort-drift-sensitive: a changed cohort under the same compose-session key emits a FULL duplicate broadcast

The service resolves the recipient cohort FRESH on every call (`resolveBroadcastRecipients`, `:357`) and then delegates to the keyed emit, whose claim digest is `<sha256("<sorted recipient ids>:<type>:<key>")>` (`emit-idempotency.ts:67-71`). The digest therefore binds the idempotency key to the RESOLVED COHORT, not to the key alone. If the cohort's membership changes between the original submit and its retry (a signup completing, a user soft-deleted/blocked, a subscription lapsing into/inside the window) — entirely plausible inside a double-click/retry window on a busy platform — the retry computes a DIFFERENT digest, misses the held claim, wins its own claim, and re-emits the full second broadcast to the new cohort (original recipients included get duplicate inbox rows). The service's replay detector never sees a stored receipt (different key), so an audit row is also written for the duplicate.

Why this is a real tension rather than engine-intended behavior: plan decision D6 rules out no-key idempotency because "a double-click on a 5 000-user cohort writes twice — unacceptable for an admin broadcast" (`plan.md:73`), and REQ-023 promises "WHEN a duplicate submission arrives with the same key THEN the engine SHALL return the stored prior receipt" unconditionally. The shipped composition honors that promise only for a byte-identical resolved cohort. The engine header does document per-cohort keying as intended (`emit-idempotency.ts:19-21`: "a DIFFERENT cohort under the same key is a different emission and claims separately") — correct for single-/few-recipient domain emits where the recipient list is caller-fixed — but for THIS surface the cohort is server-derived and time-varying, so the documented engine semantics defeat the surface-level guarantee the plan rests on. Not previously ledgered (grepped plan/specs/tasks/outcome/deferred-items — zero prior mentions).

Suggested dispositions (owner's call, non-blocking for this wave): (a) scope broadcast keys into a key-only claim namespace at the service boundary (e.g. derive the engine input key deterministically from the compose-session key + audience SELECTOR rather than the resolved ids — the selector, unlike the cohort, is client-fixed and replay-stable); or (b) document the cohort-identity precondition of REQ-023 in specs §2.2 + the canonical doc (7.1) as the sanctioned residual, mirroring REQ-041's in-flight residual. Under (a), a drifted-cohort retry hits the SAME claim, so the residual shrinks to the engine's already-documented fail-open arms.

### [LOW] admin-broadcast.service.ts:370-384 (+ redis-claim-cache.ts:109-112) — Redis claim round-trip executes while the write transaction is already open, and the shared client sets no timeout bound

The mandated composition puts `emitForUsers` — whose FIRST act is the Redis claim (`claimOrPriorReceipt` → `attemptEmitClaim`) and, on a held claim, a second `GET` round-trip — INSIDE the open `withTransaction` scope. On the production default client (`lazyConnect: true`, `maxRetriesPerRequest: 1`, no `connectTimeout`/`commandTimeout` override — ioredis defaults apply), a first-connect to an unreachable (silently dropping) Redis waits out ioredis' default 10 s connect timeout while the PostgreSQL transaction (and, under an `outerTx`, the outer unit's SAVEPOINT) is held open — a pool-pressure/lock-window amplifier precisely during a Redis outage. Plan-mandated shape (REQ-040/§4.1 step 5 require the claim inside the unit), so this is a hardening note, not a contract violation: consider `commandTimeout` (or an explicit `connectTimeout`) on the shared client so a cache outage cannot stretch the DB hold. MEDIUM-1's option (a) would additionally shrink the in-tx cache surface for retries.

### [INFO] redis-claim-cache.ts:116-122 — Connection-error listener logs per ioredis `error` event; no coalescing under prolonged outage

The `error`-event listener is load-bearing (prevents unhandled-`error` crashes) and hygiene-clean (`errorName` only, never the URL/keys), mirroring the sanctioned `IoredisFanoutClient` posture — but ioredis' default retryStrategy re-fires `error` on every reconnect attempt indefinitely, so a prolonged outage yields one `NOTIFICATION_CLAIM_REDIS_UNAVAILABLE` warn per attempt on a process-lifetime client, on top of the engine's per-keyed-emit degrade warn. No REQ-034 violation (no PII/keys/copy); flagging only as a noise-posture observation for the hardening stream (a first-failure-only or backoff-coalesced warn would match the "one structured entry" docstring reading).

### [INFO] admin-broadcast.service.ts:364,387 vs tasks.md:136 — Implementation improves on the task text's replay-detector formula (verified correct, record the delta)

tasks.md 2.4 pins the detector as `idempotencyKey !== undefined && options?.cache !== undefined && receipt.emitClaimKey === undefined`; the implementation evaluates `engineOptions.cache`, where `engineOptions = options ?? { cache: resolveBroadcastClaimCache() }`. With the production resolver passing no options, the task-text form would make the cache conjunct permanently false and every replay would write a duplicate audit row + re-publish. The code's form is the correct one and matches what the engine actually received. No action needed beyond carrying the formula correction into the 7.1 canonical doc so the task text doesn't become a regression trap.
