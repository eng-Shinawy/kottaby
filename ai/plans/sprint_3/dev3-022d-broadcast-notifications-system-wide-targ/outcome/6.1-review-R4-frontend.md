## Probe answers (evidence trail)

**Probe 1 — state-machine holes.**
- Dialog CANNOT open with an already-invalid audience: `handleFormSubmit` (Container:87-95) re-checks `audienceReady` at submit time and returns early; while the modal dialog is open the form is unreachable (MUI Dialog focus trap + backdrop), and no code path clears a companion while `confirmOpen` is true (only `changeAudienceKind` clears, which requires the radio — unreachable through the modal). The `planId` chosen is pinned as a string in the draft; a mid-dialog plans refetch cannot invalidate client state (server re-validates plan existence).
- Send CANNOT fire while the plan catalog is loading: `isAudienceReady` Plan branch requires non-null positive-integer `planId` (helpers:116-120); `planId` is only settable from the loaded Select; outer button also disabled via `!audienceReady` (Form:66). Loading shows Skeletons on `output[aria-busy]` (Companions:84-91). Failure state of the plans query, however, is indistinguishable from an empty catalog → finding F4.
- successCount staleness: content cannot go stale (it only changes on a new success), but the TOAST PRESENTATION can — the mounted `Snackbar` is reused across consecutive successes and the v9 auto-hide timer does NOT restart (see F2).

**Probe 2 — double-submit.** The OUTER submit button IS guarded during the send window, on two layers: `disabled={props.sending || !props.audienceReady}` (Form:66) and the handler re-check `if (sending || !audienceReady || titleError !== undefined) return;` (Container:91). While the dialog is open the modal blocks the form entirely; even if the dialog is Escape-dismissed mid-send, both layers still hold. Inner dialog guard: confirm button `disabled={sending}` (ConfirmDialog:43) + `handleConfirmSend` re-check (Container:99). Code-verified PASS; the unit suite pins only the inner guard → F5.

**Probe 3 — compose-key rotation.** Exactly ONE rotation site exists repo-wide: `composeKeyRef.current = randomUUID()` at Container:122, inside the `typeof deliveredCount === "number"` success branch. Failed sends (VALIDATION with/without `fields[]`, network, masked errors, `data.adminBroadcastNotification === undefined`) keep the key (Container:125-136) — retry-idempotency preserved; the header contract matches the gateway capture (`request.headers.get("x-idempotency-key")`, gqlContextFactory.ts:181) and the authLink merge is additive. A SUCCESS always rotates: the server returns a bare persisted `Int!`; count 0 is `typeof number` → rotates + renders the zero branch (correct — the receipt row was written). The key never rides the input DTO (broadcast.documents.ts:26-33). Test-pinned at test:334-360. PASS.

**Probe 4 — i18n completeness.** Every AdminBroadcasts key referenced by the components (27 slots enumerated across Header/Form/Fields/Companions/Dialog/Snackbar/Container) exists on BOTH en/ar leaves and is compile-pinned by `AdminBroadcastsLabels` + runtime-pinned by `adminBroadcasts-namespace.parity.test.ts` (mandated inventory, no-English-fallthrough sweep, registry wiring). Cross-namespace keys verified in both locales: `Common.close` (en/common/index.ts:17, ar:17), `Common.noResults` (en:19, ar:19), `AdminUsers.roleLabels.{admin,teacher,student,parent}` (en:47-52, ar:47-52). No referenced-but-undefined key. Arabic pluralization is NOT a naive count switch — it implements the proper CLDR zero/one/two/few/many branches (ar leaf:29-35): count=1 → singular "مستلم واحد"; count=2 → dual "مستلمين"; 3-10 → plural noun "مستلمين" (correct genitive after "إلى"); 11+ → counted-singular "مستلماً" (correct accusative). Boundary branches exact-pinned incl. the 5000 server cap (parity test:181-193). PASS.

**Probe 5 — companion coherence on kind switch.** `changeAudienceKind` (Container:81-84) replaces the whole draft, so the previous companion IS cleared — a stale `planId` can never ride with a role/country audience, and `buildAudienceInput` (helpers:125-132) second-guards by nulling cross-kind companions on the wire. The impossible state is NOT created. BUT the same reset also wipes `title`/`body` — the actual defect found this round → F1.

**Probe 6 — accessibility.** Dialog: MUI focus trap + Escape-to-close (no `disableEscapeKeyDown`) + `aria-labelledby` → PASS. Radio group: `aria-label` + `FormLabel` inside `FormControl` → PASS. Title/body errors: MUI TextField error→helperText `aria-describedby` association → PASS. Global formError Alert announces (MUI v9 Alert defaults `role='alert'`, node_modules Alert.js:167) → PASS. Snackbar content announces (SnackbarContent defaults `role='alert'`; root is `role='presentation'` precisely so the alert announces — useSnackbar.js getRootProps) → PASS. Gaps: the audience inline error is announced/associated NOWHERE (F3); the dialog exposes no in-flight announcement beyond the disabled+spinner confirm button (folded into F3's remediation note as optional).

## Findings

[MEDIUM] frontend/views/admin/broadcasts/BroadcastComposeContainer.tsx:81-84 — `changeAudienceKind` resets the ENTIRE draft via `setCompose({ ...initialComposeState, audienceType: kind })`: switching the audience-kind radio silently WIPES the authored `title` and `body` (and `initialComposeState` docs itself as a "fresh draft" — that semantic is only correct for the after-success reset at :119). The admin fills the copy fields FIRST (they render above the radio group in Fields), then picks an audience → everything typed is destroyed with no warning and no recovery. This is the one state-machine hole the probes surfaced. Fix: preserve `title`/`body`, reset only the companions (`role`, `country`, `planId`) and keep the `setFieldErrors({})` — e.g. `setCompose(current => ({ ...current, role: null, country: "", planId: null, audienceType: kind }))`. If the full wipe is deliberate, pin it with a test + doc comment (no test or comment encodes it today; the suite always fills copy either before any kind switch or after settling on the final kind).

[LOW] frontend/views/admin/broadcasts/BroadcastComposeContainer.tsx:115-124 + BroadcastComposeSuccessSnackbar.tsx:29-33 — consecutive successes reuse the SAME mounted `<Snackbar open autoHideDuration={6000}>`: MUI v9 restarts the hide timer only when `[open, autoHideDuration]` transition (node_modules/@mui/material/Snackbar/useSnackbar.js:43-49, deps `[open, autoHideDuration, setAutoHideTimer, timerAutoHide]`), so a second toast inherits the FIRST toast's remaining time — if send #2 lands late in the 6s window its toast can vanish almost immediately (the message content is fresh; the presentation is stale). Fix: remount per toast — key the Snackbar by a success epoch (e.g. a monotonically bumped counter or the rotated key) so each toast gets a full timer.

[LOW] frontend/views/admin/broadcasts/BroadcastComposeFields.tsx:55-80 — the audience inline error has NO programmatic association or announcement: MUI v9 `RadioGroup` consumes no `aria-describedby` from `FormControl` context (node_modules/@mui/material/RadioGroup/RadioGroup.js contains zero aria-describedby wiring), and the bare `FormHelperText` renders no role/live region — so a screen-reader user gets neither the error text linked to the radiogroup nor any aria-live notification when `fieldErrors.audience` appears (contrast: the title TextField error IS associated via MUI's TextField helperText wiring, and the global formError Alert announces via `role='alert'`). WCAG 3.3.1 association gap on the one field whose server projection (`BROADCAST_AUDIENCE_INVALID`) has no per-field map row today. Fix: stable `id` on the FormHelperText + `aria-describedby` on the RadioGroup (conditionally), or `aria-live="polite"` on the error region.

[LOW] frontend/views/admin/broadcasts/BroadcastComposeCompanions.tsx:81-119 (with BroadcastComposeContainer.tsx:151-152) — the plans query FAILURE path renders as the empty-catalog path: the container forwards only `plansLoading` + `plans` (`plansQuery.data?.adminPlans ?? []`), never `plansQuery.error`, so a transient network failure collapses to a disabled `MenuItem` with `tc.noResults` and a dead-end select — the admin cannot distinguish "no active plans" from "load failed" and has no retry affordance (correctly unable to send via `!audienceReady`, but unexplained). Suggest surfacing a localized failure/retry row when `plansQuery.error` is set (new namespace slot would need the parity belt updated in the same change).

[LOW] test/ui/components/admin/BroadcastComposeContainer.test.tsx:362-382 — the double-click protection test pins ONLY the dialog-confirm guard; the outer submit button's send-window guard (Form:66 `disabled={sending}` + Container:91 handler re-check) is implemented and code-verified but pinned by no unit test (the file's own NOTE :33-40 documents the flow-tier stall; the e2e suite `test/ui/e2e/admin-broadcasts.e2e.test.ts` covers the loop over real Chromium). Test-contract alignment gap, not a code defect: a regression that drops `props.sending` from the outer `disabled` would survive the unit tier.

[LOW] frontend/views/admin/broadcasts/broadcast-compose-skin.ts:12 — the Wave-1 fix left a stale word in the neighboring contract comment: `ACTION_BUTTON_SX` still documents "Confirm/cancel/dismiss affordances", but since the fix the dismiss affordance uses the dedicated `SNACKBAR_DISMISS_SX` (:24-25) and `ACTION_BUTTON_SX` consumers are exactly submit/confirm/cancel (Form:68, ConfirmDialog:37,45). Doc-only drift in the same skin block the Wave-1 fix touched; drop "dismiss" from :12.
