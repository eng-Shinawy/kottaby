## Findings

**[MEDIUM][SUBSTRATE-root] app/api/graphql/apollo-server.ts:60 (conspiring: app/api/graphql/rate-limit.ts:31-35 + backend/lib/ratelimit.ts:83-92) — batched/aliased `adminBroadcastNotification` amplification is UNBOUNDED: one authenticated-admin POST can drive N full broadcast pipelines, each committing in its own transaction, with zero limiter enforcement.**
`allowBatchedHttpRequests: true` (apollo-server.ts:60, browser BatchHttpLink dependency) admits a JSON-array body of any length; nothing in the gateway caps operation count, alias count, or document complexity (repo-wide grep: zero `ValidationRule`/depth/complexity/alias guards). The only bound is the 2 MB body cap (`transport-guard.ts:49`) — at ~80 bytes per minimal alias, that is on the order of tens of thousands of aliased `adminBroadcastNotification` operations in ONE request. Each alias executes the FULL pipeline (scope gate → `assertActorAdmin` user read → plan-exists → governed cohort resolve → ≤`BROADCAST_MAX_RECIPIENTS`=5000-row insert → 1 audit row → post-commit fan-out publish) and each opens its OWN `withTransaction` (admin-broadcast.service.ts:370-403) — so writes DURABLY COMMIT PER ALIAS even if the request is aborted or times out mid-batch. Mutation-specific math R1d never computed: N aliases × ≤5000 recipients ⇒ up to 500 000+ notification rows + N audit rows + N fan-out envelopes per request, repeatable indefinitely because `checkRateLimit` returns `success: true` UNCONDITIONALLY (ratelimit.ts:83-92 stub) — the 100 req/60 min `graphqlRateLimiter` config is decorative. Absent `REDIS_URL` the default claim cache resolves `undefined` (documented fail-open), so same-key dedup also does not apply across aliases.
SUBSTRATE attribution (honest scoping): the root gap is pre-existing and already ledgered — DEV3-003 deferred **BLT-05** ("allowBatchedHttpRequests:true + no op/alias cap + inert limiter ⇒ one HTTP request carrying an array/aliased batch executes N engine pipelines — live probe: array ×25 + aliases ×40 fully executed"), `docs/graphql/api-gateway-and-routing.md:165` ("No batch/complexity cap … Production hardening"), and this plan's own **REQ-035** (specs.md:78) accepted the fail-open limiter unchanged. R1d did not probe it. NEW in R3: (a) the mutation-specific amplification math (BLT-05's probe predated this surface and did not weigh the 5000-cap × N interaction or per-alias commit durability); (b) a hijacked/leaked admin token turns REQ-035's "admin-only, low-frequency" rationale false — the surface becomes a one-request storage-exhaustion + fan-out storm primitive. Severity MEDIUM not HIGH because every alias still requires a valid signed admin token (anonymous/non-admin get a uniform pre-resolver 401/403 per alias — the batch does not lower the BFLA wall). Suggested disposition: fold into the BLT-05/real-limiter hardening ticket an explicit per-REQUEST operation-count cap (or per-window admin-mutation quota) and record the amplification math in the canonical doc; do NOT hot-fix the gateway inside this ticket.

**[LOW][SUBSTRATE] backend/lib/ratelimit.ts:58-70 — limiter identity is client-forgeable (`x-forwarded-for` trusted blindly), and its 429 log line is a latent log-forging sink.**
`getClientIdentifier` returns the first raw `x-forwarded-for` entry verbatim (only `.trim()`ed), falling back to `x-real-ip`, with no trusted-proxy validation — a client fully controls its rate-limit identity. Two consequences: (1) forward-facing: when the real Redis limiter lands, per-IP buckets rotate per request via header spoofing, defeating the quota the gateway currently advertises (`rate-limit.ts:56-59` X-RateLimit-* headers, `graphqlRateLimiter` 100/60 s); (2) latent log injection: `rate-limit.ts:38` interpolates the identifier into `logger.warn(\`Rate limit exceeded for ${identifier}\`)`, and the logger is a line-based `process.stderr.write(\`[WARN] ${message}\n\`)` with NO control-character escaping (logger.ts:69-71) — interior `\n` in the header value forges log lines. Currently UNREACHABLE (the stub never denies, so the 429 branch is dead code), which is why LOW not MEDIUM; the identity-trust flaw becomes load-bearing the day the real limiter lands. R3-new: REQ-035 covers the fail-open posture but neither facet (identity trust, log-forging) is documented anywhere. Suggested disposition: add to the future rate-limiting hardening stream — trusted-proxy derivation (or connection-peer identity) + control-char sanitization of the identifier at the logger boundary.

**[INFO] backend/lib/gateway/transport-guard.ts:105-113 — the 2 MB body cap is measured in UTF-16 code units (`String.length`), not bytes; effective ceiling is ~2× the intended byte budget.**
`assertWithinBodyLimit(rawBody.length)` after `request.text()` counts UTF-16 code units; a surrogate-pair-padded body (4 UTF-8 bytes per 2 code units) passes the 2 000 000-unit checkpoint at up to ~4 000 000 actual bytes. Pre-existing DEV3-003 transport-tier substrate (the comment at :105 self-documents "UTF-16 units" semantics). Impact negligible — the cap remains bounded and Apollo parses the body normally; recorded because R3's charter is the gateway the mutation rides and this is the only transport-tier bound it inherits.

## Probes (R3 new angles) — results

**Probe 1 — Depth/complexity/batching abuse:** FINDING (above, MEDIUM SUBSTRATE-root). Bounds that DO exist: transport method/CT/2 MB cap; per-op recipient cap 5000; per-op single audit row. Bounds that DO NOT: operation/alias count per document, batch length, document depth/complexity, per-request DB-work ceiling, per-IP/user request budget (stub). Per-alias commit durability (own `withTransaction`) means partial durable progress from one request.

**Probe 2 — SDL/introspection surface:** CLEAN. `introspection: !isProduction` (route.ts:49, code-explicit constant) — production anonymous clients cannot introspect the mutation or `AdminBroadcastNotificationInput` (`hideSchemaDetailsFromClientErrors: isProduction` also suppresses schema detail in validation errors, apollo-server.ts:49). Non-production introspection is anonymous-visible — intentional dev posture. Cross-check as instructed: `backend/lib/gateway/public-operations.ts:36-46` is UNTOUCHED (frozen six: login, refreshToken, logout, registerUser, recitationReadings, _health) and `adminBroadcastNotification` is NOT allowlisted; the field carries `authScopes: { $all: { authenticated: true, role: [UserRole.Admin] } }` (admin-broadcast.mutation.ts:67-72), so it lands on the SCOPED side of the REQ-072 1:1 schema↔allowlist coverage test. Note (no finding): `isPublicOperation` has no runtime consumer in the request path — the allowlist is test-time governance (REQ-072 gate), the runtime BFLA control is the authScopes gate itself (present, `$all`-pinned).

**Probe 3 — Error-oracle (FORBIDDEN vs UNAUTHORIZED vs VALIDATION):** CLEAN. Denial ordering is gate-first: `assertActorAdmin` runs BEFORE title/coherence validation, plan existence, and cohort resolution (admin-broadcast.service.ts:336-360). An authenticated non-admin therefore receives FORBIDDEN for EVERY input — valid, invalid, empty-cohort, or existing planId alike (`BROADCAST_TITLE_INVALID`/`BROADCAST_AUDIENCE_INVALID` are unreachable below the admin boundary) — so no cohort-membership or plan-existence oracle exists for non-admins. `PLAN_NOT_FOUND` is scope-confined to the admin-gated plan path post-gate (service:260-271) — admins legitimately manage plans, and the empty-cohort/count disclosures are the mutation's designed return value for gate-passers. Response shapes are uniform (HTTP 200 + `errors[].extensions.code`; DomainError pass-through per the finalizer contract); timing deltas (UNAUTHORIZED = 0 DB reads at the scope step vs FORBIDDEN = 1 user read) are pre-cohort and negligible.

**Probe 4 — Transport guard inheritance:** CLEAN. The mutation rides the SAME seven-step pipeline: `guardTransport` runs FIRST for every POST (route.ts:171-174) — method POST-only (transport-guard.ts:37-38, 67-72; explicit 405 `Allow: POST` handlers at route.ts:227-246 for GET/PUT/DELETE/PATCH), JSON content-type allowlist (:84-93), declared + drained 2 MB checkpoints (:108-113, 145-164). The mutation document therefore can NEVER ride GET in any environment (hard invariant holds), and transport rejections consume zero limiter/context/engine resources.

**Probe 5 — The admin gate's second wall under a forged claim:** CLEAN on the R3 angle; R1d MEDIUM unchanged (substrate). (a) **No input field influences the gate**: `assertActorAdmin(actorId, locale, outerTx)` consumes ONLY the verified actor id (admin-gate.helpers.ts:59-90); `broadcast(input, actorId, …)` runs the gate as step 1 before any input is even type-checked (service:336-338), and the resolver sources the actor exclusively from `ctx.user.id` (mutation:99). The idempotency key (the only other client-controllable value) is propagation-only and never touches the gate. (b) **Forged token** (`role=admin, userId=<teacher>`): fails HS256 signature verification — `jose.jwtVerify` with a `Uint8Array` HMAC secret is key-pinned (claims are HMAC-covered; `alg:none`/RS-HS confusion unreachable; jwt.ts:143-165) → `verifyAccessToken` returns null → anonymous → pre-resolver UNAUTHORIZED. (c) **Claim/row divergence** (legitimately signed token minted before a demotion): the outer wall trusts the ≤15-min claim (`role = toUserRole(payload.role)`, gqlContextFactory.ts:221) and passes, but the inner wall re-reads the DB row and rejects on role (helpers:71-89) → FORBIDDEN; self-heals at refresh. (d) **Governed admin** (soft-deleted/blocked, role still `admin`): BOTH walls pass — the R1d MEDIUM persists byte-identically (`admin-gate.helpers.ts:59-90` still consults ONLY `role`; `gqlContextFactory.ts:200-224` still fetches governance flags it then ignores). REPORT-ONLY [SUBSTRATE]: unchanged since R1d, owned by the DEV3-016 gate owner; sibling rulings (DEV3-018 REQ-031, DEV3-022c REQ-032, DEV1-014 REQ-031) close the window per-surface for THEIR high-blast mutations — this surface's disposition remains the ledgered deferral.

**Probe 6 — Rate limiting / admin brute-force via this surface:** CLEAN on the brute-force question; the limiter-scope half is the MEDIUM finding above. The mutation is nominally inside `withRateLimit` (route.ts:188) but the limiter is a no-op stub (ratelimit.ts:83-92) — REQ-035-documented accepted posture. Brute-forcing admin role via this surface is NOT viable: anonymous callers get uniform UNAUTHORIZED with zero credential material in play; the 401-vs-403 distinction is derivable only by presenting an already-valid signed token (at which point the role that gates it is known by construction) — no oracle amplifies credential guessing. Login itself (the credential surface) is outside this review's scope; its limiter is the same fail-open stub.
