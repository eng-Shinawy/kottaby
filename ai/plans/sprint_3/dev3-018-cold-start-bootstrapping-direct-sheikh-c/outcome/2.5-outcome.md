## Deviations

1. **VALIDATION denial carries no domain log.** The assignment's "one bounded logDomainError per denial" sits in
   tension with the DEV3-016 precedent (`getUserDetail`/`updateUser` throw `ValidationError` with NO log —
   `user-management.service.ts:236, 347`). The sibling-parity behavior was kept: VALIDATION (client-shape
   rejection) is not a domain denial; all seven OTHER denial paths log exactly once (proven by the
   delta-counted log spy tests).
2. **Gate receives `outerTx`.** Plan §4.4 text shows `assertActorAdminActive(actorId, locale)` but the drift
   register / 2.4 outcome confirm the third param exists; passing it is required so the gate reads participate
   in the test transaction (and matches every `assertActorAdmin(actorId, locale, outerTx)` call site in
   `user-management.service.ts`). No behavior change in production (resolver passes no `outerTx`).
3. **D7 runtime-omission is not fuzzable under strict TS.** The input type declares `makeEvaluator: boolean`
   (non-optional), so a test cannot pass an omitted field without a banned cast. The `?? true` coalesce
   survives as defense-in-depth; explicit `true`/`false` are both covered; the GraphQL default (`= true`)
   belongs to task 3.x.
4. **Note on plan-vs-service file length**: plan §4.4's pipeline step ordering is implemented verbatim; the
   "rethrow the masked-lane error" step on the zero-row/non-approved re-read is implemented as a plain internal
   `Error` (masked to `INTERNAL_SERVER_ERROR` by the single finalizer), matching REQ-050's closed set (no new
   subclass) and the `assembleDetail` corrupt-role precedent.
