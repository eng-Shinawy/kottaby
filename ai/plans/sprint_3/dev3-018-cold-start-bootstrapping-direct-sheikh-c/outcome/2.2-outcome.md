## Deviations

1. **`findById` executor signature widened `tx?: DBTransaction` → `tx?: DBQueryExecutor`** — the
   narrowed type would make the `queryDb(...)` bare-read branch unreachable by design and breaks
   parity with both sibling precedents (`UserRepository.findById`,
   `ApplicantRepository.findByUserId`). M3 says "signature `(id, tx?)` and semantics are unchanged";
   the wider executor type is the shape that actually ships in-tree for this exact pattern.
2. **Non-tx `findById` branch is not exercised by the test suite** — covering it requires calling
   without `tx`, which escapes the rollback transaction and violates the "`tx` to EVERY call /
   every test inside `runInRollback`" mandate. Documented here rather than risking state pollution;
   the branch is byte-shaped like the already-covered sibling read paths.
3. **T3 double-insert asserts race outcome + post-race single row** instead of preserving the
   racy winner — winner-preservation is structurally impossible with per-arm savepoints (both
   savepoints queue before both inserts), so the test uses the in-tree registration-race precedent's
   one-savepoint rescue plus a deterministic settlement insert. The intended invariants (exactly one
   admitted arm, exactly one 23505, exactly one final row) are all asserted.
4. **Test placement is co-located** (`backend/db/repo/teachers/`), per the task text; the
   `backend/db/test/AGENTS.md` 100%-coverage rule targets `backend/db/test/repo/`. Note that the
   parallel `test:db` runner scans only `backend/db/test` — the co-located sibling precedent
   (`backend/db/repo/students/__tests__/student-grant-free-trial-once.test.ts`) has the same
   property; the sanctioned `run-test.ts` runner handles both.
