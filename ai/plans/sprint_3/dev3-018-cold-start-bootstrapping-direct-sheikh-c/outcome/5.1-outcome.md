- Chaos probes (a)/(a')/(d) use the GLOBAL `db` (each service call opens its own top-level transaction

  `createdUserIds`; `afterAll` hard-deletes via `deleteUsersByIds` with the
  `deleted === ids.length` + `countUsersByIds === 0` post-checks. Certification audit rows carry the
  admin actor's id, so the helper's `actor_id IN (…)` pre-clean covers them (admin id is in the delete
  set) — no `entity_type = 'teacher'` clause was needed anywhere.
- Fuzz probes (c) use `runInRollback` + `expectRepoError` (zero `rejects.toThrow` anywhere in the file).
- PGlite skip convention mirrors the sibling chaos suite VERBATIM
  (`IS_PGLITE = (process.env.DB_PROVIDER ?? "").toLowerCase() === "pglite"`, `concurrencyTest` alias),
  scoped to the concurrency describe only.
- Races are resolved by DATABASE CONSTRAINTS (`teacher` PK unique violation 23505 on the insert path,
  guarded-UPDATE row lock on the elevation path) — ZERO sleeps/timers in the file.

## Deviations

1. **(c) pre-DB proof shape.** The task text offered "zero-statement/transaction-count probe OR spy on
   `UserRepository.findById` never called". Implemented as the findById spy variant, strengthened: not
   merely "never called" (the gate legitimately reads the actor) but "never called WITH the fuzzed id"
   — every recorded call arg is asserted to equal the admin actor id.
2. **(b) harness choice.** The assignment's discipline line reserves committed-fixture style for "true
   cross-transaction concurrency"; a savepoint-scoped forced-failure proof already exists in the 2.5
   service suite. The chaos file's variant uses committed fixtures anyway (single-threaded, provider-
   portable) because its distinguishing value is proving rollback of a REAL top-level transaction
   rather than a `SAVEPOINT` — the same reason the sibling chaos file's forced-failure probe (e) runs
   committed. No flakiness implication (no concurrency inside this probe).
3. **Storm provisioning parallelization.** The 25 targets are provisioned via `Promise.all` of
   independent committed transactions (SAME rationale as the storm itself; avoids the flagged
   `await`-in-loop pattern without sharing a connection). Provisioning order is irrelevant — assertions
   bind results to targets by id.
