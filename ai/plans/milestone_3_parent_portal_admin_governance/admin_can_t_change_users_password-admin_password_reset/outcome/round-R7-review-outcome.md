Concurrency model verified against PostgreSQL semantics: production path = separate top-level `db.transaction` per request (READ COMMITTED); single-row `UPDATE`s serialize on the row lock and the WHERE qual is **re-evaluated on the latest committed row version** after a lock wait (EvalPlanQual) — this is what makes the R2 fence sound, not just best-effort.

A concurrent `adminSetUserDeleted` (via `setDeletedOnce`, which sets only `isDeleted/deletedAt/updatedAt` — never `password_hash`) committing inside that window leaves the fenced write's WHERE (`id = ? AND password_hash = ?`) fully satisfied, so the UPDATE re-evaluates after the lock wait, matches, and rewrites the dead row's hash + clears its flag; `changeMyPassword` returns a success payload for a principal with "no live credential to replace" — the exact ground both the admin path's post-write check and the steady-state self denial cite.
