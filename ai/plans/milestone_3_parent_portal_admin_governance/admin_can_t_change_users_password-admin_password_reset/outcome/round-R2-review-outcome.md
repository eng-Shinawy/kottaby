## Findings

| # | Severity | Location | Finding | Suggested fix |
|---|---|---|---|---|
| 1 | LOW | `backend/services/auth/auth.service.ts:360-401` (`changeMyPassword`) | **Self path writes a credential for a soft-deleted / governed principal — no governance denial, unlike the sibling admin path.** `gqlContextFactory.ts:259-263` treats ANY existing row as authenticated (no `isDeleted`/`isBlocked`/suspension re-check), and `changeMyPassword`'s identity load (`:360`) performs no governance evaluation either. `UserRepository.updatePassword`'s WHERE clause is id-only, so an in-session caller soft-deleted by an admin rewrites the dead row's `password_hash`, clears `must_change_password`, and receives a success payload — while `AdminUserManagementService.setUserPassword` (`user-management.service.ts:485-497`) explicitly denies deleted targets in-tx with `USER_NOT_FOUND` + rollback on the stated ground that "a deleted user has no live credential to replace". The delta thus introduces two opposite semantics for the same predicate on the two paths that share the single write home. No privilege gain (login re-checks governance via `assertUserActive`; the gate denies everything else; token revocation is deferred D2) — semantic-hygiene inconsistency, hence LOW. | Fold `user.isDeleted` (ideally the whole `assertUserActive` predicate login/refreshToken already use) into the existing single `CURRENT_PASSWORD_INVALID` denial at `:361-369` — constant shape, zero writes, and no new oracle is possible (identity is always `ctx.user.id`, so only the row owner can ever observe it). |
| 2 | LOW | `backend/services/auth/auth.service.ts:360,393-397` (`changeMyPassword`) | **TOCTOU: current-password proof races a concurrent admin rotation, and the self write silently wins.** The identity read (`:360`, bare read — no tx) and the write tx (`:395-397`) are separated by two bcrypt operations (`comparePassword` ~100 ms + `hashPassword` ~100 ms). An `adminSetUserPassword(id, { mustChangePassword: true })` committing inside that window is clobbered by the self path's unconditional `updatePassword(userId, hash, false)`: the freshly issued temporary hash is overwritten AND the fence flag cleared — the admin's forced reset evaporates while the user retains a credential they already knew. Plan §5.1 accepts last-write-wins for concurrent *admin* writes only (row lock + per-actor audit rows); the self-vs-admin direction is unspecified. Reverse order is safe (admin write lands last → flag stays true). ~200–500 ms window, no escalation — LOW. | Make the write conditional on the observed credential: `UPDATE … SET … WHERE id = ? AND password_hash = $observedHash` (a `selectHashById` projection or the pre-write row's hash) and treat zero matched rows as a retry of the single `CURRENT_PASSWORD_INVALID` denial; or re-read + re-`comparePassword` inside the tx before the UPDATE. |

Non-findings verified clean (highlights): both `findByEmail`/`findById` raw-SQL lists and `SAFE_USER_SELECT`/`AdminUserDetailRow`/`assembleDetail` carry `must_change_password` end-to-end (the `?? false` Pothos fallback cannot mask a projection gap); `updatePassword` is a required-tx, hash-in/hash-out single `UPDATE … RETURNING *` with exactly 2 production callsites (admin + self) and no second credential-write site anywhere; `setUserPassword` sequence = strict `assertActorAdminActive` → `isPositiveSafeInteger` → `validatePasswordPolicy` (empty ⇒ `PASSWORD_REQUIRED`, `< MIN_PASSWORD_LENGTH=8` ⇒ `PASSWORD_TOO_SHORT`, localized `auth` copy, fields payload verbatim per §4.3) → hash-before-tx → in-tx write → null-or-deleted ⇒ `USER_NOT_FOUND` before the audit insert (rollback ⇒ zero writes/zero audit) → one in-tx audit row (`Update`, `changedFields: ["credentials"]` + flag only) → in-tx detail re-read; census row registered (`audit-completeness.catalog.ts:101`); `changeMyPassword` taxonomy matches §4.3 exactly (`ValidationError` 4-arg overload → `CURRENT_PASSWORD_INVALID` code + field payload; policy denials ride `VALIDATION` + `extensions.fields`; vanished-row ⇒ `UnauthorizedError`); the gate allowlist is a frozen closed set with a per-operation deny predicate, alias-safe (`selection.name.value`), fragment/inline-fragment/transitive-spread flattening with a cycle guard, conservative under `@skip`/`@include`, and `didResolveOperation` fires before any resolver (zero writes on denial);
