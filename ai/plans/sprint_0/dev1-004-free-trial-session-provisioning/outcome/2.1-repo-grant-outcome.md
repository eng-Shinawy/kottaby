## 2. Implementation Details

### 2.1 Exact code snippet appended (inside `export namespace StudentRepository { ... }`)

```ts
/**
 * Atomically grants free trial session credits to a student exactly once.
 *
 * Single conditional UPDATE guarded by the trial_granted_at marker — predicate
 * evaluation and column mutation occur in the same SQL statement, so the
 * grant-once invariant holds with zero TOCTOU window. Returns true when the
 * grant was applied, false when the marker was already set (re-grant rejected);
 * the caller (student trial service) is responsible for surfacing a localized
 * conflict error on the false branch.
 */
export async function grantFreeTrialOnce(
  studentId: number,
  trialCount: number,
  tx?: DBTransaction,
): Promise<boolean> {
  const queryDb = tx ?? db;
  const updated = await queryDb
    .update(students)
    .set({
      balanceTrial: sql`${students.balanceTrial} + ${trialCount}`,
      trialGrantedAt: new Date(),
    })
    .where(and(eq(students.id, studentId), isNull(students.trialGrantedAt)))
    .returning({ id: students.id });
  return updated.length > 0;
}
```

### 2.4 Design notes

- **Atomicity**: a single conditional `UPDATE … SET … WHERE id = $1 AND trial_granted_at IS NULL … RETURNING id` — predicate evaluation and column mutation share one SQL statement, so the grant-once invariant holds with **zero TOCTOU window**. No SELECT-then-UPDATE, no advisory lock, no `SELECT FOR UPDATE` (per REQ-042).
- **Grant-once detection**: `.returning({ id: students.id })` yields `[]` when zero rows matched the predicate (marker already set OR id absent) and `[{ id: <studentId> }]` when the grant applied. `updated.length > 0` is the boolean signal consumed by the caller.
- **`tx` is OPTIONAL-LAST** (per `backend/db/repo/AGENTS.md`) — the third positional parameter after `studentId` and `trialCount`. The `const queryDb = tx ?? db;` fallback lets the method run either inside a caller-supplied transaction (registration flow, SAVEPOINT-aware) or standalone against the global handle (future standalone callers).
- **Bound parameters only** inside the `sql\`\`` template — `${students.balanceTrial}` resolves to a column reference and `${trialCount}` resolves to a Drizzle-bound parameter placeholder (`$1`), NOT an inlined literal. **No inline `--` comments** inside the template (Drizzle template hygiene rule).
- **Repo purity**: the method throws NO domain errors and contains NO i18n / permission logic. It returns `Promise<boolean>`; the caller (student-trial service, Phase 2.2) is responsible for converting `false` into a localized `ConflictError` with `extensions.code = "CONFLICT"` (per `docs/graphql/domain-error-extensions-code.md`).
- **NOT a Prepared-Statements-2.0 candidate** — this is a write (UPDATE), and prepared statements are read-only per `docs/drizzle/prepared-statements.md`. The method also contains no `inArray`, so the `inArray + Prepared Statements PROHIBITED` rule does not apply.
- **BOPLA / mass-assignment defense**: the `set` clause touches EXACTLY two columns (`balanceTrial`, `trialGrantedAt`) — no `{ ...input }` spread. The `trialCount` parameter is the value from `FREE_TRIAL_SESSION_COUNT` passed by the caller; the repo does NOT import the constant (keeps it reusable and policy-free).
- **BOPLA / identity derivation**: `studentId` is the only identity input. The repo does not validate its provenance — that is the caller's responsibility (Phase 2.3 wires it to the freshly inserted `users.id` server-side, never client input).

### 3.4 SAVEPOINT pattern for Tier 4

After a CHECK-constraint rejection, PostgreSQL places the transaction in the "aborted" state (SQLSTATE `25P02`) — every subsequent query on the same tx fails. To allow the post-rejection read-back assertion (`balanceTrial` still `0`), the test brackets the adversarial UPDATE in an explicit SAVEPOINT:

```ts
await tx.execute(sql`savepoint dev1_004_check_violation`);
const error = await expectRepoError(() =>
  tx.update(students).set({ balanceTrial: -1 }).where(eq(students.id, student.id)).returning(),
);
await tx.execute(sql`rollback to savepoint dev1_004_check_violation`);
// outer tx is now queryable again — read-back works
```

This mirrors the SAVEPOINT precedent in `backend/db/test/logic/auth/registration.service.test.ts` (the `dev2004_race` savepoint).

## 8. Carry-Forward Knowledge for Phase 2.2 (Service)

### 8.1 Contract: `grantFreeTrialOnce` returns `Promise<boolean>`

- `true` — the grant was applied (predicate `id = $1 AND trial_granted_at IS NULL` matched exactly one row; `balance_trial` was incremented by `trialCount` and `trial_granted_at` was stamped to `now()`).
- `false` — the grant was rejected (the marker was already set on a second call, OR the `studentId` does not correspond to any row). **The repo does NOT distinguish "re-grant on existing row" from "grant on missing row"** — both return `false`. The service MUST decide whether to surface a `ConflictError` (re-grant) or a `NotFoundError` (missing row) based on context.

### 8.2 Service (Phase 2.2) MUST:

1. **Convert `false` into a `ConflictError`** with `extensions.code = "CONFLICT"` and the localized `trialAlreadyGranted` message (via `getServerTranslations(locale).errorsTranslations.trialAlreadyGranted` — note the FLAT field name and the `errorsTranslations` namespace; per Phase 1.4 outcome carry-forward, NOT the nested `studentTrial.trialAlreadyGranted` shape shown in plan.md).
2. **Pass `tx` and `FREE_TRIAL_SESSION_COUNT`** to `grantFreeTrialOnce(studentId, FREE_TRIAL_SESSION_COUNT, tx)`. The repo does NOT import the constant; the service owns it.
3. **Call `logger.logDomainError`** from `@/backend/lib/logger` BEFORE throwing the `ConflictError` (REQ-052). Structured context: `{ code: "TRIAL_ALREADY_GRANTED", entity: "students", entityId: studentId, attempt: "1" }` (or the appropriate attempt count if tracked). NEVER `console.*`.
4. **No `try/catch` swallowing on the happy path** (REQ-053) — the grant is a first-class step of registration, not a side effect wrapped in ignored `try/catch`.
5. **No permission gates in the service** — provisioning is system-internal; authorization is enforced at the caller boundary (`registerUser` is public; no other GraphQL op may invoke the service).

- "100% statement + branch coverage" (per REQ-070) is operationally interpreted as "100% lines + 100% functions on the new method" when using Bun.
- Branch coverage on `tx ?? db` requires either: (a) a non-`runInRollback` test that exercises the `db` fallback arm (forbidden by `backend/db/test/AGENTS.md` rule 16 inside rollback, but possible in a separate non-rollback test that cleans up after itself — out of scope for this task), or (b) a different coverage tool (`c8` / `istanbul`) — not configured in this repo.
- The `db` fallback arm is exercised by future standalone callers (DEV2-009 conversion, DEV3-019 direct onboarding) — covered at integration-test time, not repo-unit-test time.
