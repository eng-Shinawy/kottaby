## 2. Implementation Details

### 2.1 The find-then-grant-if-null pattern (seed-students.ts)

The seed factory is a sequential reduce over `INITIAL_DEMO_USERS.filter(spec => spec.role === "student")`. For each demo student:

1. **Find** — call `StudentTrialService.findTrialGrantStateByEmail(spec.email)` (the production entry point) to resolve the existing student row by login email. Returns `null` when the user is missing or is not a student (defensive — never throws).
2. **Grant-if-null** — when `state.trialGrantedAt === null`, invoke `StudentTrialService.grantFreeTrial(state.studentId, "en")` (the canonical grant entry point — never a raw `balanceTrial` column write). The grant's atomic guarded UPDATE guarantees one-time application; the prior `null` check keeps this branch from firing on idempotent re-runs.
3. **If-not-null skip** — when `state.trialGrantedAt !== null`, log `"Demo student already has trial grant, skipping"` at INFO level and skip. The seed run stays idempotent across multiple invocations.

```ts
const state = await StudentTrialService.findTrialGrantStateByEmail(spec.email);
if (!state) {
  logger.info(`Demo student row not found, skipping trial reconcile: ${spec.email}`);
  return;
}

if (state.trialGrantedAt === null) {
  // Grant-if-null: the marker is unset, so invoke the canonical grant entry
  // point. The grant's atomic guarded UPDATE guarantees one-time application.
  await StudentTrialService.grantFreeTrial(state.studentId, locale);
  logger.info(`Granted free trial to demo student: ${spec.email}`);
} else {
  // If-not-null skip: the grant was already applied. Skip silently so the
  // seed run stays idempotent across multiple invocations.
  logger.info(`Demo student already has trial grant, skipping: ${spec.email}`);
}
```

The locale `"en"` is used because the grant's only localized surface is the `ConflictError` thrown on a re-grant attempt — which the find-then-grant-if-null pattern structurally prevents from ever surfacing during a seed run.

### 2.2 The new `findTrialGrantStateByEmail` service method (student-trial.service.ts)

The method resolves a user by login email, then reads the student row's `trialGrantedAt` marker. It returns `null` for the absent-user and non-student-user branches (no throw — the method is total over those branches).

```ts
export async function findTrialGrantStateByEmail(
  email: string,
  tx?: DBTransaction
): Promise<{ studentId: number; trialGrantedAt: Date | null } | null> {
  const user = await UserRepository.findByEmail(email, tx);
  if (!user) {
    return null;
  }
  const student = await StudentRepository.findById(user.id, tx);
  if (!student) {
    return null;
  }
  return { studentId: student.id, trialGrantedAt: student.trialGrantedAt };
}
```

### 2.5 FIX to the prior implementation — transactional correctness of `findTrialGrantStateByEmail`

**Bug discovered during verification (this subagent)**: the prior subagent's implementation called `UserRepository.findByEmail(email)` WITHOUT propagating `tx`. This broke transactional isolation: in tests inside `runInRollback`, the user row created via `createTestUser(tx)` is NOT visible to `findByEmail`'s non-tx branch (which uses the Neon HTTP fast path / global Drizzle handle — a separate connection), so the test would observe `null` instead of the freshly-inserted user.

Per `backend/db/test/AGENTS.md` Rule 16: *"Failing to pass `tx` causes the repo method to use the global `db` connection, which is outside the rollback transaction — leading to state pollution, deadlocks, and non-deterministic test results."*

**Fix applied (1-line, 2-character delta)**: propagate `tx` to `UserRepository.findByEmail(email, tx)`. The fix:
- Preserves the production seed path: when `tx` is `undefined`, both `findByEmail` and `findById` fall back to the global Drizzle handle — same behavior as before.
- Unblocks transactional test reads: when `tx` is supplied (tests via `runInRollback`), both lookups run inside the caller's transaction scope — the freshly-inserted user + student rows are visible.
- Is consistent with the service's documented contract ("accepts an optional transaction so the read can run inside a caller's transaction scope").

The fix passed `sub-loop.ts --lifecycle duplicates` (exit 0) on the service file. No semantic regression: the only caller in production (`seed-students.ts`) calls the method without `tx`, so the seed path is byte-identical in behavior.
