## 3. Verification — 10-item checklist

### 3.1 [x] Single guarded UPDATE (no read-modify-write) — REQ-012 / REQ-042

`backend/db/repo/students/student.repository.ts:84-99`:

```ts
export async function grantFreeTrialOnce(
  studentId: number,
  trialCount: number,
  tx?: DBTransaction
): Promise<boolean> {
  const queryDb = tx ?? db;
  const updated = await queryDb
    .update(students)
    .set({
      balanceTrial: sql`${students.balanceTrial} + ${trialCount}`,
      trialGrantedAt: new Date(),
    })
    .where(and(eq(students.id, studentId), isNull(students.trialGrantedAt)))
    .returning({ id: students.id });
  return updated.length > 0;
}
```

**Analysis:**
- Exactly ONE SQL statement (single `.update().set().where().returning()` chain).
- The WHERE clause combines `eq(students.id, studentId)` AND `isNull(students.trialGrantedAt)` — predicate evaluation and column mutation occur atomically in the same UPDATE.
- No `SELECT FOR UPDATE` + conditional write. No advisory lock. No read-then-write.
- `.returning({ id })` captures whether the UPDATE matched a row — `updated.length > 0` is the grant-applied boolean.
- The set expression `balanceTrial: sql\`${students.balanceTrial} + ${trialCount}\`` reads the existing value INSIDE the UPDATE (not before), so the operation is atomic per row.

**Verdict: REQ-012 + REQ-042 satisfied.** Zero TOCTOU window — concurrent `grantFreeTrialOnce` calls on the same row serialize at the row lock; exactly one UPDATE matches the `isNull(trialGrantedAt)` predicate (the first commits, sets the marker; the second sees the marker set, matches zero rows, returns false).

#### 3.2.1 Seed bootstrap — acceptable `tx` omission

The seed runs OUTSIDE any caller transaction (it is invoked by `bun run db seed` from the CLI, not from a service-layer caller). The service methods' signatures are `grantFreeTrial(studentId, locale, tx?)` and `findTrialGrantStateByEmail(email, tx?)` — `tx` is OPTIONAL, and both fall back to the global Drizzle handle via `const queryDb = tx ?? db` (repo) and pass-through to repo (service).

**Rationale for acceptability:**
1. The seed step is reconciling already-committed demo student rows (the user seeder committed them in a prior step). It does NOT need atomicity with those rows.
2. The grant's atomic guarded UPDATE (`WHERE trial_granted_at IS NULL`) provides the one-time invariant at the SQL level, independent of any surrounding transaction. Re-invoking the seed on an already-granted student returns false from `grantFreeTrialOnce`, but the seed's prior `findTrialGrantStateByEmail` check already short-circuits before invoking the grant — so the seed never reaches the conflict path.
3. The Phase 2.4 test suite (`student-trial.service.test.ts`) covers the transactional-read path explicitly via `runInRollback` + `tx` propagation — the seed's non-tx path is exercised separately by the live `bun db seed` runs documented in Phase 2.4 §4 and Phase 5.1 §5.

**Verdict: REQ-041 satisfied.** Production paths (registration) propagate `tx` at every call site. The seed bootstrap path is documented as the explicitly-acceptable exception.
