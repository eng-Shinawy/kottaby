## 2. Implementation Details

### 2.1 Exact code snippet added

Inside `backend/db/schema/students/students.ts`, immediately after the existing `balanceTajweed` column declaration:

```ts
balanceTrial: integer("balance_trial").notNull().default(0),
trialGrantedAt: timestamp("trial_granted_at"),
```

In the same file's table `check(...)` array, immediately after the existing `students_balance_tajweed_check`:

```ts
check("students_balance_trial_check", sql`${t.balanceTrial} >= 0`),
```

### 2.2 Design notes

- **Placement rationale**: the new `balanceTrial` lane is grouped with the existing balance lanes (`balanceHifz`, `balanceReviews`, `balanceTajweed`) to keep the balance family contiguous; the `trialGrantedAt` marker sits adjacent because it is the trial-grant marker paired with the trial lane. The CHECK constraint mirrors the existing `students_balance_*_check` pattern exactly.
- **Strictness**: per REQ-010, `balanceTrial` is declared `.notNull().default(0)` — stricter than the existing nullable balance lanes (which only have `.default(0)`). This produces a stricter inferred TypeScript type on `StudentSelectType.balanceTrial` (carried forward to Phase 2.1).
- **Marker column**: `trialGrantedAt` is declared nullable with NO default, matching the plan (timestamp set server-side only when the grant is first issued).
- **No inline `--` comments** were placed inside any `sql\`\`` template, per the rule (Drizzle template hygiene, also a precondition for Phase 2.1's `grantFreeTrialOnce` write expression).
- **Imports**: zero import changes — `integer`, `timestamp`, `check`, and `sql` were all already imported at the top of the existing file. No new exports, no new top-level constants.

### 2.3 Final file shape (post-edit, lines 18-47)

```ts
export const students = pgTable(
  "students",
  {
    id: integer("id")
      .primaryKey()
      .references(() => users.id, { onDelete: "cascade" }),
    balanceHifz: integer("balance_hifz").default(0),
    balanceReviews: integer("balance_reviews").default(0),
    balanceTajweed: integer("balance_tajweed").default(0),
    balanceTrial: integer("balance_trial").notNull().default(0),
    trialGrantedAt: timestamp("trial_granted_at"),
    primaryLanguage: varchar("primary_language", { length: 100 }),
    anotherLanguage: varchar("another_language", { length: 100 }),
    handshakeCode: varchar("handshake_code", { length: 50 }).notNull(),
    parentId: integer("parent_id").references(() => users.id, { onDelete: "set null" }),
    createdAt: timestamp("created_at").defaultNow().notNull(),
    updatedAt: timestamp("updated_at")
      .defaultNow()
      .notNull()
      .$onUpdate(() => new Date()),
  },
  t => [
    unique("students_handshake_code_unique").on(t.handshakeCode),
    index("students_parent_id_idx").on(t.parentId),
    check("students_balance_hifz_check", sql`${t.balanceHifz} >= 0`),
    check("students_balance_reviews_check", sql`${t.balanceReviews} >= 0`),
    check("students_balance_tajweed_check", sql`${t.balanceTajweed} >= 0`),
    check("students_balance_trial_check", sql`${t.balanceTrial} >= 0`),
  ]
);
```

The existing file-level docstring already covers the new column implicitly ("Balance CHECK constraints (balance_* >= 0) are an additional safeguard..."). No docstring edits were required.

**Phase 2.1 implications**: the `grantFreeTrialOnce` repo method writes both columns in a single guarded UPDATE. The service layer (`StudentTrialService.grantFreeTrial`) MUST NOT expose these fields in any input type (BOPLA / REQ-031) — the registration hook in Phase 3 derives the `studentId` from the just-inserted `users.id`.

### 6.2 CHECK constraint

- **Constraint name**: `students_balance_trial_check` (exact match per REQ-035 / plan §2)
- **Live-DB query (for Phase 1.2 verification)**: `SELECT conname FROM pg_constraint WHERE conname = 'students_balance_trial_check'` OR via `information_schema.check_constraints WHERE constraint_name = 'students_balance_trial_check'`. After Phase 1.2 runs `bun run db push`, this query MUST return one row.
- **Domain semantics**: defense-in-depth (REQ-035) — rejects negative `balance_trial` at the DB layer regardless of application validation. The existing `students_balance_hifz_check`, `students_balance_reviews_check`, `students_balance_tajweed_check` constraints follow the same pattern; the new constraint extends INV-B1 to the 4th lane.

### 6.3 Phase 2.1 repo method carry-forward

The future `StudentRepository.grantFreeTrialOnce(studentId, trialCount, tx?)` write expression will be:

```ts
balanceTrial: sql`${students.balanceTrial} + ${trialCount}`,
trialGrantedAt: new Date(),
```

- The `sql\`\`` template MUST NOT contain inline `--` comments (Drizzle template rule).
- The WHERE clause will use `and(eq(students.id, studentId), isNull(students.trialGrantedAt))` for the grant-once predicate.
- `tx` is OPTIONAL LAST (per `backend/db/repo/AGENTS.md`) — inside registration, it is always the transaction handle (REQ-041).
- The method returns `boolean` (`updated.length > 0`); the service converts `false` to a localized `ConflictError` with `extensions.code = CONFLICT` (REQ-013 / REQ-050 / REQ-051).
