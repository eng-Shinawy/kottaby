1. Acquires a `pg.PoolClient` from `@/backend/db`'s `getPool()` singleton.

3. Inserts a probe `users` row (`full_name='Phase 1.2 Probe'`, `email='phase-1-2-probe@example.com'`, `role='student'`) returning `id` — required to satisfy `students.id` FK→`users.id` cascade.

## 8. Carry-Forward Knowledge for Phase 2.1 (Repo Method)

### 8.1 The CHECK constraint is live — DB-layer enforcement

Direct raw `INSERT`/`UPDATE` with `balance_trial < 0` will be rejected at the PostgreSQL layer with SQLSTATE `23514` and message naming `students_balance_trial_check` (verified by §5.2 Step 3). The Phase 2.1.TE Tier 4 security test (per `tasks.md` line 85 + REQ-075 constraint test) should use `expectRepoError` to assert this SQLSTATE / message; the test will pass against the live DB without any additional setup beyond `runInRollback`.

### 8.2 Columns queryable via Drizzle

After `bun run db push`, both columns are now queryable through the existing `db.select().from(students)` Drizzle query builder. The inferred types from `$inferSelect` (carried forward from `1.1-schema-columns-outcome.md` §6.1) are:

- `StudentSelectType.balanceTrial: number` (NOT nullable — stricter than the legacy `balanceHifz: number | null`)
- `StudentSelectType.trialGrantedAt: Date | null`

Phase 2.1's `grantFreeTrialOnce` repo method will be the first code path that *writes* these columns; no existing code reads them yet (carried forward from Task 1.1 §3.2 — `bun tsgo` confirmed zero consumer breakage).

### 8.3 `grantFreeTrialOnce` repo method (Phase 2.1) — implementation carry-forward

The repo method will be added to `backend/db/repo/students/student.repository.ts` with this contract (per `plan.md` §4):

```ts
export async function grantFreeTrialOnce(
  studentId: number,
  trialCount: number,
  tx?: DBTransaction,
): Promise<boolean> {
  const queryDb = tx ?? db;
  const updated = await queryDb
    .update(students)
    .set({
      balanceTrial: sql`${students.balanceTrial} + ${trialCount}`,
      trialGrantedAt: new Date(),
    })
    .where(and(eq(students.id, studentId), isNull(students.trialGrantedAt)))
    .returning({ id: students.id });
  return updated.length > 0;
}
```

Carry-forward constraints:

- The `sql\`\`` template MUST NOT contain inline `--` comments (Drizzle template hygiene; pre-existing rule).
- `tx` is OPTIONAL LAST per `backend/db/repo/AGENTS.md` — inside registration, it is always the transaction handle (REQ-041).
- The method returns `boolean` (`updated.length > 0`); the service (`StudentTrialService.grantFreeTrial`, Phase 2.2) converts `false` to a localized `ConflictError` with `extensions.code = CONFLICT` (REQ-013 / REQ-050 / REQ-051).
- The CHECK constraint (REQ-035) is now live, so any path that attempts to decrement below zero (e.g., an unintended double-decrement in DEV3 booking) will be rejected at the DB layer — this is the defense-in-depth safety net.
- The grant-once predicate `isNull(students.trialGrantedAt)` is the atomicity mechanism (REQ-042 / INV-B7); no `SELECT FOR UPDATE` or advisory lock is needed.
