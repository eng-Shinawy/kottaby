## 2. Implementation Details

### 2.1 Single insertion point — `createRoleChild`'s student case

The grant is invoked inside `createRoleChild`'s student case, AFTER `createStudentWithHandshakeRetry(userId, tx)` resolves successfully (the students row exists in the tx), INSIDE the surrounding `withTransaction(outerTx)` SAVEPOINT-aware scope, INSIDE the student branch ONLY.

The exact insertion (file `backend/services/auth/registration.service.ts`, current line 322–326):

```ts

  await createStudentWithHandshakeRetry(userId, tx);

```

The new line is the `await StudentTrialService.grantFreeTrial(userId, locale, tx);` call — exactly ONE new line in the student branch.

### 2.2 Supporting minimal changes (signature + call-site threading)

The `locale` parameter was already in scope at `registerUser(input, locale, outerTx?)` but NOT inside `createRoleChild` (a sibling internal function). To bring `locale` into scope at the insertion point without restructuring the transaction, the following supporting changes were made:

1. **`createRoleChild` signature** — added `locale: string` as the 3rd positional parameter (between `role` and `tx`):
   ```ts

     userId: number,
     role: "student" | "teacher" | "parent",

   ): Promise<void> { ... }
   ```

2. **`registerUser`'s call site** — added `locale` as the 3rd positional argument:
   ```ts

   ```

3. **`createRoleChild` JSDoc** — extended the student-branch bullet to describe the grant behavior in domain terms (no plan-artifact references):

### 2.4 Atomicity & transaction discipline

- The grant runs INSIDE the same `withTransaction(outerTx)` SAVEPOINT-aware scope as `createUserRow` and `createStudentWithHandshakeRetry` (REQ-018, REQ-040).
- The grant receives the SAME `tx` used by `createForRegistration` (REQ-041 — tx propagation). Both calls receive the `tx` from the surrounding `withTransaction(outerTx, async tx => …)` closure.
- IF the grant throws (e.g., `ConflictError` from a re-grant attempt — structurally unreachable on a freshly inserted row but a safety net for future callers), the throw propagates back through `createRoleChild` → `registerUser`'s `withTransaction` → the SAVEPOINT on `outerTx` rolls back, erasing the user row, student row, AND the grant UPDATE atomically. NO `try/catch` swallowing added around the grant call (REQ-053 — the grant is a first-class step).
- The grant inherits the existing SAVEPOINT-aware pattern; NO new transaction boundaries introduced; NO `SELECT FOR UPDATE` or advisory lock added (REQ-042 — the repo's guarded UPDATE is the atomicity mechanism).

### 2.5 BOPLA / BFLA / BOLA defenses (preserved)

- **BOPLA (REQ-031)**: `RegistrationSubmitInput` whitelist is byte-identical to DEV1-002. NO new fields, NO `{ ...input }` spread on insert mapping (the `createUserRow` field-by-field mapping is unchanged — verified by `git diff`). The grant count comes EXCLUSIVELY from `FREE_TRIAL_SESSION_COUNT` (read by the trial service, not by the registration hook).
- **BOLA/IDOR (REQ-032)**: `userId` is the server-derived PK of the freshly inserted `users` row (= shared PK of the freshly inserted `students` row). NEVER client input. The grant receives `created.id` (the insert result), NOT `input.id` or any client-supplied identifier.
- **BFLA (REQ-030/033)**: no new GraphQL mutation surface added (the hook modifies an existing service-internal function, not a Pothos resolver). No role can invoke the grant except the student registration path. Teacher/parent/admin registrations structurally bypass the grant.

### 4.4 Tier 3 forced-failure pattern (post-grant failure injection)

The Tier 3 test uses the dynamic-import-and-reassign pattern (mirrors the existing `withForcedApplicantCreateFailure` helper in `backend/db/test/logic/auth/registration.service.test.ts`):

```ts
const repoModule = await import("@/backend/db/repo/students/student.repository");
const originalGrant = repoModule.StudentRepository.grantFreeTrialOnce;
let grantCallCount = 0;
repoModule.StudentRepository.grantFreeTrialOnce = async (
  studentId: number,
  trialCount: number,
  txArg?: DBTransaction,
): Promise<boolean> => {
  grantCallCount += 1;
  // Run the real grant — the UPDATE executes, the marker is set in the transaction.
  await originalGrant.call(repoModule.StudentRepository, studentId, trialCount, txArg);
  // Then throw to force the registration transaction to roll back.
  throw new Error(FORCED_POST_GRANT_FAILURE_MESSAGE);
};
try {
  // ... test body ...
} finally {
  repoModule.StudentRepository.grantFreeTrialOnce = originalGrant;
}
```

Key design choices:
- **Dynamic import + namespace reassign** (matches the closest sibling test in `backend/db/test/logic/auth/registration.service.test.ts`) — ES module singletons guarantee the reassignment propagates to the registration service's `StudentTrialService.grantFreeTrial` → `StudentRepository.grantFreeTrialOnce` call chain.
- **Call original FIRST, then throw** — proves the grant's UPDATE DID execute inside the tx, AND the subsequent throw forces the SAVEPOINT rollback, erasing the grant along with the user and student rows. This is the strongest possible proof of REQ-018/040 atomicity.
- **`finally { restore }`** — guarantees no cross-test pollution even if the test body throws.
- **No SAVEPOINT workaround needed** — the injected failure is a JS-thrown `Error` (NOT a DB CHECK constraint violation), so the tx does NOT enter the SQLSTATE 25P02 "aborted" state. The SAVEPOINT-aware `outerTx.transaction(fn)` rolls back the savepoint on JS throw, leaving the outer tx usable for read-back assertions. (The Phase 2.1 Tier 4 SAVEPOINT precedent was needed only for DB-side CHECK rejections; not applicable here.)

### 4.5 Avoided pitfall: unsafe type assertion in the spy

The original draft used `as Parameters<typeof originalGrant>` to type the spy's parameters. Oxlint's `no-unsafe-type-assertion` rule would flag this. The fix: declare the parameters explicitly with their concrete types (`studentId: number, trialCount: number, txArg?: DBTransaction`) — matches the actual `grantFreeTrialOnce` signature read from `student.repository.ts` and avoids any type assertion.

### 8.2 `docs/IDEMPOTENCY.md` — structural idempotency argument

`docs/IDEMPOTENCY.md` mandates idempotency protection for every mutating POST that creates a new entity (Student, Invoice, Class Instance, Payment) via an `X-Idempotency-Key` HTTP header. The trial grant hook is structurally idempotent at TWO layers, without requiring an HTTP idempotency key on `registerUser`:

1. **Upstream `users.email` unique constraint (23505 → ConflictError)** — re-registration with the same email is impossible at the DB level. The `trial_granted_at IS NULL` predicate is the grant-once guard: a second grant attempt on the same student row matches zero rows → returns `false` → the trial service converts to `ConflictError` (REQ-013). Predicate evaluation and column mutation share ONE SQL statement, so the grant-once invariant holds with ZERO TOCTOU window (REQ-042).

Together, these satisfy IDEMPOTENCY.md's spirit: no duplicate trial can be granted via any path (re-registration is blocked upstream; re-grant on an existing student is blocked at the guarded UPDATE). The existing `registerUser` mutation already had its own idempotency guarantees via the unique email constraint; the trial grant piggybacks on that, requiring NO additional `X-Idempotency-Key` header on `registerUser` (the mutation is a public registration endpoint, not a payment/booking endpoint — the IDEMPOTENCY.md list of affected operations does not include `registerUser`, which has its own upstream unique-constraint idempotency).
