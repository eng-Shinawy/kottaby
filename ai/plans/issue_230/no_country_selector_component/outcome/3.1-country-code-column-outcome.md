### 3.1 Environment deviation, handled explicitly (documented, not silent)

1. **Stale snapshot chain:** the committed snapshot leaves (`20260919222143_fine_living_mummy`, `20260920140048_real_garia`) predate schema objects that only ever reached the DBs via `db push` (`broadcasts` table + enums, `evaluations.weakness_area`, `notification_type 'applicant_outcome'`, related indexes/FKs). A plain generate therefore emitted the **whole backlog diff**, not just the column. Committing that backlog would (a) violate the task's hard requirement that the migration SQL be exactly the additive column and (b) fail `bun db migrate` on the already-pushed sandbox DBs (42710/42P07 class). Resolution: the generated folder was kept, its `migration.sql` trimmed to the single `country_code` statement and passed through the repo's own `makeMigrationSqlIdempotent`, while `snapshot.json` stayed as generated. The backlog objects remain push-managed exactly as before this task; the pre-existing branchy snapshot chain is unchanged (pre-existing repo condition, out of 3.1 scope).
2. **Empty migration journal:** the sandbox DBs were built with `db push` (which records nothing), so `drizzle.__drizzle_migrations` did not exist and `bun db migrate` would have treated all 25 committed folders as pending. The repo's designed flow for this state is `ensureMigrationsBeforeSeed` (baseline already-applied folders → migrate pending); its baseline probes only know upstream folder names, so the equivalent baseline was performed directly: schema `drizzle` + table `__drizzle_migrations` created with the same DDL as `runDrizzleMigrations`, then 25 rows (sha256 of each folder's `migration.sql` + `folderMillis` from the folder timestamp + folder name — the exact fields the migrator writes) inserted for every committed folder **except** the new one. `bun db migrate` then applied exactly 1 pending folder: the new migration. Zero repo files changed by this repair (script: `/tmp/baseline_journal.sql`).
