## 1. Summary

Extended `AuthLabels` with the two country-selector validation keys and implemented them in both locale leaves, directly beside the legacy `countryRequired` (which is untouched — backward compat per REQ-7 assumption). Message semantics per specs.md REQ-7 + tasks.md 4.2:

| Key | en | ar |
|---|---|---|
| `countryCodeRequired` | `Please select a country.` | `يرجى اختيار الدولة.` |
| `countryCodeInvalid` | `The selected country is not recognized.` | `الدولة المحددة غير معترف بها.` |

- **required** conveys "the user must select a country" — en mirrors the sibling `roleRequired` ("Please select a role."); ar mirrors `يرجى اختيار دور.`.
- **invalid** conveys "the selected country is not recognized" — flat copy in both locales (the service MAY still fall back to `errors.validation` = "Invalid input."/"إدخال غير صحيح." per REQ-7 AC4; that is a 3.3 concern, not a label-text constraint).
- Arabic is natural RTL consistent with the sibling keys' tone (`يرجى …` request form; `الدولة المحددة` for "the selected country"); both values are Arabic-block verified (Tier 2).

**How to access them:**

  - keep field path `country` (REGISTER_FIELD_PATHS projection unchanged); optional fallback per REQ-7 AC4: `getServerTranslations(locale).errorsTranslations.validation`.
- `user-management.helpers.ts` (3.4) — the binding is `const tAuth = t.authTranslations` (`:217-219`): use `tAuth.countryCodeRequired` / `tAuth.countryCodeInvalid` in the create-path branch (update patch stays free-text per D-4).

**Pairing with validation:** empty-vs-invalid branch logic comes from `countryCodeSchema` / `normalizeCountryCode` (`@/shared/lib/country-code`, task 1.2 outcome §5) — empty/whitespace ⇒ REQUIRED code; anything else failing the schema ⇒ INVALID code.
