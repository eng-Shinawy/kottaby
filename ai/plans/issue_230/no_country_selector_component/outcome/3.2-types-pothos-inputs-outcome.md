## 1. Summary

Retyped the shared registration input helper's `country` field from `String!` to the `CountryCode!` scalar — one line in `backend/graphql/pothos/shared/userFieldHelpers.ts` — which propagates to BOTH wire inputs that compose it (`RegisterUserInput` and `AdminCreateUserInput`), and recorded the new ISO-code semantics on the service-boundary types (`RegistrationSubmitInput.country` / `AdminRegistrationSubmitInput.country` stay `string`, now documented as carrying an ISO 3166-1 alpha-2 code). The admin directory filter (`AdminUserFiltersInput.country`) and the admin update patch (`AdminUpdateUserInput.country`) deliberately stay legacy nullable `String` (deferred D-4). Regenerated + committed the SDL; the operations artifact `graphql.ts` is byte-identical BY DESIGN (see §3.3). The two pass-through resolvers (`auth.mutation.ts`, `admin-users.mutation.ts`) required NO changes: the builder's `Scalars` slot (task 2.1) types `CountryCode` `Input: string`, so `input.country` is still `string` at the resolver and flows unchanged into `RegistrationSubmitInput`/`AdminRegistrationSubmitInput`.

## 4. Carry-forward knowledge (for tasks 3.3 / 3.4 / 5.2)

- **The wire now enforces `CountryCode` on register + admin-create inputs.** Verified behaviorally: `"XX"`, `"Egypt"`, non-strings, missing values and unknown extra keys all die at variable coercion with `BAD_USER_INPUT` before any resolver — the service never sees them. What still REACHES the service: any code on the library's full ISO list (case-insensitively, UNCHANGED — e.g. `"eg"`, `"IL"`, `"XK"`). **Service normalization + curated-dataset membership therefore remain MANDATORY** — 3.3 (`registration.service.ts`) and 3.4 (`user-management.helpers.ts` create path) must still run `countryCodeSchema.safeParse(input.country)` and write `normalizeCountryCode(...)`'s result; do NOT treat the scalar as the membership gate (2.1 carry-forward restated with the retyped inputs).
- **Residual admin-create-form UX consequence (documented, accepted):** the admin create wire input now requires an ISO code (it shares `userFieldHelpers.ts` with registration), while the admin create FORM UI is not rebuilt in this plan — typing a display name ("Egypt") in that form will now be rejected at the wire. Recorded in `plan.md` §5.4/§8, `tasks.md` 3.2, and `deferred-items.md` D-4; the follow-up, if product wants to avoid it, is splitting the shared input helper (plan-review "Residual, documented consequence").
- **Frontend impact (5.2):** generated TS is UNCHANGED (`country: string`) — `RegisterFormValues.country` stays `string`; the codegen maps `CountryCode → string`, so no frontend type churn and the register document needs no edit. 5.2's work is the selector + RHF wiring, not generated types.
- **`graphql.ts` byte-identity gotcha:** any future input retypes between scalars that map to the same TS type will similarly produce NO `graphql.ts` diff — verify wire changes via `schema.graphql` + coercion tests, not via the operations artifact.
- **Wire-tier test conventions established:** coercion failures surface through `testClient` as `BAD_USER_INPUT` (not code-less) — assert `extractErrorCode(error)).toBe("BAD_USER_INPUT")` to distinguish transport rejection from service `VALIDATION`; Pothos enum variables take the TS enum KEYS (`"Student"`, not `"student"`).
