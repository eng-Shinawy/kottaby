```ts
// backend/db/repo/billing/plan.repository.ts
export const PLAN_ID_BATCH_LIMIT = 1000;

export interface AuditTrailLatestEntryRow {

  readonly actionType: string; // RAW stored pgEnum string — certification stays above the repo seam (5.2's job)
  readonly createdAt: Date;
}
export const AUDIT_ENTITY_ID_BATCH_LIMIT = 1000;
export namespace AuditTrailRepository {
  function countEntriesByEntityIds(
    entityType: string,              // the canonical audit label constant, e.g. SUBSCRIPTION_AUDIT_ENTITY_TYPE ("subscription") — passed BY THE SERVICE as data
    entityIds: readonly number[],
    tx?: DBTransaction
  ): Promise<Map<number, number>>
  function listLatestEntriesByEntityIds(
    entityType: string,
    entityIds: readonly number[],
    tx?: DBTransaction
  ): Promise<Map<number, AuditTrailLatestEntryRow | null>>
}
```

### Semantics (binding for 5.2)

- **`PlanRepository.findByIds`** — one row per MATCHED id; unmatched ids contribute NO row (the service's map assembly distinguishes present from absent — it must fill `null`, mirroring `findById`); duplicate ids collapse to the single stored row; **row order is unspecified** (key results by `id`); NO active predicate (a deactivated plan enriches historical rows — the `findById` twin); empty ids → `[]` without touching the DB.
- **`countEntriesByEntityIds`** — exactly one map entry per DISTINCT requested id; an id with no entries under the label is the honest `0` (never absent, never an error); rows under a different `entityType` label never count.
- **`listLatestEntriesByEntityIds`** — exactly one map entry per DISTINCT requested id; absent → `null` (the honest empty arm). The winning row per entity is the `created_at DESC, id DESC` winner (same-timestamp ties → higher id; `created_at` dominates insertion order) — proven equal to `listEntries`'s first row, so the batched peek agrees with the single-row peek.
- **Chunking:** lists longer than the 1000-id limit are split into sequential chunk statements whose results merge; a page-sized batch (≤100 ids) is a single chunk = a single round trip. Callers never manage chunking.

### Deliberate signature deviations from plan.md Component 8 (recorded for 5.2)

1. **`listLatestEntriesByEntityIds` returns `Map<number, AuditTrailLatestEntryRow | null>`, not `Map<number, SubscriptionAuditTrailPeek | null>`.** Plan.md's own implementation note rules "the repo returns raw rows; certification stays above the repo seam" — `SubscriptionAuditTrailPeek.actionType` is the certified `AuditActionType` member, and the fail-closed certification + domain logging is service-layer work (`subscription-admin.service.ts:575-601` pattern). **5.2's `auditTrailPeekBatch` must map `{ entityId, actionType (raw string), createdAt }` → `{ actionType: certifiedMember (withheld `null` on an uncertifiable literal), at: createdAt }`.** This also avoids the audit repo importing a billing service type.
2. **Audit methods take `tx?: DBTransaction`, not `DBQueryExecutor`.** The audit file's established read convention is `(tx ?? db)` with no `queryDb` split (plan.md prescribes the queryDb split only for the plan repo); `DBQueryExecutor`'s `Pool`/`PoolClient` members have no `.select` and that file has no guard leg for them. Every realistic 5.2 call (omit `tx`, or pass a `DBTransaction`) type-checks unchanged.
3. **Id parameters are `readonly number[]`** (accepts `number[]`; mirrors the file's `findBalanceLanesByIds` precedent).
