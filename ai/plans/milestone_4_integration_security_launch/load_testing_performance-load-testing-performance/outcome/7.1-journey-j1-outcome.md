## Design Rulings Recorded During Implementation

1. **SpiedFanoutTransport seam:** `createSession` owns its post-commit publish call (`NotificationEngine.publishReceipts([receipt], locale)` — `backend/services/classes/session-lifecycle.service.ts:237-239`) and exposes NO transport-injection parameter, so the `SpiedFanoutTransport` class cannot be installed at the transport seam on this flow. Per `test/workflows/AGENTS.md` rule 5 (spy the dispatch boundary via namespace import + `spyOn`), the spy sits on `publishReceipts` — the engine's publish contract IS the injection seam here. The recorded receipts carry `recipientUserIds` (and the persisted row), so the target-userId assertions the specs demand ("teacher-targeted dispatches matching the created sessions") are exact. Zero realtime/network delivery occurs: the spied method never reaches `publishAfterCommit`/transport resolution.
2. **Per-booking fail-open warns are pre-existing engine behavior:** each booking logs one `[DOMAIN] NOTIFICATION_IDEMPOTENCY_DEGRADED` warn (`claimOrPriorReceipt` — `backend/services/notifications/notification-engine.helpers.ts:47-49`) because `createSession` injects no claim cache. This is the documented fail-open posture (`emit-idempotency.ts` header), identical for every existing session-booking journey; no publish path is involved.
3. **Pool behavior at 100-way concurrency:** the 101 transactions queue on the hardcoded `max: 10` pool (~10 concurrent transactions; per-teacher `FOR UPDATE` serialization adds ~20-deep lock queues per hot teacher) and the whole wave still completes in ~170–190 ms — no `connectionTimeoutMillis` pressure, no deadlocks (the uniform teacher-row-first lock order held). No waves needed: full `Promise.allSettled` semantics preserved.

## Carry-Forward Knowledge

1. **Journey fixture pattern for large casts:** `entity-setup.ts` per-row helpers inside ONE committing `beforeAll` transaction scale fine to ~212 rows (~1 s), but provisioning loops must be recursive helpers (oxlint `no-await-in-loop` is deny-warnings); registration order (users row first, role-child second) IS the FK-safe reverse deletion order.
2. **`TrackedFixtures` over `SessionFixtureRegistry` for journeys with notification rows:** the domain-scoped registry has no `notifications` vocabulary; the table-generic `TrackedFixtures` registers them explicitly and its `cleanup()` re-probes every row (512 deletes + probes ≈ 1 s). Register service-created rows by querying ALL rows scoped to fixture ids (sessions by `studentId OR teacherId`, claims by `userId`, notifications by `userId`) — never assume the service's return values are the complete worklist.
3. **Array-index access + type-aware lint:** the project does NOT enable `noUncheckedIndexedAccess`, so `arr[i] === undefined` guards read as always-false to `sonarjs/different-types-comparison` — use `.at(i)` / `.find(...)` which produce genuine `T | undefined` types, or annotate the variable as `T | undefined`.
4. **Cognitive-complexity budget is 15 per function** (`sonarjs/cognitive-complexity`, type-aware stage): split large wave tests into module-level classify/assert/register helpers — the sub-loop's type-aware lint stage is stricter than oxlint.
