## The Document (section outline)

1. **Why** — caching is the most expensive performance lever (staleness + invalidation surface on a financial-truth platform); the mirror of REQ-3.5's no-speculative-indexes ruling: "a cache without a measured evidence case is not added — no folklore caches."
2. **Cache Inventory** — the 4 surfaces, each with a bounds table (scope / TTL-staleness / size bound / invalidation trigger / permission posture):
   - **Process-lifetime env snapshot** (`backend/lib/env.ts:65`; reset via `:488-490`; one object, process lifetime).
   - **In-memory rate-limit sliding windows** (`backend/lib/ratelimit.ts:96`; limiter configs incl. 100/60s GraphQL at `:61-65`; cap 10,000 identifiers at `:88-89`; LRU eviction to 80% at `:103-112`; per-window pruning at `:98-101`; fail-open at `:223-230`; SHA-256 identity keys at `:175-181`).
   - **Redis notification claim cache** (SET-NX-EX claim `backend/services/notifications/redis-claim-cache.ts:65-68`; TTL 24h = 86,400 `emit-idempotency.ts:30`; shared-client memo `:92`; 2s command/connect timeouts + `maxRetriesPerRequest: 1` at `:109-118`; fail-open §3.6 deviation, `docs/notifications/realtime-engine.md:149`).
   - **Request-scoped React `cache()` auth dedupe** (`backend/lib/auth/server-auth.ts:119`; request-lifetime memo; caches the caller's OWN permission resolution, never an authorization decision).
   - Plus adjacent bounded state (WS registries `notification-ws-server-state.ts:43-44`; throttle `WS_THROTTLE_MAX_TRACKED_IPS = 10_000` `notification-ws-server-constants.ts:20`; in-process transport registry) and the two non-surfaces.
3. **When to Cache — evidence-threshold rules** — the 5-step funnel (MEASURE → fix the query/EXPLAIN → fix the shape/batch → CACHE LAST → anything else → ledger with evidence, the D14 precedent) + 5 entry criteria, ALL mandatory: measured p95 breach from a retained artifact; cheaper levers adjudicated exhausted; permission-compatible read path; written staleness-window decision (financial surfaces default to zero staleness = no cache); a revert-path seam. "A proposal that cannot show all five is closed with 'no folklore cache'."
4. **Batch enrichment is the first line** — the before/after table (3N+1/3N+2: 4/76/301 own, 5/77/302 admin → constant 4/5 ≤ K=6 at sizes 1/25/100), the K=6 wire oracle + service-seam call-count lock, the counter-pattern (`backend/services/classes/session-lifecycle.queries.ts:113-121`), and the intentionally-unloaded dataloader plugin (`backend/graphql/pothos/builder.ts:15-17`) — caching is the second line because the batch fix needed no invalidation design, no TTL, no stale reads, no new dependency.
5. **The `CACHE_PROVIDER` seam — D2 deferred pointer** — parsed-but-unconsumed (`env.ts:26/:303/:421`, `.env.example:206`, zero consumers proven), wiring is a deferred separately-ticketed decision (ledger D2), with the **D2 entry criteria**: staging/cloud re-run showing a DB-bound p95 breach with `pg_stat_activity` evidence (sustained non-idle at the `max: 10` ceiling, `backend/db/client.ts:175`), shape+index adjudication already passed, and a permission-compatible read with a decided staleness window; the claim-cache adapter's injected-port shape named as the wiring precedent.
6. **Permission before cache** — `backend/services/AGENTS.md:14` restated precisely (gating before lookup; equivalently permission-scoped keys where reordering is impossible — a bare-entity-id key on an auth-gated surface is the forbidden construction) + a per-surface compliance table for all 4 caches.
7. **Closing evidence from 6.2** — the passing gates (6.2 p95 6.85ms/28.7× headroom; 6.3 WS; 6.5 K=6; 6.6 37/37; 6.7 47/47 — all with no query cache) AND the 6.1 FAIL-local as the strongest evidence: peak non-idle DB connections **0 across 33 samples** while p95s ran 2,473–4,288ms (my-subscriptions 4,288ms with an idle DB and a constant 4-statement page); a distributed cache would not have rescued the gate — the bottleneck was single-process server CPU (bcryptjs-12 + GraphQL execution). Conclusion: "No distributed query cache is justified at ~100 concurrent users on the measured stack."
8. **What NOT to Do** — 8 prohibitions (folklore caches; cache-before-permission; speculative `CACHE_PROVIDER` wiring; caching broken shapes / cache-masking a broken batch; treating the claim cache as a data cache; entity caches without invalidation design; blaming the DB without the pg snapshot; manufacturing a cache case by lowering gates/shrinking seeds).
