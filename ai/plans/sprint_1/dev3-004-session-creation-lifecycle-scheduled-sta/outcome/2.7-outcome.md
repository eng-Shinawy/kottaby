## 2. Exact Public API (for task 2.8 — method-by-method contract)

Every method: **`tx?: DBTransaction` LAST parameter**. Writes on `tx ?? db` (same fallback as 2.6's `insertSession`); reads on `tx` (Drizzle select) or standalone via raw parameterized SQL through `queryDb`.

```ts
export namespace SessionRequestIdempotencyRepository {
  insertClaim(insert: SessionRequestIdempotencyInsertType, tx?: DBTransaction): Promise<SessionRequestIdempotencySelectType>;
  updateClaimSessionId(claimId: number, sessionId: number, tx?: DBTransaction): Promise<void>;
  findByKey(key: string, tx?: DBTransaction): Promise<SessionRequestIdempotencySelectType | null>;
}
```

- **`insertClaim`** — ONE `INSERT … RETURNING *`; caller supplies `{ idempotencyKey, userId }` (session id NOT set at claim time; `createdAt` schema-defaulted). A duplicate key raises PG `23505` (`session_request_idempotency_key_unique`) wrapped by Drizzle — **NOT caught/translated here**; carries the repo-wide defensive invariant throw (`insert returned no rows`, unreachable — same house precedent as `SessionRepository.insertSession`).
- **`updateClaimSessionId`** — ONE `UPDATE … SET session_id=? WHERE id=? RETURNING {id}`; key/owner columns never re-written; throws the defensive invariant `update matched no rows` if zero rows matched (unreachable inside the creation flow — the claim was inserted in the same tx).
- **`findByKey`** — equality on `idempotency_key` (`$1` bound parameter in the standalone `queryDb` branch); returns the full row (with `sessionId` when the backfill landed) or `null`. Participant/user scoping of a replay is the service's decision.

## 7. Carry-Forward for Task 2.8 (SessionLifecycleService) — esp. the 23505 cause-chain path

1. **REQ-040 four-phase order in ONE `withTransaction(outerTx)` tx:** phase 3 = `SessionRequestIdempotencyRepository.insertClaim({ idempotencyKey, userId: actingStudentId }, tx)`; phase 4 = `SessionRepository.insertSession(...)` → `SessionRequestIdempotencyRepository.updateClaimSessionId(claim.id, sessionRow.id, tx)`.
2. **23505 → `DUPLICATE_REQUEST` cause chain:** a duplicate claim insert rejects with Drizzle's `DrizzleQueryError` wrapping the driver error. Traverse `error.cause` (cycle-safe `seen`-set walker, exactly like the test's `hasPostgresErrorCode`) until an `Error` with `code === "23505"` is found — NEVER read `.code` off the top-level wrapper and NEVER branch off `.message`. Optionally verify `constraint === "session_request_idempotency_key_unique"` on the deepest cause. Then: `findByKey(key, tx)` to load the claim — if `claim.sessionId !== null`, return the already-created session (success-equivalent replay per REQ-014/`docs/IDEMPOTENCY.md`); if the claim is still session-less (original tx still in flight or aborted), classify per spec (replay branch vs conflict). SEC: translate WITHOUT echoing the raw Drizzle message (it embeds the key) — log `{code, entity:"session"}` only.
3. **`updateClaimSessionId` throws its invariant on zero rows** — inside the flow that can only mean a bug (claim inserted in the same tx); let it fail loudly, do not catch.
4. **Ownership scoping of a replay is the service's job:** `findByKey` returns the raw claim — compare `claim.userId` against the acting student and treat a mismatch as a conflict (never surface another user's claim).
5. **Claims are inserted session-less first:** `sessionId` is null until the backfill — a committed-but-unbackfilled claim (impossible inside one tx, but possible after a manual statement boundary) must not be treated as a completed replay with a session to return.
6. **Key guard lives at the service boundary** (non-empty ≤128 BEFORE the repo is reached); the repo intentionally performs no length/format validation — the DB varchar(128) + `22001` is the backstop, never the primary check.
