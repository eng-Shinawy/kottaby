## DateTime scalar amendment (rationale)

- **Fact:** the Pothos registry had NO DateTime scalar — documented in `teachers/applicant.pothos.ts`, which rode the HealthCheck precedent of exposing nullable timestamps as ISO-8601 `String` fields.
- **Driver:** REQ-060 mandates real `DateTime` fields on `Plan` (`deactivatedAt: DateTime` nullable, `createdAt/updatedAt: DateTime!`). Byte-fidelity to REQ-060 requires a genuine custom scalar, not a String retelling.
- **Implementation:** `gqlSchemaBuilder.scalarType("DateTime", { serialize, parseValue })` — `serialize: value => value instanceof Date ? value.toISOString() : String(value)`; `parseValue` validates (rejects non-string/non-Date inputs and `Invalid Date`) and returns a real `Date`. One registration, imported into `plan.pothos.ts` so it flows through the side-effect chain.

### TypeScript wiring decision (deviation worth recording)

The project builder (`backend/graphql/pothos/builder.ts`, **unmodified**) instantiates `SchemaBuilder` with `{ Context, Defaults: "v3", AuthScopes }` and **no `Scalars` override**. In @pothos/core 4.13.1 that makes `ScalarName<Types>` resolve to only the five base scalars, so `scalarType("DateTime", …)` does **not** type-check out of the box, and the documented `PothosSchemaTypes.UserSchemaTypes` augmentation route is closed (its `Scalars` member is pre-declared with a string index signature — redeclaring it raises TS2717).

Resolution: a **module augmentation of `@pothos/core`'s `V3DefaultScalars`** table (declared inside `datetime.pothos.ts`):

```ts
declare module "@pothos/core" {
  interface V3DefaultScalars {
    DateTime: { Input: Date | string; Output: Date };
  }
}
```

Verified via tsgo probes that this (a) admits `"DateTime"` as a scalar name, (b) resolves `Types['inputShapes']['DateTime'] = string | Date` and `Types['outputShapes']['DateTime'] = Date`, so field resolves type-check with real `Date` parents (drizzle `timestamp` mode `date`). This is type-level only — zero runtime effect — and touches no existing file. Also recorded: graphql-js types `parseValue` as `(inputValue: unknown) => TInternal`, so the declared `Input` shape constrains the parser's RETURN, not its parameter; `parseValue` therefore narrows at runtime.
