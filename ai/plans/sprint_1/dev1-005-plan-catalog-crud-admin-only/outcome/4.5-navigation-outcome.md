## Sanctioned deviation — nav label stays on the DASHBOARD namespace

The task text said the plans item's label comes "from the `plans` namespace".
That is not implementable at the nav layer: `DashboardNavItem.labelKey` is
typed `keyof DashboardLabels`, so a nav label MUST be a dashboard-namespace
key (the sidebar resolves it via `resolveNavItemLabel(item, t)` where
`t = useAppTranslation(Dashboard)`). The `plans`-namespace keys (pageSubtitle,
loading, emptyStateTitle, … — Task 1.4) serve the PAGE CONTENT (Task 4.2's
`app/(dashboard)/admin/plans/`), not the nav. The dashboard namespace already
carries `plans: "Plans"` (EN) / الباقات (AR), which is the established
nav-label mechanism used by every other sidebar item. Documented here as the
deviation; no type or mechanism change made.

## Test-harness findings (recorded for later agents)

- The shared `happydom-preload` registers a **1024px viewport**, below MUI's
  `lg` breakpoint (1200px). At that width the sidebar's permanent drawer
  (`display: { xs: "none", lg: "block" }`) is `display:none` → the anchors are
  INVISIBLE to `getByRole("link", …)` (RTL excludes hidden elements), while the
  closed temporary drawer (keepMounted) is aria-hidden. Fix: the suite widens
  the viewport to 1600px in `beforeAll` via happy-dom's `window.happyDOM
  .setViewport()` — reached assertion-free through a `Reflect.get` + type
  guard (oxlint `no-unsafe-type-assertion` / `jsx-no-constructed-context-values`
  clean; context values hoisted to module-level constants).
- `next/link` renders real anchors under this harness — no mock needed.
