### Lifecycle mechanics (derived from Task 1.2 BOPLA audit)

`PlanSubmitInput` structurally excludes `isActive`/`deactivatedAt` — there is **no service path to create a plan pre-deactivated**. Fixture (d) is therefore provisioned in two service calls:

1. `createPlan(PlanSubmitInput)` — row starts active (schema default `is_active = true`, Task 1.1).
2. `setPlanActiveStatus(id, false)` — the guarded conditional UPDATE (D2). Idempotency is free: on re-run the transition `active→inactive` can only fire once; any second call hits the `eq(plans.isActive, !target)` guard, returns empty RETURNING → `null`, mutates nothing, raises nothing. Re-run find-or-create finds (d) inactive by title and must NOT re-activate it.
