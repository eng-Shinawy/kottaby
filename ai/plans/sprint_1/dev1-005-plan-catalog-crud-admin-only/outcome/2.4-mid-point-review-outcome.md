## 4. Documentation rulings (no code change)

### Ruling A — sanctioned test deviation (Finding 3)

`backend/db/test/logic/billing/plan-catalog.service.test.ts` uses module-scope `getServerTranslations("en")` / `getServerTranslations("ar")`. `backend/db/test/AGENTS.md` Rule 19 forbids `getServerTranslations` in tests (its rationale: tests must not depend on server-side i18n plumbing for their own scaffolding). Here, however, the translations are not scaffolding — they are the **assertion oracle** for the service's localized domain-error messages (service receives a locale and must produce exactly the `plans.*` namespace copy for that locale). Recreating the copy inline would duplicate the very strings under test and rot silently. **Ruling: sanctioned deviation for service-localized-message assertions only; not a deferral; no code change; Rule 19 remains binding for all other backend/db tests.**

### Ruling B — Phase 3 carry-forward (Finding 4)

`PlanCatalogService` translates PG `23514` (check violation) into a localized `ValidationError` whose top-level `code` is `PLAN_*_INVALID` (class `VALIDATION`). Outcome 2.3 §7's resolver carry-forward table did not list this code. **Ruling (carry-forward note for Phase 3):** the GraphQL `formatError` mapping implemented in Phase 3 MUST pass `PLAN_*_INVALID` through with class `VALIDATION` (so the wire contract is `extensions.code = PLAN_*_INVALID`, class `VALIDATION`, `fields[]` populated), consistent with `docs/graphql/domain-error-extensions-code.md`. This obligation is inherited by Tasks 3.3 (mutation TE/IV items) and is not a defect in the service.
