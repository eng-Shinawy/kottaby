## ⚠️ KEY DEVIATION — one census binding edit (sanctioned by tasks.md rule 7), with root cause

The planned census binding title for the U4 backstop said *"a referenced-user raw DELETE raises **23503** in a savepoint"*. **Against the live test DB this is factually wrong** — verified by a live probe:

- The dossier's cite (`session_student_id_students_id_fkey` → `students.id`, migration `20260904084151`) is **stale**: migration `20260920140048_real_garia` DROPPED that constraint and re-pointed `session.student_id` → **`users.id`** with constraint name **`session_student_id_users_id_fkey`** (also visible in the live schema, `backend/db/schema/classes/session.ts:57-59`).

Landing the planned title verbatim would have produced a test whose title asserts a falsehood (or a red test asserting 23503). ## Carry-forward knowledge

1. **`session.student_id` references `users.id` (RESTRICT), not `students.id`** — re-pointed by migration `20260920140048_real_garia`. Any test asserting session-student FK shape or writing session fixtures must use user ids directly and expect `session_student_id_users_id_fkey` + SQLSTATE **23001** (restrict_violation) on referenced deletes. 23503 is unreachable via RESTRICT FKs on this path.
2. **ON DELETE RESTRICT ⇒ 23001, not 23503** — the C4 helper's `expectFkViolation` (23503) fits insert-side FK violations; referenced-row deletes under RESTRICT need `hasPostgresErrorCode(err, "23001")` + `constraintNameOf`. If a future task needs this often, an `expectRestrictViolation` expector belongs in task 2.2's helper (owned file — do not bolt it on elsewhere).
3. **The committed-fixture exception is structural, not stylistic**: `AuthService.login`/`refreshToken` read identity via the bare pool and rotate in their own transactions — any test of those gates needs committed fixtures + `deleteUsersByIds` teardown. The census INV-U3 row's `notes` field documents this for future readers.
4. **Fixture teardown ordering for users with full history**: student_payments (RESTRICT to students + append-only trigger) → sessions (RESTRICT to both participants; reports cascade) → `deleteUsersByIds` (audit rows + subscriptions + evaluations + users). `deleteUsersByIds` alone is NOT sufficient when a fixture has sessions or payments.
5. **Registration credentials**: `RegistrationService.registerUser` hashes the password itself — do NOT pre-hash and overwrite (my initial draft did; removed). The D11 mirror is the authoritative shape.
6. **`setUserSuspended(id, false, null, …)`** — the unsuspend direction ignores/accepts a null `periodDays` (validation applies to the suspend direction only, 1..3650).
7. Cross-axis transitions (suspended→blocked→deleted) are all permitted by the guarded predicates (they exclude only `is_deleted`) — the ladder is the documented shipped semantics; the doc's §6.2 matrix omissions are covered by the census `docDrift` records and task 6.1's annotations.
