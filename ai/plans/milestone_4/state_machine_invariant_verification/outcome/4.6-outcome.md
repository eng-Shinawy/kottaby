## Carry-forward knowledge

1. **`PlanCatalogService` catalog mutations mint audit rows** — every `setPlanActiveStatus`/`updatePlan` call appends exactly ONE plan-anchored `audit_logs` row (Suspend/Update, `entity_type='plan'`) attributed to the acting admin. Journeys exercising this surface MUST sweep those rows FIRST in `afterAll` under `withAuditDeleteTriggersSuspended` (the admin-lifecycle precedent) or the RESTRICT FK blocks the users teardown.
2. **The booking's teacher request wave rides the SAME `NotificationEngine.publishReceipts` seam as the activation receipt** — a journey with both legs sees publish call 1 → purchaser, call 2 → teacher; the persisted teacher notification row must be tracked (found by `userId = teacher`), and the wave is composed in the teacher's persisted locale.
3. **A fresh `provisionStudentActor` fixture has `balanceTrial = 0`** (DB default; the trial grant is a registration-path effect the factory does not run), so a booking after a lane credit funds from the INTENT lane directly — `heldBalanceLane = Hifz` without any trial-drain setup. Journeys that want the trial to fund must seed it explicitly (the expiry journey's `TRIAL_REGRANT` pattern).
4. **Byte-snapshot pattern for cross-actor invariance**: capture the full row (Drizzle select object) + the lane tuple after the crediting step, then `toEqual` at every later observation point — the full-row comparison catches ANY write (including `updatedAt`), not just the fields the plan enumerates. The `snapshots()` narrow-guard makes step order a hard precondition.
5. **The real GraphQL `planCatalog` query is cheap in-process journey surface** for catalog-visibility flips (presence pre-mutation / absence post-mutation by the same caller) — `t.exposeID` serializes ids as strings, so map `Number(entry.id)` before comparing to numeric fixture ids.
