## Usage idiom (for Phase 3/4 consumers)

```ts
import { runInRollback } from "@/backend/db/test/test-utils";
import {
  probeInsideSavepoint,
  expectCheckViolation,
} from "@/backend/db/test/logic/invariants/invariant-probe.helpers";

await runInRollback(async tx => {
  const fixture = await createTestWallet(tx, teacherId, { balance: "10.00" });
  const error = await probeInsideSavepoint(tx, "wallet balance probe", () =>
    tx.update(wallet).set({ balance: "-1.00" }).where(eq(wallet.id, fixture.id))
  );
  expectCheckViolation(error, "wallet_balance_check");
  // outer tx still queryable — re-read the row to prove it is unchanged:
  const [after] = await tx.select().from(wallet).where(eq(wallet.id, fixture.id)).limit(1);
  expect(after.balance).toBe("10.00");
});
```

Semantics Phase 3 agents MUST know:
- `probeInsideSavepoint` opens `savepoint inv_<sanitized label>` via `tx.execute(sql.raw(...))`, runs the probe under try/catch, and executes `rollback to savepoint` in a `finally` — the savepoint is rolled back ALSO when the probe succeeds, so probe writes never leak into the outer `runInRollback` transaction (verified live: a successful probe leaves the row byte-identical).
- It THROWS (with the label in the message) when the probe resolves without failing — a probe that violates nothing is a broken probe, not a green test. For succeed-then-rollback legs (e.g. 3.4's unreferenced-plan DELETE, 3.9's set-null survival) do NOT use this helper — those run plain statements inside `runInRollback` (or committed fixtures per their tier).
- The label is sanitized to a SQL identifier (non `[A-Za-z0-9_]` → `_`, lowercased, empty → `probe`) because savepoint names are identifiers, not bind parameters — verified against a hostile label containing a backtick + SQL comment.
- All statements inside the probe body must use the SAME `tx` (mixing `tx` and `db` deadlocks).
- The named-constraint expectors assert THREE things: SQLSTATE in the cause chain, `constraintNameOf(error) === constraintName`, and the name present in the joined cause-chain text — an aborted-transaction `25P02` can never satisfy them.
- `expectTriggerRaise` matches the raised text only (immutability triggers use custom SQLSTATEs); assert the exact DDL RAISE substring.
