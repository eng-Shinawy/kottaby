## Design decisions (recorded for reviewers)

1. **D-412 resolution (the prescribed one):** no `createTestProgress` helper was added. The legal lesson-less leg writes through `ProgressRepository.insertRow({ studentId }, tx)` — the repo's own pointer writer, whose `ProgressInsertType` (`$inferInsert`) accepts `lessonId` as optional — and the adversarial NULL/orphan legs use raw wire-level `tx.execute` probes (the typed insert surface requires `studentId`, so the null can only arrive at the DB tier, which is exactly what the probe asserts). This mirrors 3.2's D-411 handling: single-consumer paths stay raw, the frozen entity-setup battery stays frozen (knip).
2. **PR3 erratum vs. dossier 09 §4 (honesty note):** the dossier (and plan §5.2) describe the null-plan denial as "the `:172-173` gate calls `assertPlanExistsForLesson(null)`". Live trace: a wire-shaped `planId: null` never REACHES that gate — `validatePlanIdField` (`backend/services/classes/lesson.helpers.ts:179-188`) rejects null first (`null` fails `Number.isInteger`) and throws the IDENTICAL `ValidationError` payload (`buildPlanIdFieldError` ⇒ `LESSON_PLAN_NOT_FOUND` on the planId field) the gate produces for non-existent ids. The user-visible contract — `LESSON_PLAN_NOT_FOUND`, zero writes — is the same either way, so the census binding and the test are honest as written; the in-test comment describes the ACTUAL behavior (the plan-membership denial payload), not the dossier's internal-step guess. No doc drift arises (the doc's invariant statement is about the contract, not the internal step).
3. **One binding = one test:** each census `testName` is a single `test(...)` title carrying all its legs (the oracle greps a substring of the title). The HW1 cascade leg runs LAST in its test (it removes the fixture row the earlier legs re-read); the HW2 survive leg ends with a legal grade so "row survives" is proven as "intact AND gradeable", not just "present".
4. **Probe mechanics:** every failing probe goes through `probeInsideSavepoint` + the named expectors (`expectNotNullViolation`/`expectFkViolation`/`expectCheckViolation`) from the C4 helper — never `expect(...).rejects`, never hand-rolled savepoints. The two succeed legs (PR1's legal NULL row; HW1's cascade delete) run plain statements inside `runInRollback` per the 2.2-outcome rule (`probeInsideSavepoint` THROWS on succeeding probes).
5. **Orphan ids are computed, not guessed:** `absentSessionId`/`absentLessonId` read `coalesce(max(id), 0)::int + 1_000_000` inside the caller's transaction (the `absentPlanId` precedent, `lesson.repository.test.ts`), so the probes can never collide with a parallel worker's committed row.
