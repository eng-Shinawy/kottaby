## 6. Notes for the plan (scope risks, sibling-plan overlap, ambiguities)

1. **Ticket Gherkin is stale vs the doc**: docs/planning/TICKETS.md:2893 reads "Subscription & balance (INV-B1 through INV-B6)" — B7/B8 are NOT in the ticket table (they postdate it; the ticket's Payment row also caps at INV-PAY1..PAY5 while the doc has PAY7). The ticket description (:2884) says "all state machine invariants from docs/specs/state-machine-invariants.md", so the plan should treat the DOC as canonical and include B7/B8. This dossier confirms both are already heavily covered — near-zero new-test cost.
2. **INV-PC1..PC3 are OUT of the ticket's 10-machine Gherkin** (ticket lists S/TV/A/B/W/U/P/PAY/HW+PR/E only; §11 Plan Catalog is an 11th machine). The ticket's "10 state machines and 50+ invariants" phrasing excludes PC. Plan must rule explicitly: either (a) exclude PC1..PC3 with a recorded rationale, or (b) include as cheap scope extension — only ONE genuinely missing test (the PC2 journey, §4) plus a PC3 doc-ruling; PC1 and the SDL half of PC3 are already covered.
3. **INV-B5 doc-vs-code mismatch (load-bearing)**: the doc's "review sessions decrement `balance_reviews`" clause has NO product surface — `SessionIntent` is hifz/tajweed/evaluation (session-intent.enum.ts:6-10), `HeldBalanceLane` deliberately excludes reviews (held-balance-lane.enum.ts:14-15), and grep proves zero decrement writers for `balance_reviews`. The reviews lane is credit-only today (activation/plan-change-set/expiry-zero). The verification plan must pin the implemented half (segregation among trial/hifz/tajweed) and record the unimplemented clause as a doc-level enforcement gap, NOT a test gap. Writing a runtime test for reviews-lane booking is impossible.
4. **INV-PC3 is enforced by absence, not by a DB guard**: there is NO `prevent_plans_delete` trigger anywhere in backend/drizzle (grep across all custom_*.sql: only audit_logs, student_payments, teacher_transaction triggers exist — custom_3-immutability-triggers/migration.sql:30-98). `PlanRepository` has no delete method (plan.repository.ts:42-241), the SDL has no deletePlan (pinned by plan-catalog.schema.test.ts:58), and only `subscriptions.plan_id` restricts (:35-37) — `lessons.plan_id` is `set null` (lessons.ts:21). A raw SQL DELETE of an unreferenced plan WOULD succeed. The test plan can pin the referenced-plan FK rejection + the writer-absence; a true DB-level DELETE guard would be a schema change (out of ticket scope).
5. **Enforcement-mismatch nuance on INV-B3 vs the flat balance model**: the shipped semantic is CONDITIONAL lane zeroing (covered lanes survive the sweep — zero-lane.helpers.ts:60-94, tested at student-zero-lane.repository.test.ts:223/:240), and the admin-cancel note (doc :177-190) documents the deliberate cancel-preserves-balance asymmetry, plus "cancelled is NON-covering, so a LATER sweep of ANOTHER covering subscription may still zero a cancel-preserved lane" (doc :186-187). No existing test exercises that cancel→later-sweep interplay. If the plan wants full note-coverage, that is ONE small rollback-wrapped case in backend/services/billing/subscription-expiry.service.test.ts (cancel one covering sub, let a second sub's sweep zero the lane).
6. **INV-B8 ordering proof lives in a journey, not the service suite**: the only both-lanes-positive ordering assertion is test/workflows/classes/session-report-homework.journey.test.ts:583-584. The service-tier booking suite's trial-success case (session-lifecycle.booking.test.ts:542) runs after the sweep zeroed the paid lane, so it does not prove ordering. Cheap strengthening: one runInRollback case in session-lifecycle.booking.test.ts seeding `{ balanceTrial: 1, balanceHifz: 3 }` (no sweep) asserting `heldBalanceLane === Trial`, trial 1→0, hifz stays 3.
7. **Sibling-plan overlap**: dossier 08-payment.md covers INV-PAY3/PAY6 (activation exactly-once) which shares `activatePendingOnce` with INV-B2 — the plan should place the credit-side assertion under B2 and the replay/idempotency assertions under PAY6 to avoid duplicate journey work. Dossier 11 (test infra) owns runInRollback/registry mechanics.
8. **Test-isolation gotcha**: `SubscriptionExpiryService.expireDue` sweeps the WHOLE shared test DB; exact-count assertions MUST use the `scopeSweepToUsers` spyOn seam (subscription-expiry.service.test.ts:198-210) or committed-fixture journeys, otherwise unrelated due rows break counts.
