## 6. Notes for the plan (scope risks, sibling-plan overlap, ambiguities)

1. **Doc-vs-code mismatches discovered (pin them as "as-shipped" in the tests, do NOT "fix" the doc in this test-writing plan):**
   - INV-PAY1 says `>= 0` but the live CHECK is `amount > 0` (backend/db/schema/billing/student-payments.ts:74) — `0.00` is REJECTED. The new test must assert the shipped semantics (reject `0.00` and negatives). The entity-setup docblock at backend/db/test/entity-setup.ts:259 also wrongly says "must stay non-negative".
   - INV-PAY4 lists 5 gateway values (stripe, paypal, paymob, fawry, other) but the live pgEnum has 9 (backend/db/schema/enums.ts:67-77: + offline_cash, bank_transfer, scholarship, mock). The enum-set pin test should assert the 9-value shipped list.
2. **Ticket Gherkin scope ambiguity:** docs/planning/TICKETS.md:2905 names "Payment (INV-PAY1 through INV-PAY5)" but the spec doc defines 7 payment invariants (:307-:308 add PAY6/PAY7, both marked as owned by docs/billing/subscription-purchase.md — doc :285-289, purchase doc :49-52). The parent plan should treat the ticket's "50+ invariants … all state machine invariants from state-machine-invariants.md" as the governing scope → include PAY6/PAY7 (they are the best-covered; only registry/naming work, if any).
3. **E2E ruling (gathered facts):** `bun run test:ui:e2e:paymob` (package.json:35) requires `PAYMOB_LIVE_TESTS=1` + `.env.paymob.test` live credentials + `build:test` (package.json:42) + a real ngrok tunnel (test/workflows/billing/paymob-live-tunnel.journey.test.ts:4, :507 `describe.skipIf(!live)`). If the ticket demands *named per-invariant verification tests*, the cheapest compliant shape is a thin **registry/alias layer** — e.g. one `INV-PAYn` mapping test per invariant citing the existing test(s) — rather than duplicating assertions.
