## Guard Order Proof (1.3.SEC)

`guardTransport` order preserved verbatim with the new tier appended last —
`method → content-type → declared content-length → drain → drained-length → JSON parse → batch-count`:

1. `assertAllowedMethod` (`:183`) → 2. `assertJsonContentType` (`:188`) → 3. declared-length checkpoint (`:195`) → 4. `request.text()` drain (`:205`) → 5. drained-length checkpoint (`:211`) → 6. strict `JSON.parse` (`:218`) → 7. `assertBatchOperationCount(parsed)` (`:225`).

Batch-count runs after parse BY NECESSITY (the cap compares the parsed array's length). Any `ok:false` short-circuits — the route (`app/api/graphql/route.ts:172-174`) returns `transportRejectionResponse(transport.kind, request)` before the context factory or engine is ever reached (proven end-to-end: the 11-op POST returns the 400 `BATCH_OPERATION_LIMIT` envelope). Order-under-adversity locked by tests: a >2 MB body carrying 11 ops is rejected as 413 `PAYLOAD_TOO_LARGE` (size wins — drained checkpoint precedes parse/batch); a content-type attack on an 11-op body dies as `UNSUPPORTED_CONTENT_TYPE`; a lying small `content-length` forces the DRAINED site to fire. The cap cannot be bypassed by wrapping operations in a single object body: an object IS one operation (embedded arrays are request data, not fan-out) — pinned by test AND stated in the guard docblock.
