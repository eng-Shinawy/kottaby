Normalization: untrimmed unicode email reaches the service TRIMMED; empty/whitespace email + empty password reject pre-service with invalid-credentials (spy: service NOT called).
- **Tier 2 (boundaries + unicode):** password 72 and 1_024 reach the service (spy called exactly twice); 1_025 rejects pre-service; unicode email trims through the resolver, and casing/whitespace variants of one unicode email share ONE identity bucket (20 pass / 21st rejects through the wire — the resolver's `hashAuthIdentity` folds trim+lowercase).
- **Tier 3 (concurrency):** 11 PARALLEL login executions from one IP → exactly 10 UNAUTHORIZED (passed the gate, failed credentials) + exactly 1 RATE_LIMIT_EXCEEDED (event-loop atomicity).
- **Tier 4 (bypass probes):** field aliasing (`loginAlias: login`, `burstAlias0..10`) does NOT bypass — under the limit the aliased field reaches the service; an 11-burst of distinctly-aliased executions still yields 10/1; on an exhausted bucket the aliased field answers RATE_LIMIT_EXCEEDED. Empty/whitespace-only email digests to the `""` sentinel → IP-only bucketing (25 distinct-IP calls never trip the 20-cap identity bucket; from ONE IP the 11th whitespace-email call rate-limits).
- **Ordering proof, zero spies:** the under-limit vs exhausted distinction on the SAME (nonexistent-email, wrong-password) input — UNAUTHORIZED vs RATE_LIMIT_EXCEEDED — IS the proof that enforcement runs before any credential work; no `checkRateLimit`/service spies on that path.

## Design note: aliased-mutation probe vs GraphQL execution semantics

The task's Tier-4 sketch ("11 aliased login fields in one document") hits graphql-js's non-null propagation rule: when an erroring root mutation field has a NON-NULL payload type, the null bubbles past the root and graphql-js CANCELS the remaining sibling field executions — so a single multi-alias document executes only the first field. The probe was reshaped to the semantics that still prove the requirement: (a) an aliased login under the limit reaches the service (the alias runs the same resolver); (b) a parallel burst of 11 DISTINCTLY-ALIASED login executions from one IP still yields exactly 10 pass / 1 rate-limited (aliases mint no fresh buckets); (c) an aliased login against an already-exhausted bucket answers RATE_LIMIT_EXCEEDED. Field-level enforcement is bypass-proof under aliasing, which is the actual security claim.
