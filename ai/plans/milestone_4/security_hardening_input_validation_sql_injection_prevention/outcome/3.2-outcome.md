## Payload-Matrix Results — ALL NEUTRALIZED, ZERO WIDENING

For every payload × every suite:
- **Literal-match proof**: a carrier fixture embedding the payload VERBATIM in its searchable name is the only match (plus any genuinely-literal foreign rows — verified against an independent `position()`-based literal-substring oracle, which shares zero semantics with the LIKE path under test).
- **Widening proof**: decoy fixtures that WOULD surface under wildcard semantics (`1000`/`100xyz` for `100%`, single-char swaps for `_`, `%`-named rows for `\`, `admin`/`administrator` for `%admin%`, `a0b9cd`/`a%b_cd` for the mixed payload, sibling SQL strings) NEVER appear in the result.
- **Exact match-set equality**: directory + payments suites assert `total === oracleCount` and full id-set equality against the `position()` oracle; the matching suite asserts exact `total === 1` + id equality (its RARE_READING certification already isolates the page to the suite's own fixtures).
- **Zero rows modified**: `tx.$count(...)` before/after every payload execution is identical (`users` + `teacher` in matching/directory; `student_payments` + `users` in the audit suite) — the SQL-injection strings reached the database only as bound parameters and executed nothing.
- **Membership invariant**: every surfaced row's searchable text literally contains the (trimmed, where the service trims) payload — no non-literal row can leak in.

**No production defect found** — every search surface already escapes at its single `escapeLikeWildcards` point and binds parameterized patterns, exactly as documented.
