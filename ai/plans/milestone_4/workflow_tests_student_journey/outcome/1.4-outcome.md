1. **Progress increment is tajweed-gated — asserted as the shipped exemption (ledger row D7).** REQ-008.4 / the task text says step 16 asserts "progress incremented", but the shipped `incrementForConfirmedSession` returns BEFORE any write for non-tajweed intents (`backend/services/classes/student-progress.service.ts:282-284` — Hifz tracking does not exist yet), and even the tajweed path would no-op here (S holds a Hifz-lane subscription, no curriculum). Step 16 therefore asserts the honest shipped end state — ZERO `progress` rows for the student — and ledger row D7 records the pointer. **Task 1.7's step-30 end-state table must NOT expect a progress row.**
2. **The lifecycle namespace spy is installed PER STEP, not suite-wide.** D6's letter (and its `session-lifecycle.journey.test.ts:250-263` precedent) installs `spyOn(NotificationEngine, "publishReceipts")` once in `beforeAll`. That is unsound in THIS suite: the optioned services (settlement, link, and 1.5's report submit) publish through the SAME namespace member with their injected transport — a standing spy would intercept those calls and the spied transport would record nothing, breaking steps 6/9/10 retroactively and 1.5's report waves prospectively. The seam is therefore installed fresh around each lifecycle call (`try/finally`, restored in-step) via `spyLifecyclePublication()`; each step's spy starts at zero so the publish assertions are step-local. This is the pattern 1.6's lifecycle steps must reuse.
3. **`afterAll` gained the teacher-ledger sweep NOW** (the plan letter assigns "afterAll HARDENING" to task 1.7) — the same lean 1.2 precedent: this leg is the first to commit rows `tracked.cleanup()` alone cannot delete (`teacher_transaction` is DELETE-blocked by the immutability trigger AND restrict-deletes the tracked wallet row). The sweep deletes by `ledgerWalletId` and re-probes zero; 1.6's sessions B/C credit the SAME wallet, so no further teardown vocabulary is needed for them. The audit-row suspension stays with 1.6/1.7 exactly as planned.
