## E. Census Design Notes (for reviewers)

- **Why the bijection scans ANY `.delete(`, not just retention identifiers:** the task text's allowlist contains two files whose deletes target NON-retention tables (`lessons`, `notifications`) — under a retention-identifier-only scan those entries would be dead. The intended semantics (per research-01 rec 3 + the allowlist wording) is the conservative one: within these three surfaces, every hard-delete callsite must be consciously allowlisted, so a *new* delete path against any table trips the census. The retention-targeted scanner is the absolute zero on top (no allowlist can cover it).
- **Corpus hygiene:** `node_modules`, `test`, `__tests__` directories and `.test.ts`/`.test.tsx`/`.spec.ts`/`.spec.tsx` files are excluded — cron route tests and `scripts/ops/*.test.ts` are rollback-contained/run-and-record code, mirroring the audit census's test-layer exclusions.
- **Determinism:** `localeCompare`-sorted traversal at read time; repeated runs are byte-stable.
- **Lexical caveat (accepted, same as audit census):** text-level scans flag occurrences inside comments/strings and JS collection `.delete()` uses (e.g. `Map.delete()`); false positives are visible and cheap, false negatives require obfuscated code that fails review anyway.
