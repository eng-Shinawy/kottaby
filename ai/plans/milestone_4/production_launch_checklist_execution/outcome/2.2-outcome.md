2. **Soft-delete (Admin):** real `setUserDeleted(target, true)` → guarded UPDATE (`is_deleted=true`, `deleted_at` set) + exactly ONE `Delete` audit row with the pinned zero-PII details contract `{deleted: true}`; the matrix's idempotency column is pinned too — a re-delete request is a typed `ConflictError` (`USER_ALREADY_DELETED`, translated substring) with zero writes and zero new audit.

4. **Login denial (Student):** `AuthService.login` → `ForbiddenError` with the AUTH-namespace translated substring (`accountBlocked`) at the real governance gate; zero writes (users row byte-stable, no new audit, silent).
5. **Hard-delete probe (System, PG tier):** inside its own transaction the guard GUC is re-armed transaction-locally (`set_config('kottaby.users_delete_guard','on',true)` — auto-reverts at transaction end, never leaks to the pooled connection, so the teardown DELETEs keep their inherited opt-out), and a direct `DELETE FROM users` on the fixture family is bracketed in its own SAVEPOINT via the shared `probeInsideSavepoint`. **Environment-branched exactly as mandated:** with the trigger live (this migrate-provisioned DB — verified `tgenabled='O'` before the run) the leg asserts the trigger RAISE (`expectTriggerRaise`, `"users is not hard-deletable"`); on push-provisioned DBs (trigger absent, or installed-but-disabled — the 2.1 §F hazard is baked into the predicate: `tgenabled` 'O'/'A' + BEFORE + row-level + DELETE) the leg asserts the FK-RESTRICT failure class (SQLSTATE 23503; the family's session + payment restrict FKs make the deletion impossible either way). Row survives byte-identically either way.
6. **BFLA denial (Control student):** the honest `student`-role cast member probes the admin READ surface (`getUserDetail`) and the admin MUTATION surface (`setUserDeleted`) on the governed user → both `ForbiddenError` with the translated `forbidden` substring through the real `assertActorAdmin` gate; zero writes, zero audit from either denial, target row byte-identical.
7. **Reactivate (Admin):** `deleted_at=null` + exactly ONE `Reactivate` audit row (`{deleted: false}`) + login restored through the real credential path.
8. **Teacher variant (Admin):** soft-delete the teacher → the earning ledger row, wallet, and the session it is anchored on survive byte-identically; reactivate flips the guarded UPDATE back (Delete + Reactivate audit rows for the teacher; terminal admin audit ledger = exactly 5 rows).

Cross-actor visibility is asserted BOTH directions throughout: the control tenant's users/student/session/report/payment rows are byte-compared after every leg, and every step asserts ZERO fan-out publishes at the spied `NotificationEngine.publishReceipts` boundary (the plan's side-effect matrix: the governance arc is silent) with the spy restored in `afterAll`.
