## Harness Recommendations

The launch ticket is a verification/orchestration ticket, not a feature ticket. Its plan should:

1. **Treat the precondition honestly.** The plan's Task 1 should be a dependency audit producing the mapping table above. Rows 1, 4, 6, 7 (student journey, security hardening, state-machine sweep, load testing) are not done — either the launch plan gates on their owning tickets, or it explicitly in-scope-folds the residual verification (recommended for: student-journey chain, security battery — both are test-layer work matching the journey harness; NOT recommended for load testing, which needs new tooling and its own 8-SP ticket).
2. **Student-journey chain** (if folded in): one file `test/workflows/students/student-full-journey.journey.test.ts` following `test/workflows/AGENTS.md` (committed fixtures, actor-context cast, tracked cleanup, SpiedFanoutTransport for the parent notification) — composable from existing legs: registration (`registration-phone.journey.test.ts` pattern), purchase+settle+debit (`subscription-full-lifecycle.journey.test.ts` steps 2-5), dual-confirm+wallet credit (`financial-safety-verification.journey.test.ts` step C), parent notification assertion via spy (parent-full-journey pattern).
3. **Security battery** (if folded in): extend `backend/lib/errors/test/` + GraphQL integration layer — (a) SQLi/XSS documents against real resolvers in `backend/graphql/test/` asserting rejection with zero writes, (b) auth rate-limit middleware + tests (the `RateLimitExceededError` + limiter namespace pattern already exists at `backend/lib/gateway/cron-endpoint.ts:73` — reuse it for login/reset), (c) CSRF: document SameSite=Strict as the chosen mechanism and pin it with a cookie-contract test next to `test/config/security-headers.test.ts` (a `test/config/` home fits repo layout).
4. **State-machine sweep:** do NOT duplicate — the sibling ticket's parallel wave (`ai/plans/milestone_4/state_machine_invariant_verification/`) owns it. The launch plan should only add a thin "INV matrix runner" report step that greps/counts which INV rows have a green suite, consuming `docs/specs/state-machine-invariants.md` as the row source. Flip stale row 5.3.3 (INV-B3) using `subscription-expiry.journey.test.ts`.
5. **Section 8 (33 decisions) verification:** schema-level probes belong in `backend/db/test/logic/` (existing precedents: `handshake-code-immutability-scan.test.ts`, `audit-census-drift.test.ts`) — a single `backend/db/test/logic/decisions/decision-census.test.ts` that imports `backend/db/schema/*` and asserts each A.x/B.x/C.x structural decision (columns, enums, FKs, unique constraints) keeps the launch ticket from hand-running 33 SQL probes.
6. **Load testing:** recommend keeping it as its own ticket (8 SP, new tooling — autocannon/k6 under `scripts/load/`, results under `docs/ops/`) and having the launch checklist cite its report; if launch must proceed without it, record an explicit descope decision in the plan's deferred-items ledger with named targets from Section 6.
7. **Section 1.1/1.4 soft-delete + retention probes:** extend the existing admin journeys (`test/workflows/admin/admin-user-lifecycle.journey.test.ts`, `account-governance.journey.test.ts`) with hard-delete denial probes and a static "no purge jobs" scan (mirroring `audit-immutability.test.ts`'s static corpus pattern).
8. **Run location discipline:** journey/integration verification → `test/workflows/<domain>/`; static census/drift → `backend/db/test/logic/`; ops verification → `scripts/ops/` + `docs/ops/`; all runs logged via `bun run test/scripts/run-test.ts <path>`.
