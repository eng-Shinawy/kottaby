```ts
export type LaunchStage = "s1-data-integrity" | "s2-financial" | "s3-realtime" | "s4-security"
  | "s5-invariants" | "s6-performance" | "s7-dr" | "s8-decisions" | "s9-gate";

export type LaunchModality = "AUTOMATED-TEST" | "SCRIPT-PROBE" | "MANUAL-DRILL" | "DOC-SIGNOFF";

export type RowDisposition = "PASS" | "WAIVED" | "FAIL";

export interface LaunchGateState { stage: LaunchStage; owner: "launch-gate";
  lifecycle: "FRESH" | "IN_PROGRESS" | "DONE"; lastRun: string; }   // ISO string

export interface LaunchRow { readonly rowId: string; readonly section: 1|2|3|4|5|6|7|8|9;
  readonly modality: LaunchModality; readonly command: string; readonly evidenceRef: string;
  readonly waiver?: { readonly why: string; readonly owner: string }; }

export interface LaunchReportRow { readonly rowId: string; readonly section: 1|2|3|4|5|6|7|8|9;
  readonly modality: LaunchModality; readonly command: string; readonly exitStatus: number;
  readonly result: RowDisposition; readonly evidenceRef: string; readonly timestamp: string; }

export interface StageResult { readonly stage: LaunchStage; readonly status: "PASS" | "FAIL";
  readonly startedAt: string; readonly finishedAt: string; }          // ISO strings

export interface ProbeLine { readonly rowId: string; readonly result: "PASS" | "FAIL"; readonly detail: string; }
```

## F. Carry-Forward Knowledge for Tasks 1.2–1.6

1. **`LaunchRow` lives HERE, not in `launch-checklist.ts`.** Task 1.1 (authority) exports `LaunchRow` from `launch-types.ts`. Plan C2's prose ("`launch-checklist.ts` … `export interface LaunchRow`") describes the registry's consumption, not a second declaration — **task 1.2 must `import type { LaunchRow, LaunchStage, LaunchModality } from "@/scripts/launch/shared/launch-types"` and NOT re-declare the interface**, or the duplicates gate (cross-file clone) will fire and the canonical-type rule is violated.
2. **`STAGES` (the ordered `LaunchStage` array) is task 1.2's export** — it lives in `launch-checklist.ts` beside the row registry, NOT in the type module (task 1.1 mandates no constants here). It must list the nine `LaunchStage` literals in the literal-order documented in the type (s1…s9); the `LaunchStage` docblock already points consumers at it.
3. **Report serializer (1.3) derives its D7 redaction allowlist from `LaunchReportRow` + `StageResult` field names** — exactly `rowId, section, modality, command, exitStatus, result, evidenceRef, timestamp` (rows), `stage, status, startedAt, finishedAt` (stages), plus the report-envelope fields (`verdict`, `generatedAt`, `waivers`). No other fields may be serialized.
4. **`LaunchGateState.owner` is the literal `"launch-gate"`** — matches the `withProcessLock("launch-gate", …)` description that 1.4 uses; `lifecycle` is `"FRESH" | "IN_PROGRESS" | "DONE"` (note: differs from quality-gate's `NEED_CONFIRM` — no confirmation stage in the launch gate). State trusts the stage index over the lifecycle label (a stale `DONE` on a non-`s9-gate` stage is resumable — plan §6.1).
5. **`StageResult.status` is strictly `"PASS" | "FAIL"`** — do not widen it to `RowDisposition`; waivers are per-row and the report carries them in the separate `waivers` array with `signatory` (collected at human sign-off, task 4.5 — NOT part of `LaunchRow.waiver`, which carries only `{why, owner}`).
6. **`ProbeLine.result` is strictly `"PASS" | "FAIL"`** — probes (1.5) never emit `WAIVED`; unreachable checks are named FAIL lines, never silent skips.
7. **`LaunchReportRow.exitStatus: number`** — evidence-existence rows (MANUAL-DRILL/DOC-SIGNOFF) write `0`; spawn-signal exits should be normalized by the gate (1.4), not by widening this type.
8. **Timestamps (`lastRun`, `timestamp`, `startedAt`, `finishedAt`) are ISO-8601 strings** — same convention as `.quality-gate-state.json` and the ops restore reports.
