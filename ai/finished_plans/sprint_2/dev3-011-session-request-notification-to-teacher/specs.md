## 1. Executive Summary & Problem Statement

- **Feature:** The canonical, test-locked notification module for the on-demand session-request lifecycle. Whenever the (future, DEV3-004) session engine records that a student requested a session with a teacher, a `session_request` notification is persisted for the teacher and pushed in real time; on the outcome wave (accepted / declined / preference-routed auto-reject / queued / alternatives-offered), the student receives the corresponding notification. All emission flows exclusively through the shipped `NotificationEngine` single-writer contract — persist-first, publish-after-commit, recipient-locale copy composed at the emitter.
- **Problem from user perspective:**
  - **Certified Sheikh (recipient):** must SEE instantly that a specific student requested a session with a given intent (Hifz/Tajweed), in HIS OWN locale; today the notification type exists (`NotificationType.SessionRequest`, `backend/enum/notifications/notification-type.enum.ts:6`) and the delivery engine exists, but NO emitter can ever produce that wave — the platform would run silently.
  - **Student (producer of the request, recipient of the outcome):** must learn the outcome of his request (accepted / declined / queued / auto-rejected / alternatives) as a durable, localized inbox row — not as silence.
  - **DEV3-004 / DEV2-011 / DEV3-008 (downstream engine owners):** need ONE canonical emitter module with frozen key/entity/idempotency conventions; without it, each engine ticket re-invents copy composition, locale routing, and publish choreography.
- **Business value:** FR-4.5 and FR-9.1 (real-time session-request notifications) are launch-gate features; Workflow 02 §4's request→notify→accept/decline sequence has NO implementation without this wave. This ticket converts the notifications engine from infrastructure into the first business-meaningful emission, and it is the FIRST full consumer of the DEV2-003 `SessionEventNotificationContract`.
- **Actors involved:** Student (request producer; outcome recipient) · Certified Sheikh (request recipient) · System (future session engine — caller of the module; in this ticket, journeys invoke the emitters directly per the sanctioned fixture-level pattern) · NotificationEngine / WS sidecar (delivery substrate, consume-only).
- **Non-goals (explicitly OUT of scope):**
  - NO session-request creation mutation, NO accept/decline mutations, NO session state transitions — those are DEV3-004/DEV3-005 (request intake + lifecycle state machine). This ticket performs ZERO `session` writes; it READS committed session rows and emits.
  - NO B.16 preference RESOLUTION logic (detecting in-session state and choosing queue vs reject vs alternatives) — the engine owns the routing decision; this ticket owns the three wave emitters the router calls. No queue storage (no pending-request entity exists), no alternative-teacher computation (DEV3-008).
  - NO new GraphQL root field, NO new Pothos type/input, NO SDL change of any kind; NO patch to the public-operation allowlist (frozen six).
  - NO new frontend surface: recipients consume the wave through the ALREADY-SHIPPED inbox drawer / badge / realtime toast (DEV3-010), whose type label `typeSessionRequest` already exists (`shared/locale/en/notifications/index.ts:11`, `ar`:11). No actionable accept/decline CTA inside the notification row (the engine's realtime payload allowlist is closed; CTA metadata would be an engine change — forbidden here; forward item).
  - NO schema changes of any kind (`session`, `teacher`, `users`, `notifications` all sufficient as-is; `git diff backend/db/schema/**` MUST be empty).
  - NO changes to the engine (`emitForUser`/`emitForUsers`/`publishReceipts`, transports, sidecar, payload projection) — consumed verbatim.
  - NO parent-side session notifications (INV-P3 emitters are DEV1-017), NO evaluation-result / payment / cancellation emitters (DEV2-016/017, DEV3-012/013 lineage).
