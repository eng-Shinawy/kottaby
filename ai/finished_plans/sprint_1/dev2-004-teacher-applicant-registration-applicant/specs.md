# Requirements & Specification: DEV2-004 — Teacher Applicant Registration & Applicants Table

> **Date**: Sprint 1, Week 3
> **Target Ticket**: DEV2-004 — Teacher Applicant Registration & Applicants Table
> **Plan directory**: `ai/plans/dev2-004-teacher-applicant-registration/`
> **Blocking dependencies**: DEV1-001 (`applicants` table, `user_role` enum), DEV1-002 (public `registerUser` contract — teacher branch ALREADY creates `applicants` row, never `teacher`), DEV2-002 (`role` authScope, canonical 401/403 contract, `requireRoleForPage`).
> **Critical design note**: Per the Existing Codebase State rule and the DEV1-002 canonical reference (`docs/auth/user-registration.md` §1, §5), **the applicant-registration write path is already implemented** (role=teacher → `applicants` row with `status='pending'`, `verification_attempts=0`, `last_attempt_at=NULL`, `cooldown_until=NULL`; NO `teacher` row; `CreateRoleChild` dispatch inside the registration transaction). DEV2-004 SHALL NOT re-plan or rebuild that path. This ticket's net-new scope is: (a) permanent invariant tests locking the registration→applicants contract, (b) the canonical applicant lifecycle vocabulary (`ApplicantStatus` value set over the existing `varchar(50)` column — NO DB enum, NO schema change), (c) the applicant self-service status surface (`myApplicantProfile`), and (d) the cooldown/re-application eligibility contract consumed by DEV2-005 (verification plan purchase). Any schema gap discovered is escalated via `deferred-items.md`, never patched inline.

## 1. Executive Summary & Problem Statement

**Feature:** Deliver the complete teacher-applicant lifecycle substrate: verify and permanently lock the DEV1-002 registration contract (teacher → `applicants` row, never `teacher`), define the canonical applicant status state vocabulary (`pending → in_evaluation → passed|failed` with cooldown semantics), expose an authenticated self-service applicant status query, and ship the cooldown-eligibility guard contract that gates verification-plan re-purchase in DEV2-005.

**Problem from user perspective:**

- **Teacher Applicant (Ibrahim):** registers as a teacher, must see a truthful "you are an applicant, pending evaluation" status — never a certified-teacher experience. After a failure, he must know exactly when his cooldown expires and that re-application is then permitted (and that re-applying increments his recorded attempt count).
- **Certified Sheikh / Platform integrity:** no applicant may hold a `teacher` row, appear teachable, or be granted any teaching surface before passing verification (B.7, FR-3.1, INV-TV1).
- **Super Admin:** future override surfaces (DEV2-010) require the applicant record (`status`, `verification_attempts`, `cooldown_until`) to be persisted accurately from day one.
- **Dev 2 (owner) / DEV2-005/006/007 (consumers):** need a single authoritative status enum, cooldown math, and attempt-tracking repo methods — not per-ticket re-derivation.
- **Dev 1 / Dev 3:** registration flows (DEV3-019 direct onboarding) and matching (teachers only, never applicants) depend on this boundary holding.

**Business value:** The applicant lifecycle is the quality-gatekeeping foundation of the platform's core promise (uncompromising teacher quality — `docs/architecture/architecture-overview.md` §1). Shipping the permanent contract tests now prevents silent regressions where a later ticket accidentally creates `teacher` rows at registration (catastrophic for INV-TV1) or lets cooldown-expired applicants be double-tracked. The `myApplicantProfile` surface is also the visible deliverable for the M1 gate ("applicant can register, purchase verification plan, complete evaluation loop — and see where they are in it").

**Actors involved:**

- **Teacher Applicant (caller):** registration (existing public surface), status inspection (new authenticated surface).
- **Super Admin (privileged caller):** reads applicant state laterally (DEV3-016 era); no new admin mutation here.
- **DEV2-005 (verification plan purchase):** consumes the cooldown eligibility guard and attempt-increment repo contract.
- **DEV2-006/007 (evaluation loop/aggregation):** consume status transition semantics (`in_evaluation`, `passed`, `failed` writes) via their own tickets.
- **Matching engine (DEV3-008):** structurally guaranteed applicants never enter the teacher directory (no `teacher` row ⇒ no wallet, no `subjects`, no availability).

**Non-goals (explicitly OUT of scope):**

- No schema changes: `applicants` table, indexes, and the `status varchar(50)` column are DEV1-001-owned. `ApplicantStatus` is a TypeScript enum over the varchar (precedent: DEV1-001 documents status as a varchar with a canonical value set). No `pgEnum` addition, no `db push`.
- No verification plan purchase implementation (DEV2-005 owns purchase; this ticket ships only the cooldown guard + attempt-increment contract it must call).
- No evaluation session booking (DEV2-006), scoring/aggregation into `passed`/`failed` (DEV2-007), failed→student conversion (DEV2-009), or admin override (DEV2-010).
- No changes to the public `registerUser` mutation surface, input whitelist, or `RegisterPublicRole` enum (DEV1-002 baseline is frozen).
- No teacher availability/subjects/is_online flow (DEV2-011+).
- No notifications (DEV3-010 owns dispatch).
- No admin CRUD over `applicants` (DEV3-016 era).

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (Registration Contract — Locked, Not Rebuilt)**: WHEN the permanent verification suite for this ticket runs THEN it SHALL assert that `registerUser` with `role = teacher` creates EXACTLY ONE `users` row AND exactly one `applicants` row sharing the user's PK, AND creates ZERO rows in `teacher`, within one atomic transaction (per DEV1-002 REQ-010/REQ-013/REQ-030). The implementation SHALL NOT modify the registration write path unless a defect is proven by these very tests.
- **REQ-011 (Applicant Row Defaults)**: WHEN a teacher registration completes THEN the `applicants` row SHALL have `status = 'pending'`, `verification_attempts = ` nullish-zero default `0`, `last_attempt_at = NULL`, `cooldown_until = NULL`, `created_at`/`updated_at` set by database defaults (per B.6 signature and the Drizzle schema in `backend/db/schema/`).
- **REQ-012 (ApplicantStatus Canonical Vocabulary)**: WHEN any layer reasons about applicant status THEN the value SHALL come from a new canonical TypeScript enum `ApplicantStatus` defined in `backend/enum/teachers/applicant-status.enum.ts` with EXACTLY the members `Pending = "pending"`, `InEvaluation = "in_evaluation"`, `Failed = "failed"`, `Passed = "passed"` (matching the canonical value set recorded for `applicants.status` by DEV1-001), plus a type guard `isApplicantStatus(value: unknown): value is ApplicantStatus`; the enum SHALL be re-exported from `backend/enum/teachers/index.ts` (and via the top-level barrel). NO raw string literals for status SHALL appear anywhere outside this file and its tests. NO `pgEnum`/DB migration: the column remains `varchar(50)` — structurally enforced by the "no schema drift" rule.
- **REQ-013 (Status State Machine Semantics — Contract)**: WHEN applicant status is written by any future flow THEN transitions SHALL follow: `pending → in_evaluation` (verification plan purchase — DEV2-005), `in_evaluation → passed | failed` (aggregation — DEV2-007), `failed → in_evaluation` (re-purchase after cooldown — DEV2-005 with this ticket's guard), `pending|in_evaluation|failed` are terminally readable; `passed → teacher row exists` (DEV2-007 writes, not this ticket). This state vocabulary SHALL be documented in the canonical doc (REQ-080) as binding on the Sprint-1 DEV2-005..DEV2-010 chain.
- **REQ-014 (Attempt Counter Contract)**: WHEN DEV2-005 needs to record a (re-)application THEN the repository SHALL expose `ApplicantRepository.recordVerificationAttempt(userId: number, tx?: DBTransaction)` executing a single atomic `UPDATE applicants SET verification_attempts = verification_attempts + 1, last_attempt_at = now() WHERE id = @id RETURNING *` (in-place increment, parameterized — NO SELECT-then-UPDATE read-modify-write), and the service contract `ApplicantLifecycleService.recordReapplication(userId, locale, tx?)` SHALL wrap it with failure-surfacing (NotFoundError if zero rows returned) and `logger.logDomainError` on domain rejections only.
- **REQ-015 (Cooldown State Contract)**: WHEN any layer evaluates whether an applicant may (re-)purchase a verification plan THEN the determination SHALL come exclusively from `applicants.cooldown_until` (INV-TV3 authoritative source): cooldown is active IF AND ONLY IF `cooldown_until IS NOT NULL AND cooldown_until > now()`; an expired or NULL cooldown permits purchase. The guard `ApplicantLifecycleService.assertCanPurchaseVerification(userId, locale, tx?)` SHALL throw `ValidationError` with a custom code (`APPLICANT_COOLDOWN_ACTIVE`) + localized message interpolating the expiry timestamp when blocked, and SHALL be a no-op otherwise. (Purchase execution itself is DEV2-005's scope; this ticket ships the guard + tests.)
- **REQ-016 (User-Level Suspension Bridge — Documented)**: The ticket-acceptance "failed applicant has cooldown_until set AND users.suspended applies" (INV-U2, Workflow 01) SHALL be documented as a two-source contract: re-purchase gating is ALWAYS read from `applicants.cooldown_until`; login/session-class gating is read from `users.suspended` governance fields (DEV2-001/DEV2-002 domain). DEV2-004 SHALL NOT write either of those user-governance fields (a failed-evaluation writer is DEV2-007/DEV2-008 scope); this ticket locks the read semantics only.
- **REQ-017 (My Applicant Profile Surface)**: WHEN an authenticated caller whose `users.role = teacher` calls the new `myApplicantProfile` query THEN the system SHALL return `ApplicantProfileReturnType` — `{ id, status (ApplicantStatus), verificationAttempts, lastAttemptAt, cooldownUntil, cooldownActive, canPurchaseVerification }` — resolved from the caller's `ctx.user.id` with server-computed booleans (`cooldownActive`, `canPurchaseVerification` evaluated against `now()` server-side). IF the caller's user has a `teacher` row (certified) or a governance-blocked/deleted account THEN the query SHALL resolve according to the documented precedence: governed accounts never reach the resolver (DEV2-002 fail-closed context); a certified teacher returns `null` (no active applicant file) — which the client renders as the "certified" state, never as an applicant state.
- **REQ-018 (Status Display Truthfulness)**: WHEN the frontend renders the applicant status dashboard card THEN a `Pending` applicant SHALL see translated pending copy, `InEvaluation` SHALL see in-evaluation copy with attempt count, `Failed` + active cooldown SHALL see the cooldown expiry date, `Failed` + expired cooldown SHALL see the re-application eligibility affordance, and at NO point SHALL an applicant see teacher-certified-only affordances (INV-TV1 honesty; UI evidence of B.7).

### 2.3 Security, Authorization & Tenancy

- **REQ-030 (BOLA / IDOR — Identity From Context Only)**: WHEN ANY applicant-read or lifecycle method executes THEN the target applicant SHALL be derived exclusively from the server-verified caller identity (`ctx.user.id`); the `myApplicantProfile` query SHALL accept ZERO arguments (no `userId`/`id` input may exist in the operation contract); a parent/student/admin caller attempting to read another user's applicant file has no parameter surface to attempt it.
- **REQ-031 (BFLA — Role Gate)**: WHEN `myApplicantProfile` is invoked THEN the Pothos `authScopes` SHALL be `{ role: [UserRole.Teacher] }` (Runtime RBAC from DEV2-002: unauthenticated → `UNAUTHORIZED` 401 semantics; authenticated non-teacher (`student`/`parent`/`admin`) → `FORBIDDEN` 403 semantics with the canonical localized deny). The query SHALL sit in the authenticated (NOT public) surface; it SHALL NOT grant any write path.
- **REQ-032 (BOPLA — No Write Surface)**: WHEN this ticket ships THEN there SHALL be NO mutation accepting applicant fields (`status`, `verificationAttempts`, `cooldownUntil`) from any client; all status/attempt writes are server-internal (`recordVerificationAttempt`, future aggregation). Closed `readonly` input/output shapes; no `{ ...input }` spread into any Drizzle call anywhere.
- **REQ-033 (No Privilege Escalation via Applicant State)**: WHEN any applicant-state change occurs THEN it SHALL NOT affect `teacher.is_approved`, `is_evaluator`, `is_online`, `subjects`, or `request_preference`; a `teacher` row exists only if DEV2-007/DEV2-008 or DEV3-018 (admin cold-start) creates it. The certification boundary (role≠certification, DEV2-002 REQ-023) is structurally preserved: nothing in this ticket can mint a teacher.
- **REQ-034 (Rate Limiting — Unchanged)**: WHEN the new authenticated query is called THEN no NEW rate-limit surface is added beyond the existing authenticated posture; the public `registerUser` rate-limit pattern (fail-open stub per DEV1-002/DEV1-003) remains entirely untouched.
- **REQ-035 (No Oracles in Deny)**: WHEN access to an applicant file is denied (role mismatch, governed account) THEN the response SHALL be the canonical localized deny — it SHALL NOT disclose whether the target user exists, whether an `applicants` row exists for them, or any owner-specific state (aligned with DEV3-002 error-oracle rules and DEV1-002 no-account-oracle pattern).

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (Registration Atomicity Is Inherited, Not Re-Opened)**: WHEN registration runs THEN the user + applicants inserts SHALL stay inside the existing DEV1-002 `withTransaction(outerTx)` (SAVEPOINT-aware) transaction; this ticket SHALL NOT refactor those transaction boundaries — it only locks them with tests proving zero residual rows on forced child-insert failure.
- **REQ-041 (tx Propagation)**: WHEN any repository method participates in this ticket's code THEN every repository/service call inside a transaction SHALL receive the same `tx` (optional `tx?: DBTransaction` as the last parameter per repo conventions); mixing `tx` writes with global-`db` reads inside flows is PROHIBITED.
- **REQ-042 (Attempt-Increment TOCTOU Elimination)**: WHEN `recordVerificationAttempt` executes THEN the increment SHALL be the single statement in REQ-014 (no read-then-write; the `verification_attempts` column value is NEVER first read into memory and incremented in the application); `RETURNING *` provides the row for audit/log use.
- **REQ-043 (Cooldown Evaluation Is Pure Read-Compute)**: WHEN `assertCanPurchaseVerification`/profile shaping executes THEN the logic SHALL be a single read followed by pure computation against a captured `now` — no write, no lock needed; concurrent re-purchase attempts at timestamp boundaries are resolved by DEV2-005's transactional purchase flow (this ticket's guard is advisory-at-its-isolation-level and documented as such in the canonical doc).
- **REQ-044 (No Prepared Statements for Writes / Reads follow repo rules)**: WHEN the writes in REQ-014 and the reads in REQ-017 are authored THEN no `sql.placeholder` prepared statements SHALL be used for the write (writes are out of prepared scope per `docs/drizzle/prepared-statements.md`); the single-PK read path MAY use the existing `queryDb(tx)` Neon-HTTP pattern only if `ApplicantRepository` already presents such a method to extend — otherwise a plain parameterized query is used; NO `inArray` + prepared combination anywhere.
- **REQ-045 (Schema Drift Prohibition)**: WHEN implementation completes THEN `git diff` for `backend/db/schema/**` and `backend/db/migration/**` SHALL be EMPTY for this ticket. (The `ApplicantStatus` TS enum deliberately has no `pgEnum` counterpart; the varchar value-set contract is documented in this plan.)

### 2.5 Validation & Error Contracts

- **REQ-050 (DomainError Discipline)**: WHEN any failure surfaces from this ticket's code THEN it SHALL be a `DomainError` subclass propagated with `extensions.code` per `docs/graphql/domain-error-extensions-code.md`: `NotFoundError` (`APPLICANT_NOT_FOUND`) when no applicant file exists for a certified/governed edge, `ValidationError` with custom code `APPLICANT_COOLDOWN_ACTIVE` when REQ-015 blocks, and the canonical `FORBIDDEN`/`UNAUTHORIZED` codes from the DEV2-002 authScope layer. Plain `new Error(...)` is PROHIBITED.
- **REQ-051 (Localized-Only Messages)**: WHEN any message is produced THEN it SHALL resolve through compile-time i18n. New keys (in the EXISTING `errors` namespace plus a NEW `applicant` namespace where display labels are needed) SHALL be registered in `shared/locale/types/**` + BOTH `ar` and `en` implementations (and namespace registration per `shared/locale/AGENTS.md`/`shared/AGENTS.md` if a new namespace is introduced); hardcoded or `console.*`-logged strings are PROHIBITED.
- **REQ-052 (Expected-Rejection Logging)**: WHEN cooldown blocks or domain rejections fire THEN logging SHALL use `logger.logDomainError` (debug under `TEST_SERVER=1`, warn in production — never `console.*`), carrying structured context (`entity: "applicants"`, the user id, and the relevant code) without PII-heavy payloads.
- **REQ-053 (Silent-Path Prohibition for the Happy Path)**: WHEN a pending applicant with no cooldown views their profile or a valid re-application attempt proceeds THEN no error, warning, or swallowed `try/catch` SHALL be emitted — the flow is a first-class contract, not a suppressed side effect.
