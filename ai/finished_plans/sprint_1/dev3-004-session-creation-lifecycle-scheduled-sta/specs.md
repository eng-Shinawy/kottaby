## 1. Executive Summary & Problem Statement

- **Feature**: The P2P session lifecycle vertical: a student books an instant session with a certified Sheikh (one allowance unit is held atomically, the fee and 24h confirmation deadline are platform-set), the Sheikh starts and completes the session, either party can cancel with automatic hold release, and every transition is a guarded single SQL statement governed by the session state machine. Two participant-scoped list queries and one oracle-safe detail query feed two minimal dashboard pages (`/student/sessions`, `/teacher/sessions`). The surface is the substrate DEV3-005 (state-machine enforcement), DEV3-006 (reports), DEV3-011 (notifications), and DEV3-012/013 (dual confirmation + wallet escrow) build on.
- **Problem from user perspective**:
  - **Student (Yusuf)**: with a credited balance (or his free trial), he must be able to book a certified teacher *now*; his allowance must be held exactly once per booking (never double-spent), and a cancelled session must return his unit immediately and provably.
  - **Certified Sheikh (Abdullah)**: he sees sessions addressed to him, starts them, and completes them — with the certification gate re-verified at completion, so a decertified teacher can never push a session toward payout.
  - **Teacher Applicant (Ibrahim)**: holds `role=teacher` but no `teacher` row — must find zero session surface (INV-TV1: no shortcut around verification).
  - **Parent (Fatima) / Anonymous**: no surface whatsoever; session existence between a student and teacher is private (sessions get the OPPOSITE oracle ruling from the non-sensitive plan catalog — REQ-030).
  - **Super Admin**: governance over sessions (filter/reschedule/cancel/reassign) is DEV3-021; this ticket grants admins nothing.
  - **Dev 3 downstream (DEV3-005/006/011/012/013)**: needs the state machine, guarded transitions, hold semantics, and the idempotent creation contract to exist EXACTLY once — never re-implemented.
- **Business value**: Sessions are the product's core transaction and the escrow anchor (B.2/B.3/B.4). The guarded-transition + guarded-debit pair makes double-spending an allowance and double-charging a lifecycle structurally impossible, which is the property DEV3-025 (financial safety verification) will later prove in load. The M1 gate ("Student can subscribe & book") requires this slice.
- **Actors involved**: Student (creator, participant, canceller), Certified Teacher (participant: start/complete/cancel), denial actors (applicant/other students/other teachers/parent/admin/anonymous), System (state machine + idempotency enforcement). Downstream consumers: DEV3-005, DEV3-006, DEV3-011, DEV3-012, DEV3-013, DEV3-021, DEV2-016.
- **Non-goals** (explicitly OUT of scope):
  1. **Dual-confirmation student confirm + 24h auto-cancel sweeper** — DEV3-012. `confirmed_by_student_at` is never written here.
  2. **Wallet crediting / `teacher_transaction` writes / balance finalize-on-confirm** — DEV3-013/014. This ticket writes ZERO financial-ledger rows (INV-S3/INV-W4 hold by absence).
  3. **In-session availability lock (`teacher.is_online=false` on start) and 15-minute inactivity** — DEV2-011/012/013 + DEV3-005 (INV-S6).
  4. **Session reports / homework / recitation rows** — DEV3-006/DEV3-007/DEV2-014 (INV-S7/S8 report gating is DEV3-005).
  5. **Session request notifications** (A.4 consumption) — DEV3-010/011 (deferred D1).
  6. **On-demand matching, directory browse, subject/language/country filtering, queueing (B.16)** — DEV3-008/009 (deferred D3/D4).
  7. **`disputed` state and admin arbitration** (B.18) — DEV3-022; no path to `disputed` exists in this ticket.
  8. **Admin session governance surface** — DEV3-021 (admins get nothing here, including on `sessionById`).
  9. **Evaluation/re-evaluation sessions** (`session_type = teacher_evaluation`/`re_evaluation`, `intent = evaluation`) — DEV2-006; `createSession` ACCEPTS Hifz/Tajweed only.
  10. **Any schema change to existing tables beyond the two documented deltas** (REQ-013).

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (Session Creation — Contract Defaults)**: WHEN an authenticated student (role `student`, governance-clean context) invokes `createSession({ teacherId, intent })` with a valid idempotency key and a certified teacher target THEN the system SHALL insert ONE `session` row inside one transaction with: `status = 'scheduled'` (DB default, never client-set), `sessionType = SessionType.StudentSession`, `intent ∈ { SessionIntent.Hifz, SessionIntent.Tajweed }`, `studentId = ctx.user.id` (shared PK), `teacherId` = the locked target teacher, `fee` = the platform constant for the intent (REQ-021), `feeHeld = true`, `confirmationDeadline = <captured now> + 24h`, all other timestamps server-set. The inserted shape SHALL satisfy `SessionRequestContract`'s structural invariants (`feeHeld: true` literal, non-null fee/deadline, idempotency key present) — statically asserted.
- **REQ-011 (Certification Gate — INV-S5, TOCTOU-Free)**: WHEN the creation transaction executes THEN it SHALL FIRST `SELECT … FOR UPDATE` the target `teacher` row (locking it for the transaction) and SHALL throw `TEACHER_NOT_CERTIFIED` if the row exists with `isApproved = false`, or `TEACHER_NOT_FOUND` if no `teacher` row exists (an applicant's `users.id` is NOT a teachable id — INV-TV1); the check and the later insert SHALL share the transaction so a concurrent certification flip cannot slip between check and write. ~~Teacher-role callers (`role=teacher`) MAY create a session as the STUDENT side only if they hold a `students` row (failed-applicant conversion, INV-TV6); otherwise they are FORBIDDEN by the role scope.~~ **Ruling (2026-08-30, orchestrator): STRUCK — teachers are unconditionally FORBIDDEN from `createSession` in this slice.** The static `role:[UserRole.Student]` scope of REQ-032 stands unchanged (repo ground truth: `backend/graphql/pothos/builder.ts:127` is a pure `ctx.role` membership check and cannot express a students-row carve-out). INV-TV6's honest-denial intent is preserved: applicant teachers (no `teacher` row — INV-TV1) and certified teachers alike receive the honest role-scope `FORBIDDEN`, and INV-TV6's student-privileges clause holds on the normal conversion path (role flips to `student`). The teacher-with-`students`-row creation carve-out (INV-TV6 extension) is deferred → deferred-items **D7** (future ticket).
- **REQ-012 (Eligibility & Trial-First Hold — INV-B4/B8)**: WHEN creation proceeds THEN the system SHALL debit ONE allowance unit inside the same transaction via a guarded-conditional ladder: (1) `UPDATE students SET balance_trial = balance_trial - 1 … WHERE id = ? AND balance_trial > 0 RETURNING id`; if it matches a row, the held lane is `trial`; (2) ELSE the same guarded statement on the intent lane (`balance_hifz` for `Hifz`, `balance_tajweed` for `Tajweed`); (3) IF both match zero rows THEN the system SHALL throw `INSUFFICIENT_BALANCE` (422-class, localized) and the transaction SHALL roll back leaving zero writes. The debit SHALL precede the session insert so a failed insert can never strand a debit.
- **REQ-013 (Schema Deltas — Provenance & Idempotency, Push-Only)**: WHEN the hold mechanism is implemented THEN the schema SHALL gain EXACTLY two deltas, applied exclusively via `bun run db push` in the same commit set as the code: (a) `session.held_balance_lane varchar(20) NULL` (populated when `fee_held = true`; nulled on release/confirm later; vocabulary is the TS enum `HeldBalanceLane { Trial, Hifz, Tajweed }` in `backend/enum/scheduling/held-balance-lane.enum.ts` with an `isHeldBalanceLane` guard — NO new pgEnum, ApplicantStatus-varchar precedent); (b) a new table `session_request_idempotency` (`id` identity PK, `idempotency_key varchar(128) NOT NULL UNIQUE`, `user_id integer NOT NULL REFERENCES users(id) ON DELETE CASCADE`, `session_id integer NULL REFERENCES session(id) ON DELETE SET NULL`, `created_at timestamp NOT NULL DEFAULT now()`). No other structural diff is permitted; `db reset`/`cleanGenerate` remain forbidden.
- **REQ-014 (Idempotent Creation — DUPLICATE_REQUEST)**: WHEN `createSession` executes THEN the mutation SHALL require the `X-Idempotency-Key` header (`ctx.idempotencyKey`, adopted in consistency with `docs/IDEMPOTENCY.md`'s class-instance booking mandate — its mandated Affected Operations list covers the quota-era `class_instances` and SHOULD eventually be extended to name `session` bookings explicitly — and with the `DUPLICATE_REQUEST` success-equivalent contract in `docs/graphql/error-handling-contract.md`); a missing/empty key SHALL fail `VALIDATION` before any DB work. Inside the creation transaction (AFTER the certification lock and debit ladder) the system SHALL `INSERT` the claim row; a `23505` on the unique key SHALL translate via the cycle-safe cause-chain pattern (DEV1-002) into a `DUPLICATE_REQUEST` conflict — returning it as an idempotent-replay of the already-applied booking (success-equivalent per the error-handling contract's client mapping). Any failure/rollback releases the claim (the row rolls back with the transaction), so a failed booking never burns the key. No 24h sweeper ships in this ticket; claim age is not consulted (documented, D2-adjacent note).
- **REQ-015 (Start Transition)**: WHEN the session's teacher invokes `startSession(id)` THEN the system SHALL execute `UPDATE session SET status='started', started_at=now(), updated_at=now() WHERE id=? AND teacher_id=<ctx.user.id> AND status='scheduled' RETURNING *`; zero rows SHALL trigger ONE cold-path probe: nonexistent or foreign-owned → `SESSION_NOT_FOUND` (indistinguishable); owned but wrong state → `SESSION_INVALID_TRANSITION`. No other field may change; the deadline SHALL NOT re-arm.
- **REQ-016 (Complete Transition)**: WHEN the session's teacher invokes `completeSession(id)` THEN the system SHALL execute a single guarded `UPDATE session SET status='completed', ended_at=now(), confirmed_by_teacher_at=now(), updated_at=now() WHERE id=? AND teacher_id=<ctx.user.id> AND status='started' AND EXISTS (SELECT 1 FROM teacher WHERE teacher.id = session.teacher_id AND teacher.is_approved = true) RETURNING *` (certification re-asserted IN the statement — zero TOCTOU). Zero rows SHALL be disambiguated by the probe chain: nonexistent/foreign → `SESSION_NOT_FOUND`; wrong state → `SESSION_INVALID_TRANSITION`; decertified → `TEACHER_NOT_CERTIFIED`. Report submission is NOT required by this transition in this ticket (INV-S7 enforcement is DEV3-005 — D5).
- **REQ-017 (Cancel Transition + Hold Release)**: WHEN either participant (the session's student OR its teacher) invokes `cancelSession(id, reason?)` THEN the system SHALL, inside one transaction: (1) execute `UPDATE session SET status='cancelled', fee_held=false, updated_at=now() WHERE id=? AND status IN ('scheduled','started') AND (student_id=? OR teacher_id=?) RETURNING *`; on zero rows, probe: nonexistent/non-participant → `SESSION_NOT_FOUND`, else `SESSION_INVALID_TRANSITION` (covers completed/cancelled regression attempts — double-cancel can never double-refund because only the winner's transaction proceeds); (2) IF the returned row's `held_balance_lane` IS NOT NULL THEN re-increment THAT SAME lane by 1 on the student's row (unguarded increment — no upper bound exists; CHECK `>= 0` cannot trip) in the same transaction. A cancelled session SHALL keep `started_at` as-is and SHALL leave `ended_at` NULL.
- **REQ-018 (Terminal & Regression Guards — INV-S1/S2/S3)**: WHEN ANY transition is attempted from `completed` (to started/scheduled/cancelled) or from `cancelled` (to anything) THEN the guarded predicates SHALL match zero rows and the caller SHALL receive `SESSION_INVALID_TRANSITION` (owner) — the illegality is structural, not a code branch. No `disputed` transition surface exists (B.18/DEV3-022). No code path in this ticket may write `teacher_transaction`, `wallet`, or `student_payments` rows (INV-S3/INV-W4 by absence — grep-verifiable).
- **REQ-019 (Zero Side Effects)**: WHEN any lifecycle operation completes THEN it SHALL write no `notifications` rows (D1), no `audit_logs` rows (no admin action exists), no `reports`/`home_work` rows (DEV3-006), and SHALL NOT modify `teacher.is_online` (D5) — the ONLY tables written are `session`, `students` (one lane), and `session_request_idempotency`.

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (Creation Atomicity & Ordering)**: WHEN creation runs THEN the transaction order SHALL be EXACTLY: (1) teacher `SELECT … FOR UPDATE` + certification assertion; (2) guarded allowance debit ladder (trial → intent lane); (3) idempotency claim `INSERT`; (4) session `INSERT … RETURNING *`. Any failure SHALL roll back ALL of it — a forced-failure test SHALL prove zero rows in `session`/`students`-delta/`session_request_idempotency` and that the idempotency key is reusable after a failed attempt.
- **REQ-041 (Guarded Single-Statement Transitions — TOCTOU = 0)**: WHEN start/complete/cancel transitions execute THEN each SHALL be ONE guarded conditional `UPDATE … RETURNING *` with its full predicate (ownership + current status [+ certification EXISTS for complete]) evaluated under PostgreSQL's row lock; NO SELECT-then-update SHALL exist on the hot path; the post-null probe SHALL only disambiguate error CLASS (recognizing the DEV1-005 D3 cold-path pattern) and SHALL never influence writes.
- **REQ-042 (Cancel-Refund Ordering)**: WHEN cancellation executes THEN the guarded session transition SHALL precede the lane re-increment inside one transaction; double-cancel via `Promise.allSettled` SHALL yield exactly one success + one `SESSION_INVALID_TRANSITION`/`SESSION_NOT_FOUND` and EXACTLY ONE unit refunded; the final row shows `status='cancelled'`, `fee_held=false`, lane balance incremented exactly once.
- **REQ-043 (Chaos Matrix — Mandatory Proofs)**: WHEN chaos tests run THEN they SHALL prove via `Promise.allSettled`: (a) concurrent double-start → one success + one transition conflict, final `started`; (b) start⚡cancel race → deterministic winner, state consistent with the winner, refund iff cancel won; (c) double-complete → one success, `confirmed_by_teacher_at` written once; (d) two concurrent creations by a student holding exactly ONE unit → exactly one session + one `INSUFFICIENT_BALANCE`, balances never negative (DB CHECKs intact); (e) same idempotency key replayed concurrently N times → exactly one session, all others `DUPLICATE_REQUEST`.
- **REQ-044 (tx Propagation Everywhere)**: WHEN any repository method is written THEN it SHALL accept `tx?: DBTransaction` as the LAST parameter and every service flow SHALL thread one `tx` through ALL repository/Drizzle calls (including the eligibility ladder reads); services SHALL compose via the existing `withTransaction(outerTx)` SAVEPOINT-aware pattern so `runInRollback` tests isolate cleanly.
- **REQ-045 (Schema-Delta Discipline)**: WHEN implementation completes THEN `git diff` on `backend/db/schema/**` and `backend/db/migration/**` SHALL contain ONLY REQ-013's two artifacts; no custom SQL migration; no `db reset`/`cleanGenerate`; Drizzle schema remains the sole structural ground truth; `CHECK` constraints remain unchanged (new column is nullable, no new CHECK added — the lane vocabulary guard is app-layer per the ApplicantStatus precedent).
- **REQ-046 (Deterministic Time)**: WHEN any operation writes timestamps THEN each operation SHALL capture `now` ONCE and reuse it for `started_at`/`ended_at`/`confirmed_by_teacher_at`/`updated_at` within that operation; deadline math uses that same instant; concurrent operations NEVER share a captured instant.
- **REQ-047 (Process-State & Repo Discipline)**: WHEN new modules load THEN they SHALL hold ZERO module-level mutable state; read paths (`sessionById`, lists) use the `queryDb(tx)` Neon-HTTP-eligible pattern; no `inArray` exists anywhere in the slice (prepared-statement/`inArray` prohibition not triggered); no prepared statements are introduced for writes.

### 2.9 Cross-Actor Workflow Scenarios (Journeys)

The lifecycle is inherently cross-actor: one actor's write changes another actor's visible state over shared rows (`session`, `students` balance lanes). These journeys map 1:1 onto `test/workflows/sessions/session-lifecycle.journey.test.ts` (J1) and `test/workflows/sessions/session-lifecycle-denials.journey.test.ts` (J2), written TEST-FIRST.

**Actor Table:**

| Actor | Role / State | CAN | CANNOT |
|---|---|---|---|
| Student (has units / and a trial-only variant) | `role=student`, `students` row | create; read own; cancel own | start/complete; read others' sessions; see teacher-only lists |
| Certified Teacher | `role=teacher` + `teacher` row `is_approved=true` | read own sessions; start; complete; cancel own | create — unconditionally `FORBIDDEN` in this slice (Ruling 2026-08-30 → D7); mutate others' sessions |

| Super Admin | `role=admin` | nothing in this ticket | everything here (DEV3-021 owns it) |
| Anonymous | none | nothing | everything (`UNAUTHORIZED`) |

**Journey J1 — Full Happy Lifecycle (request → hold → start → complete; and a second fixture: cancel-with-refund):**

1. *System* → commit fixtures: student A (trial + 1 hifz unit), student B (trial only), certified teacher T, applicant AP → tracked ids.
2. *Student A* → `createSession(T, Hifz, key K1)` → **state:** session `scheduled`, `feeHeld=true`, `heldLane=trial` (trial-first), A.trial −1; student B: `createSession(T, Hifz)` → his trial binds.
3. *Teacher T (observer)* → `myTeacherSessions` ⇒ sees A's and B's sessions, `scheduled`, correct fees/deadlines. *Student A (observer)* → `myStudentSessions` ⇒ identical visibility of his own; **trial lane provably consumed before paid lane**.
4. *Student A* → replays K1 → `DUPLICATE_REQUEST`; zero new rows; A's balances unchanged (observer: T's list count stable).
5. *Teacher T* → `startSession(A's id)` → `started`, `startedAt` set; *student A (observer)* reads `sessionById` ⇒ `started`.
6. *Teacher T* → `completeSession(A's id)` → `completed`, `endedAt`, `confirmedByTeacherAt` set, deadline unchanged; *student A (observer)* ⇒ `completed`; **student confirmation & wallet deliberately absent (D2).**
7. *Student B* → `cancelSession(B's id)` → `cancelled`, `feeHeld=false`, **trial lane +1 back exactly once**; *Teacher T (observer)* ⇒ session `cancelled` in his list.
8. *Teacher T* → `cancelSession(completed id)` → `SESSION_INVALID_TRANSITION` (INV-S1 family); row unchanged.
9. *Teardown* → tracked hard-delete; zero residue; second consecutive run passes identically.

**Journey J2 — Hostile & Boundary Legs (denials):**

1. *Applicant AP* → targeted as teacher in creation → `TEACHER_NOT_FOUND`; caller's balances untouched.
2. *Student A with zero units everywhere* → `INSUFFICIENT_BALANCE`; zero writes; key reusable after.
3. *Second Student* → `cancelSession(others' id)` / `sessionById(others' id)` → `SESSION_NOT_FOUND` / `null` — indistinguishable from nonexistent (REQ-J4).
4. *Applicant AP calling `startSession`* → role-scope allows teacher role but NO session row can exist for him → `SESSION_NOT_FOUND`.
5. *Creation with `intent=evaluation`* → `VALIDATION` pre-DB; `teacher_evaluation` type rows impossible through this surface.
6. *Admin & Parent callers* → typed `FORBIDDEN`/`SESSION_NOT_FOUND` on every op; zero audit rows (REQ-019 count-delta assertion).

**Cross-Actor EARS Criteria (observer-phrased):**

- **REQ-J1**: WHEN a student books THEN the TEACHER observing his own list SHALL see exactly one new `scheduled` session AND the student's lane SHALL be debited trial-first, while EVERY other observing role SHALL see no trace of it.
- **REQ-J2**: WHEN the teacher starts and completes THEN the STUDENT observing the session SHALL see `started` then `completed` with `confirmedByTeacherAt` set and `confirmationDeadline` unchanged, and NO wallet/balance mutation SHALL be observable by anyone (D2-owned).

- **REQ-J5**: WHEN terminal states are reached (`completed`, `cancelled`) THEN EVERY subsequent transition attempt by ANY actor SHALL fail with `SESSION_INVALID_TRANSITION`-class errors and the rows SHALL remain immutable thereafter (INV-S1/S2).
- **REQ-J6**: WHEN fixture teardown runs THEN a fresh identical journey SHALL pass with identical outcomes proving zero residual state leakage (harness honest-cleanup proof).
