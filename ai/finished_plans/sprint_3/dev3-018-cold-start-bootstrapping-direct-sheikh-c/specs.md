## 1. Executive Summary & Problem Statement

**Feature:** Ship the platform's cold-start certification authority: ONE new admin-gated mutation, `adminCertifyTeacherColdStart(userId: Int!, makeEvaluator: Boolean = true): AdminUserDetail!`, that promotes an existing teacher-role user to a certified founding Sheikh — inserting the `teacher` row with `is_approved = true` (+ `is_evaluator` per the flag, default `true`), finalizing the `applicants` row when present (`status = 'passed'`, `cooldown_until = NULL`), appending exactly one in-transaction `audit_logs` row with `action_type = 'override'`, and emitting one localized `evaluation_result` notification to the certified teacher (transactional insert via the engine; publish strictly after commit). This is INV-TV1(b) made executable: the ONLY sanctioned path that mints a teaching authority without the 5-session loop.

**Problem from user perspective:**

- **Super Admin (Workflow 05 §3):** at platform launch there are ZERO certified Shuyukh, so the evaluation loop cannot run (INV-TV2 requires 5 distinct certified evaluators who do not yet exist). The Admin needs a sanctioned, audited, race-safe switch that forms the founding Evaluation Committee. Today there is NO such path: `DEV3-016`'s create flow deliberately mints only an `applicants` row and NEVER a `teacher` row (INV-TV1 enforcement).
- **Founding Sheikh (recipient):** on direct certification he must (a) become teachable and evaluable immediately (`is_approved`/`is_evaluator`), (b) receive a truthful notification of certification (Workflow 05 §3 "Onboarding notification"), and (c) never carry a stale cooldown or half-finalized applicant record into his certified life (the lifecycle doc's own rule: a pass must clear `cooldown_until` — `docs/teachers/applicant-lifecycle.md` §6).
- **Teacher-Applicant integrity (downstream consumers):** DEV2-006's evaluation booking needs `is_evaluator = true` members to exist; the applicant lifecycle invariants (B.6/B.7, INV-TV1) require that this admin path — and ONLY admin paths — can mint a `teacher` row outside the aggregation flow.
- **Compliance/observer (admin peers, DEV3-020's trail browser):** every certification must be reconstructable from the audit trail: WHO certified WHOM, with WHAT flags, WHEN.

**Business value:** Without this ticket the platform literally cannot seed its teacher marketplace — the certification loop is circularly dependent on a committee that only cold-start can create (Workflow 05 §3). This also completes the DEV3-016 scope-split row ("Cold-start bootstrapping … DEV3-018") and satisfies FR-3.9 + the M3 release gate's admin-governance pillar (`docs/planning/ROADMAP.md`).

**Actors involved:**

| Actor | Role |
|---|---|
| **Super Admin (caller/actor)** | The ONLY certifier; every write is attributed to `ctx.user.id`. |
| **Founding Sheikh (target)** | A teacher-role user holding (normally) an `applicants` row; becomes the certified teacher/evaluator; receives the certification notification. |
| **Admin B (observer)** | Reads back the new state through EXISTING surfaces (`adminUserDetail` teacher snapshot; `adminUserActivity` audit entries). |
| **Non-admin roles (student/teacher/parent)** | Structurally denied at scope AND service layers. |
| **Downstream consumers** | DEV2-006 (committee membership), DEV3-020 (audit read-back of our `override` rows), DEV3-022c (analytics counts now truthful), DEV3-019 (sibling admin onboarding — untouched). |

**Non-goals (explicitly OUT of scope):**

- **NO UI affordance.** The admin "Certify (cold-start)" button/page is DEFERRED (ledger item D-UI, owner: the admin teacher-management surface ticket). The admin views layer exists (shipped users + plans surfaces), but no certification affordance exists on any admin surface yet; `navItems.ts` is NOT touched; the `/teachers` nav item keeps its current target.
- **NO teacher-elevation of the evaluator flag on an ALREADY-certified teacher** (`is_approved=true` → flip `is_evaluator`). That is a separate governance mutation (ledger D-EVALUATOR-ELEVATION). This ticket's rule: an existing APPROVED row ⇒ conflict, always.
- **NO changes to any existing write path** — registration (`RegistrationService`), DEV3-016's `AdminUserManagementService`, and the applicant lifecycle service are imported-by-reference, never edited.
- **NO subscription/payment/verification-plan side effects.** Cold-start bypasses purchase BY DESIGN (INV-TV1(b)); zero writes to `plans`, `subscriptions`, `student_payments`, `wallet`.
- **NO session/evaluation-loop integration.** The committee's usability by DEV2-006 is a downstream consumption fact, proven here only at the read level (the flags exist and are queryable).
- **NO new Pothos object types and NO new schema.** The mutation returns the existing `AdminUserDetailPothosObject`; zero `backend/db/schema/**` diffs (no `db push`); the `DateTime` scalar question is moot (no new timestamp-bearing fields are introduced by this mutation's contract beyond what the reused object already exposes).
- **NO edit of the applicants row beyond the finalize rule**, and NEVER deleting the applicants row (history is preserved).
- **NOT in the `docs/IDEMPOTENCY.md` mandated key set.** Replay protection is the already-certified conflict (repeat ⇒ `TEACHER_ALREADY_CERTIFIED` BEFORE any second notification or audit row) — documented, not key-wired.
- **NO edits to `docs/specs/open-decisions-and-gaps.md` or `docs/specs/state-machine-invariants.md` numbering** — this ticket binds by reference (INV-TV1(b), B.6/B.7, A.5).

### 2.2 Core Feature Logic / Happy Paths

- **REQ-010 (Cold-Start Certification — Row-Absent Path)**: WHEN an active admin certifies an existing, non-governed, teacher-role user with NO `teacher` row THEN the system SHALL, inside ONE transaction: insert the `teacher` row with `isApproved = true` and `isEvaluator = <makeEvaluator>` (insert-time defaults honored for `averageRating` NULL / `isOnline = false` / `subjects` NULL / `requestPreference` default `"queue"` per `backend/db/schema/teachers/teacher.ts:25-30`), and commit that row alongside the finalize + audit + notification writes of REQ-012/017/016 — never partially.
- **REQ-011 (Elevation Path — Unapproved Row Exists)**: WHERE a `teacher` row exists with `is_approved = false` (e.g. pre-created by a future flow) THEN a certification call SHALL elevate it via a SINGLE guarded UPDATE (`SET is_approved = true, is_evaluator = <makeEvaluator> … WHERE id = ? AND is_approved = false … RETURNING`); a zero-row RETURNING on that path SHALL be disambiguated by a follow-up existence/state read and resolve to the REQ-013 conflict — never to a silent no-op.
- **REQ-012 (Applicants Finalization — Lifecycle Coherence)**: WHEN the certification write commits THEN any EXISTING `applicants` row for the target SHALL be finalized in the same transaction to `status = ApplicantStatus.Passed` and `cooldownUntil = NULL` (the lifecycle doc's clear-on-pass rule — `docs/teachers/applicant-lifecycle.md` §6 consumer guidance), REGARDLESS of prior status (`pending` / `in_evaluation` / `failed`) and REGARDLESS of any active cooldown (admin cold-start SUPERCEDES it — INV-TV1(b) supreme-authority reading); `verificationAttempts`/`lastAttemptAt` are NEVER rewritten by this flow. WHERE NO `applicants` row exists, the certification proceeds and the audit `details` SHALL record that fact (`applicantRow: "absent"` vs `"finalized"`).
- **REQ-013 (Already-Certified Conflict)**: IF the target's `teacher` row exists with `is_approved = true` THEN the mutation SHALL throw `ConflictError("TEACHER_ALREADY_CERTIFIED", <localized>)` and SHALL write ZERO rows (no teacher/applicants mutation, ZERO audit rows — JR-C-1 — and ZERO notifications/publishes). The `ConflictError(code, message)` overload is verified at `backend/lib/errors.ts:170-182`.
- **REQ-014 (Target Role Gate)**: IF the target user exists but `users.role != teacher` THEN the mutation SHALL reject with `ConflictError("TEACHER_ROLE_REQUIRED", <localized>)` BEFORE any write — certification NEVER coerces `users.role` (role mutation is a different, unbuilt surface) and NEVER mints a `teacher` row for a non-teacher role (shared-PK coherence).
- **REQ-015 (Target Governance Gate)**: IF the target user is governed (`isDeleted OR isBlocked OR suspended` — NULL-safe OR) THEN the mutation SHALL reject with `ConflictError("TEACHER_ACCOUNT_GOVERNED", <localized>)` BEFORE any write. Rationale: certifying a deleted/blocked/suspended account is incoherent — the admin must reactivate first (composition, not coercion); suspension-window hysteresis (`suspendedPeriodDays`) is deliberately NOT consulted (mirrors the login SSR hard-stop at `backend/lib/auth/server-auth.ts:97-106`).
- **REQ-016 (Certification Notification — In-Tx Emit, Publish-After-Commit)**: WHEN a certification commits THEN the SAME transaction SHALL contain ONE `notifications` row for the target via `NotificationEngine.emitForUser({ userId: target, type: NotificationType.EvaluationResult, title, body, relatedEntityType: "teacher", relatedEntityId: target }, locale, tx, options)` (copy composed in the ADMIN's locale per A.4.3 emitter-locale rule; per-recipient locale routing remains engine-deferred D2 — out of scope), and the returned receipt SHALL be published ONLY after the transaction commits via `NotificationEngine.publishReceipts([receipt], locale, options)`. A mid-transaction failure SHALL make the publish structurally unreachable (zero rows, zero audit, zero pushed envelopes).
- **REQ-017 (Audit Emission — In-Tx, Exactly Once, `override`)**: WHEN the certification transaction commits THEN it SHALL contain EXACTLY ONE `audit_logs` row via `AuditService.createAuditLog` inside that transaction: `actorId = <calling admin id>` (never input), `actionType = AuditActionType.Override`, `entityType = "teacher"`, `entityId = <target user id>`, `details` = a ≤2000-char PII-free JSON carrying ONLY `{ makeEvaluator, applicantRow: "finalized" | "absent", elevation: "created" | "elevated" }` — never names/emails/content. Denials (REQ-013/014/015/030 paths) SHALL append ZERO audit rows (JR-C-1 parity, `docs/admin/user-management.md` §2.4).
- **REQ-018 (Return Contract — Truthful Fresh Detail)**: WHEN the certification succeeds THEN the mutation SHALL return the REFRESHED `AdminUserDetailReturnType` read through the SAME transaction (so the `teacher` snapshot `{ isApproved: true, isEvaluator }` and, when finalized, the `applicant` snapshot `{ status: Passed }` are already visible), never a hand-assembled partial. The read composes the EXISTING `AdminUserManagementService.getUserDetail(id, locale, actorId, tx)` — no forked assembler.
- **REQ-019 (`makeEvaluator` Semantics)**: WHEN the mutation omits `makeEvaluator` THEN it SHALL DEFAULT to `true` (FR-3.9: the cold-start cohort IS the Evaluation Committee); an explicit `false` SHALL certify WITHOUT evaluator capability (`teacher` can teach; cannot evaluate applicants).
- **REQ-020 (Cross-Entity Purity)**: WHEN any certification path runs THEN the ONLY tables written SHALL be `teacher` (insert or guarded update), `applicants` (finalize update, conditional), `audit_logs` (one row), and `notifications` (one row); ZERO writes to `users` (profile/role/governance), `wallet`, `subscriptions`, `plans`, `session`, `teacher_transaction` SHALL occur (oracle-proven by tests).

### 2.4 Atomicity, Concurrency & Data Integrity

- **REQ-040 (Single Transaction Boundary)**: WHEN a certification executes THEN ALL writes (teacher insert/elevate → applicants finalize → audit insert → notification emit) SHALL occur inside ONE `withTransaction(outerTx, fn)` (`backend/lib/db/with-transaction.ts`, imported at `user-management.service.ts:67`, call sites `:881, 946, 987`) with the SAME `tx` propagated to EVERY repository/engine call (mixed `tx`/`db` inside the flow is PROHIBITED); the returned detail is read inside the same `tx` (REQ-018).
- **REQ-041 (Mid-Stage Failure ⇒ Full Rollback + Zero Publish)**: IF ANY stage throws (constraint error, forced repo failure) THEN the transaction SHALL roll back — ZERO residual `teacher`/`applicants` mutations, ZERO audit rows, ZERO notification rows — AND `publishReceipts` SHALL NOT be invoked (structurally unreachable pre-commit; proof mirrors `notification-engine.service.ts:352-357`).
- **REQ-042 (Concurrent Certification Race)**: WHEN two admins concurrently certify the SAME target THEN exactly ONE commits the row-creation/elevation and the other SHALL surface `TEACHER_ALREADY_CERTIFIED` via the `teacher.id` PK unique violation (`23505` cause-chain translation — the `translateDbError` (`backend/lib/errors.ts:200-208`) / `isUniqueViolation` (`backend/services/shared/user-provisioning.helpers.ts:74`) precedent) on the insert path, OR via the guarded-UPDATE zero-row + re-read disambiguation on the elevation path; the final DB state SHALL show exactly ONE certified row and the LOSER SHALL have appended ZERO audit rows and emitted ZERO notifications.
- **REQ-043 (Certify-Once Replay Answered by Conflict, Not Keys)**: WHEN a caller double-submits (UI double-click, retry) THEN the second call SHALL resolve as REQ-013 — this is the documented idempotency ruling for this surface (admin op outside the `docs/IDEMPOTENCY.md` mandated key set; mirrors the DEV3-016 ruling, `docs/admin/user-management.md` §2.5); a replay NEVER produces a second notification because the conflict precedes emission.
- **REQ-044 (Historical Preservation)**: WHEN certification commits THEN it SHALL preserve all historical rows: the `applicants` row lives on (only `status`/`cooldown_until` change), and NO teacher/user/applicant/history row is ever deleted (INV-U1/U4/U5 preserved by construction).
